# ADR 0034 — Jonah proposals: reviews of sent-back runs propose definition changes, approved by publishing

Status: accepted · 2026-10-28 · Amends [ADR 0002](0002-jonah-evals.md) (its phase 5 amendment, decisions 2 and 5) · Builds on [ADR 0014](0014-factory-rules.md) (`rules/` in a definition), [ADR 0016](0016-ui-revamp.md) (the screens are binding) and [ADR 0008](0008-portable-runs-connections-and-knowledge.md) (run boxes and connections)

## Context

The approved Jonah screens, [jonah](../design/screens/jonah/jonah.html) ([picture](../design/screens/jonah/jonah.jpg)) and [proposal](../design/screens/jonah/proposal.html) ([picture](../design/screens/jonah/proposal.jpg)), bind the UI ([ADR 0016](0016-ui-revamp.md)). The overview lists what Jonah noticed this week: each observation has a summary, a detail line, the items it is based on and either "Proposed" or "Watching, 3 of 5". A proposal page shows one hypothesis: a title, the files it changes as diffs (for example `agents/frontend-engineer.md` and `rules/evidence.md`, "2 files, v21 to v22"), why (the runs that review sent back, each with its quoted reason), the metric it should move with a value before and after, and Approve, Edit and Reject.

That differs from the plan in [phase 5, continuous learning](../history/specs/5-continuous-learning.md) and from the phase 5 amendment of [ADR 0002](0002-jonah-evals.md#amendment--phase-5-the-minimal-loop). They planned one retro run per finished item with touches; proposals of three kinds (Learned facts, single-file edits, eval cases) whose edits go into the draft; and an allowlist without `rules/`. The plan stays unchanged as a record. Four facts in the repository disagree with it today:

- **Migration numbers.** The plan reserves `00060–00069` with `00060–00062` planned, but `db/migrations/` already holds `00060_item_paths.sql` through `00074_saved_views.sql`, written by other work.
- **`rules/`.** [ADR 0014](0014-factory-rules.md) added `rules/` to a definition after the plan was written, and the proposal screen edits a rule.
- **Many runs, many files.** The screens build one proposal from several sent-back runs (four on the sample screen) and let it change several files. A retro on one item cannot see a pattern across items.
- **Approve publishes.** The screen's Approve publishes a new version ("Publishes v22; runs in progress keep v21"). Edit is the path into the draft.

What exists to build on: the `item_touches` view (`db/migrations/00052_touches.sql`) gives each person's touch of an item with its kind (`rejected`, `gate_rejected`, …), its station and its labelled reason. The permissions `definition:edit` and `definition:publish` exist in `contracts/api/permissions.yaml`. The 409 code `draft-open` already means "the factory has an open draft", and `draft-conflict` already means "the draft changed under you" (412) in the draft file routes. `internal/jonah` holds Jonah's judge and eval loops, and depguard limits it to `domain` and `ports`. `engine.RunTask` does not exist yet: the part that extracts it from the line's run lifecycle comes with this work.

## Decision

1. **A Jonah review is one agent run per factory, of run kind `jonah`, through the engine's run lifecycle (`engine.RunTask`).** The review reads the factory's sent-back events: the `rejected` and `gate_rejected` touches from `item_touches`, with their reasons, in a window since the last review. It also reads the files of the current definition version and the proposals rejected in the last 90 days with their reasons. It runs in a small box with the factory's model connection only: no repository, no other connection and no MCP tools. Its task token is of kind `jonah` and names no connection. The loop lives in `internal/jonah` (domain and ports only), next to the judge and eval loops. This replaces the name `internal/core/jonah` that the brief for this work used: the package already exists at `internal/jonah` and depguard enforces it there.
2. **A review is queued by a person or by the threshold, one at a time, within a weekly budget.** A person can press "Look for improvements now", which queues a manual review. goald's loop queues a threshold review when the factory has at least `learning.jonah.proposeAfter` (default 5) new sent-back touches since the last review. At most one review is pending or running per factory; a second request while one is pending or running gets that one. No review is queued, by either way, while the cost of the factory's review runs over the last 7 days is at or above `learning.jonah.weeklyUsd` (default 10, in US dollars).
3. **A review outputs observations and proposals.** An observation has a summary, a detail line, the items it is based on and a count. A proposal is one hypothesis: a title, a summary, a set of file edits, its evidence and an estimate. Each edit is a path, a `base_sha256` (the SHA-256 of the file in the version the review read; empty for a new file) and the file's new content. The evidence is the sent-back events the proposal rests on, each with the quoted reason. The estimate names the metric the proposal should move, sent-back rate or lead time p85, for one station; the model's estimated value after; and the change in cost per item. goald computes the value before from the recorded events; the model never supplies it.
4. **Edits touch only `factory.yaml`, `agents/`, `skills/`, `rules/` and `contracts/`, never `evals/`.** goald checks every path against that allowlist before it stores a proposal and drops a proposal with any other path. The store refuses one too, with a CHECK on the edit's path. Judges and eval cases change only by a person.
5. **A threshold review proposes only what it has seen often enough.** On a threshold review, an observation becomes a proposal only when its count reaches `proposeAfter`. Until then it shows as "Watching, n of proposeAfter" (for example "Watching, 3 of 5"). A manual review may propose below the threshold, because a person asked.
6. **Proposals are numbered per factory and have five states.** Each factory numbers its proposals from 1 ("Proposal 7"). The states are `proposed`, `published` (approved, and the version is published), `applied` (written into the draft by Edit), `rejected` and `superseded` (a later review replaced it, or another proposal's publish changed a file it edits).
7. **Approve publishes as the approver.** Approve opens a draft from the current version, writes the proposal's files into it and publishes it as the person who approved. It needs `definition:publish`. It is refused with 409 `draft-open` when the factory already has an open draft, and with 409 `proposal-stale` when a file's current SHA-256 no longer matches its `base_sha256`. Publishing goes through the same validation and publish path as the builder, so every check that gates a publish gates this one.
8. **Edit writes the proposal into the draft and hands it to the builder.** Edit applies the proposal's files to the draft, opening one from the current version if none is open, and the person continues in the builder. It needs `definition:edit`. It is refused with 409 `draft-conflict` when the draft's copy of a file no longer matches the proposal's `base_sha256`.
9. **Reject needs a reason, and later reviews read it.** Reject stores the person's reason with the proposal. Every later review of the factory reads the proposals rejected in the last 90 days with their reasons (decision 1), so Jonah does not propose the same change again.
10. **Restore stays the undo.** A published proposal is an ordinary version. To undo it, a person restores the earlier version; nothing new is built for this.

Out of this decision, for later work: Learned facts, eval cases and eval runs proposed by a review, judges in reviews, bake-offs, auto-publish and sampling. The screens show eval results and judges on these pages; until that work lands, the pages leave those parts out.

## Consequences

- One review per factory reads many sent-back runs, so a pattern across items (four UI changes without a screenshot) becomes one proposal instead of four retros that each see one item.
- People approve a complete change in one press. The cost is that Approve publishes without a second look in the builder; Edit is there for a person who wants one, and Restore undoes a bad publish.
- `base_sha256` makes a stale proposal visible instead of silently overwriting a newer file. A person must reject or re-run a stale proposal.
- Rejected reasons in later reviews' input keep Jonah from repeating itself, at the price of a longer prompt; the 90-day window bounds it.
- The weekly budget and the one-review-per-factory rule bound the cost of a factory that sends back a lot of work.
- What must change and who does it, in the parts of the assembly that ship with this ADR: `spec.learning.jonah` (`proposeAfter`, `weeklyUsd`) in the factory definition schema; the tables for reviews, proposals and observations in the next free migration (`00075` at the time of writing, not the plan's `00064`), with row-level security and the path CHECK; `engine.RunTask`, shared by line runs and review runs; goal-agent's `jonah` mode; the review loop in `internal/jonah`, run by goald; the API routes and the error codes `draft-open`, `proposal-stale` and `draft-conflict`; `goal jonah` in the CLI; and the overview and proposal screens. `docs/engineering/architecture.md` still describes retros and should be updated by the part that builds the loop.
