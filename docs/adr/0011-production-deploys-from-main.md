# ADR 0011 — Production deploys from main through GitHub Actions

Status: accepted · 2026-10-25 · Builds on [ADR 0008](0008-portable-runs-connections-and-knowledge.md) (the Cloudflare install) and [ADR 0010](0010-infrastructure-applied-from-main.md) (the `production` environment)

## Context

Until now a person deployed the app by hand: `wrangler deploy` from `deploy/cloudflare`, which builds the goald, auth and goal-agent images, pushes them to Cloudflare's registry and deploys the control Worker. The owner decided that a merge to main which changes the app deploys production on its own, once CI has passed for that commit.

## Decision

1. **`.github/workflows/deploy.yml` deploys on `workflow_run` of `ci`**, only for a successful run of a push to main from this repository, and checks out that run's `head_sha`. Pull requests never deploy. *Amended 2026-11-02:* the owner's rule is that ci runs only on pull requests into main, so there is no ci on main to follow. `deploy.yml` has only the `workflow_dispatch` trigger: a person dispatches it with a sha of main, and it checks that the sha is a commit of main (`git merge-base --is-ancestor`) and deploys it. It looks for no ci run, because every commit of main arrived through a pull request into main that passed ci. A merge no longer deploys on its own.
2. **Only when the app changed.** `workflow_run` has no paths filter. A first job compares the commit with the one the last successful deploy job deployed (the run name carries the sha) over the app paths: `cmd/`, `internal/`, `apps/web/`, `apps/worker/`, `apps/auth/`, `packages/`, `deploy/cloudflare/`, `db/migrations/`, `contracts/`, `go.mod`, `go.sum` and the pnpm files. Comparing with the last deploy, not with the parent commit, means a failed or superseded deploy is never forgotten. `deploy/terraform/`-only and docs-only pushes deploy nothing. *Amended 2026-11-02:* withdrawn. A person chooses the commit, so there is no paths check and no lookup of the last deploy.
3. **The same tasks a person runs.** `task deploy:worker` (wrangler deploy), then `task deploy:health`: `GET /v1/health` on the public host must answer `{"status":"ok"}` within 5 minutes, else the job fails.
4. **One deploy at a time.** A concurrency group that never cancels a deploy in flight. *Amended 2026-10-25:* ci on main is never cancelled in flight either (ci cancels superseded runs only for pull requests), so its runs on main finish in push order and a `workflow_run` deploy can always follow the newest merge; before this, merges faster than ci cancelled every ci run on main and nothing deployed. *Amended 2026-10-26:* only the newest push deploys. Each event has its own concurrency group; a newer push deploy cancels the push deploy in flight, a rollback (workflow_dispatch) is never cancelled, and a guard step keeps a rollback and a push deploy from running `wrangler deploy` at the same time. Cancelling is safe because the next deploy diffs against the last *successful* deploy and only newer cancels older (cloudflare-operations.md, Deploys). *Amended 2026-11-02:* with only manual runs, there is one concurrency group, `deploy-production`, that never cancels a run in flight, and no guard step. GitHub keeps one pending run per group, so a newer dispatch replaces an older one still pending. ci no longer runs on main, so the rule that ci on main is never cancelled is gone.
5. **Its own credential.** The deploy job runs in the GitHub environment `production`, which admits every branch for the pull request plans (ADR 0010); the workflow itself runs only for main and accepts a manual run only from main. It reads only `CLOUDFLARE_DEPLOY_API_TOKEN`, an account token made by hand with what `wrangler deploy` needs, and `CLOUDFLARE_ACCOUNT_ID`. It never reads terraform's stronger `CLOUDFLARE_API_TOKEN` from the same environment. The token goes only into the env of the wrangler step. There is no other registry login: wrangler pushes the images with the same token. *Amended 2026-11-02:* a dispatch is accepted from any ref, not only main; the sha must still be a commit of main. A dispatch from another ref runs that ref's copy of the workflow with the deploy token, which the `production` environment already admits for every branch. Only people with write access can dispatch, and a change to a workflow is reviewed like any other.
6. **Rollback is a deploy of an earlier commit.** Run the workflow by hand with the sha of a commit of main that `ci` passed for. It deploys that commit without the paths check. Migrations are forward-only and are not rolled back. *Amended 2026-11-02:* a rollback is a dispatch like any other, with the sha of an earlier commit of main; it no longer checks that ci passed for it.

## Consequences

- A merge of an app change is a deploy. *Amended 2026-11-02:* no longer: a merge does not deploy, and production runs the last commit someone dispatched. A change to the boxes' networking passes the network gate (runbook, bootstrap step 9) before it is merged, not before a deploy.
- The health check shows that the public host is healthy, not which version answers.
- The runbook (`docs/engineering/cloudflare-operations.md`, Deploys) lists every secret and variable the workflow reads, and where each value comes from.
