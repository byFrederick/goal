# ADR 0015 — Overlapping in-flight work: plans see open work, bind late and wait for the files they share

Status: accepted · 2026-10-26 · Builds on [ADR 0012](0012-assemblies-and-parts.md) (assemblies, parts, `work_items.paths` and the waiting reason) and the item dependencies of migration 00058 (`item_edges` and the claim gate)

## Context

Owners hold new requests until a running assembly finishes. The station that plans the work plans against a main that is mid-change: it cannot see what is in flight, so a part's brief names paths that another assembly moves before the part runs. One structure request was submitted while an assembly was still moving `terraform/` and `docs/design/`; its parts were planned against the old layout. Shared files cause the rest: `Taskfile.yml`, `docs/engineering/change-map.md` and `AGENTS.md` are edited by most items, so two items merged close together conflict and the second goes back to rework.

The pieces to fix it exist. `item_edges` (migration 00058) gates claims on `planned`, `linked` and `overlap` edges, `work_items.paths` (migration 00060) holds the globs each item expects to change and `Transition.Paths` replaces them, `domain.PathsOverlap` compares two sets of globs, `Store.ItemByNumber` finds an item by its ref, `ports.CodeHost.UpdateBranch` reports a merge conflict, and `ItemWaiting {kind, items, files}` says why an item waits. Nothing writes `overlap` edges, reads `work_items.paths` or tells a run what else is open. The factory definition has `flow.assemblies` (`freshBase`, `onConflict`, `overlap`, `materialize`) and per-agent `tools.allow`; a station has no setting that gives its run the open work.

The goal: a person submits at any time and gets the same result as if they had waited. As with ADR 0012, everything stays factory config: no station, agent or work type is named in Go, SQL or TypeScript (AGENTS.md rule 1): a station opts in with a boolean, never by its name.

## Decision

1. **The planner sees in-flight work.** A station whose definition sets `context: [inflight]` (a new optional list on a station in `contracts/definitions/factory.schema.json` whose only value is `inflight`; no station is named in code, AGENTS.md rule 1) gets an `## In flight` section in its run's `GOAL_FEEDBACK`. The section lists at most 30 of the factory's open items and assemblies (neither done nor cancelled), leaving out the item itself, its own assembly and that assembly's other parts. Each entry gives its ref (`<factory>#<number>`), title, state, station and paths: `work_items.paths`, or for an assembly the union of its open parts' `part_paths`. Entries are ranked by how many of their path globs have a literal prefix (the glob up to its first wildcard) that appears in the item's title or body, then most recently updated first; entries without paths come last. The section states what it lists and gives the agent no instructions: how agents use it belongs in the factory's prompts and rules. The same list will be a gateway tool, `goal__inflight`, granted by `tools.allow`, so any agent can ask for it; `context: [inflight]` preloads it.

   *Amended 2026-10-26 (software#121):* the opt-in was a boolean `inFlight: true` and the section told the agent to name an overlapping item in `after` or declare the overlapping paths. The owner moved the context to a gateway tool preloaded per station with `context: [inflight]`, and the instructions to the factory's prompts. The rendering and ranking are `domain.InFlightSection`, which the tool will reuse; the tool is not built yet. Decision 5 still says `inFlight: true`: it means a station with `context: [inflight]`.
2. **The `after` output field.** Like `lane` and `plan` (ADR 0012), `after` is platform-defined: an optional top-level list of item refs of the same factory, outside the `plan`. When a station finishes with it, the engine checks that every ref exists (`Store.ItemByNumber`) and is open, then adds a `linked` edge by the agent actor. For a single item the edge goes from the item; for a plan it goes from every part that has no in-plan needs. An unknown, closed or other-factory ref, or an edge that would close a cycle, fails the output with a reason, and nothing is written.

   *Amended 2026-10-26 (software#120):* the owner made the field's name config, as decision 3 does for paths. The definition maps the output property with `board.flow.dependencies.after: <property>`; with that key unset no property is read. The checks and edges are as above.
3. **A mapped output field replaces the item's paths.** The definition names the output field with a new optional `flow.dependencies.paths` (for example `paths: touches`, the software factory's spec contract field); the platform names none (AGENTS.md rule 1), the same way `flow.assemblies` is config. When a station finishes with a non-empty list of globs in that field, the engine replaces the item's `work_items.paths` with it through `Transition.Paths`. An output without the field, or with an empty list, and a definition that maps no field leave paths as they were (as `Assemble` set them). Amended 2026-10-26 by the owner: the first draft made `touches` a platform-defined field.
4. **The overlap hold.** When the engine claims an item with paths and `flow.assemblies.overlap` is `serialize` (the default), it first adds an `overlap` edge to every open, lower-numbered item of the factory whose paths overlap (`domain.PathsOverlap`). It skips the items of the item's own assembly, assemblies themselves (their parts carry the paths), items already needed and any edge that would close a cycle. The engine writes the edges for a station's waiting items before it calls `ClaimNext`, since the store picks the item, so the claim gate skips a held item in the same claim. The claim gate then holds the item until those items are done or cancelled. With `overlap: allow` no overlap edge is written.

   *Amended 2026-10-26 (software#133):* ordering by item number alone held work that was further along behind work that had not started: an item back at build after a merge conflict waited for lower-numbered parts of another assembly still queued at the first station, and an unlinked edge came back on the next turn. The hold now orders by progress on the line. An item has *started* when its station comes after the line's first agent station (by position in the line's stations), or when it has a run; an item at a station not on the line has not started. A started item never waits for one that has not; of two started items the one at the later station goes first, and a tie, like two items that have not started, goes to the lower number. The hold may therefore make a lower-numbered item wait for a higher-numbered one, so it reads every open item of the factory with paths. On every turn, before it adds edges, it removes each waiting item's `overlap` edge whose reason no longer holds (the paths no longer overlap, or the needed item no longer goes first) with an `edge_removed` event by the engine whose data carries the `reason` (`Store.RemoveEdge` takes one). When an edge it adds would close a cycle because the other item still has a stale `overlap` edge on this one, it removes that edge and adds its own. `planned` and `linked` edges are never removed by the hold. The order stays config-driven (`flow.assemblies.overlap`) and names no station.
5. **Plans bind late.** When a station with `inFlight: true` finishes, the engine records the head commit of the code-host repository's default branch in `work_items.base_commit`; `Assemble` copies it to every part. When such an item is later claimed at a station with `inFlight: true`, or sent back to rework after a merge conflict, and main has commits since `base_commit` that touch its paths, its `GOAL_FEEDBACK` gets a `## Changed since your plan` section. Each entry gives the commit's merged item ref and title (matched by the `merged` event's sha), or the commit subject when no item merged it, and the changed paths that overlap the item's. The section tells the agent to re-derive concrete paths against current main. This needs `CodeHost.BranchHead` and `CodeHost.Compare`.
6. **Shared files stop conflicting at the source.** The root `Taskfile.yml` includes one Taskfile per area. Change-map rows and the ADR index become one file per entry, and their index files (the ADR index is new: `docs/adr/` has none today) are generated by `task docs:gen` and checked for drift by `task check`. `AGENTS.md` stays one hand-written index; the overlap hold serializes the items that change it.
7. **Visibility.** `ItemWaiting` gains `needs: [{ref, title, paths}]`, so the board and the item page can say "waits for software#93 (moves terraform/)".
8. **Next step, not built here.** On a merge conflict confined to generated or append-only globs, the merge step regenerates the file or keeps both sides instead of sending the item to rework.

## Consequences

- A person can submit at any time: the planner can see what is open, a plan names what it waits for, overlapping items wait instead of conflicting, and a part that starts late learns what changed under it. Fewer items go back to rework for a conflict in a shared file.
- Claims get heavier: each claim of an item with paths reads the factory's open items' paths and may add edges before the claim. A claim at a station with `inFlight: true` and a rework after a merge conflict read the code host; a code-host error there blocks the item as a store error does for `## Assembly`, never runs it without the section.
- Every docs change that adds an ADR or a change-map row must run `task docs:gen`, and `task check` fails until it does.
- The software factory's definition in the bucket must set `inFlight: true` on its planning station and say in its prompts and rules how agents use `after`, `touches` and the two sections. That is a definition change, not one in this repository. Tests use a fixture definition with made-up station and agent names.
- The parts of assembly software#107 build the decisions: `overlap-hold` (software#119) decisions 3 and 4, `after` (software#120) decision 2, `in-flight` (software#121) decision 1, `codehost-compare` (software#122) `CodeHost.BranchHead` and `CodeHost.Compare`, `bind-late` (software#123) the rest of decision 5, `split-taskfile` (software#124) and `docs-entries` (software#125) decision 6, `waiting-api` (software#126) and `waiting-ui` (software#127) decision 7. Decision 8 has no part yet.
