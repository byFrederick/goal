# Frontend and monorepo

The UI is a static React single-page app. `goald` embeds it for the laptop; the same build deploys to Vercel or S3 + CloudFront. One OpenAPI contract connects it to the Go backend, and generated types keep both sides in step. Decision: [ADR 0004](../adr/0004-frontend-and-monorepo.md).

## Monorepo layout

One repository, two toolchains: a Go module at the root and a pnpm workspace for TypeScript. The root `Taskfile.yml` and the area Taskfiles it includes (`apps/web/`, `apps/auth/`, `apps/worker/`, `packages/api-client/`… [ADR 0013](../adr/0013-repository-layout.md)) orchestrate both (Turborepo is not installed; it earns its place once workspace builds need caching), and `task check` runs both.

```
goal/
  go.mod                       Go module (goald, goal CLI, engine, adapters)
  cmd/  internal/  db/          Go code, and db/migrations/, db/queries/, db/sqlc.yaml
  contracts/api/openapi.yaml   THE contract between goald and every TypeScript client (incl. the SSE StreamEvent)
  contracts/definitions/       factory.schema.json, environment.schema.json, memory.schema.json
  package.json                 private root: pnpm only, no app code
  pnpm-workspace.yaml          the apps (auth, docs, web, worker) and packages/*; the catalog pins better-auth once
  apps/
    auth/                      the identity service (Node 22, Hono + Better Auth; phase 3, ADR 0007)
    web/                       the UI (React 19 + Vite)
    worker/                    the agent container (Node 22 + Claude Agent SDK)
  packages/
    contracts/                 generated: TS types from contracts/api/openapi.yaml and contracts/definitions/*.json
    api-client/                typed fetch client (openapi-fetch), errors as Problem, SSE subscription
    ui/                        design system: tokens from docs/design/MASTER.md + shadcn/Radix components
    config/                    shared Biome config and tsconfig bases (Node, browser, Workers); no Vitest preset
```

Rules:

- `web` and `worker` depend on `packages/*`, never on each other.
- `packages/contracts` is generated and committed; CI fails if regenerating it produces a diff, so the Go and TypeScript sides cannot drift.
- `packages/ui` has no knowledge of Goal's API; it only renders. Domain components live in `web`.
- Exact versions in `package.json`, one lockfile (`pnpm-lock.yaml`), `pnpm` pinned via `packageManager` and `.mise.toml`.

## The contract

`contracts/api/openapi.yaml` (OpenAPI 3.1) is written first, by hand, and reviewed like code.

- Go: `oapi-codegen` generates a strict server interface that `internal/adapters/http` implements. Handlers call the engine through ports, as everywhere else.
- TypeScript: `openapi-typescript` generates types into `packages/contracts`; `openapi-fetch` gives a typed client with no hand-written fetch code.
- Realtime: `GET /v1/orgs/{org}/stream?factory=` streams one organization's Server-Sent Events: `event: item` (data: the `StreamEvent` schema in `contracts/api/openapi.yaml`, `id:` the event id) and `event: resync` (data `{}`: events may have been missed). There is no replay, so a client re-reads what it shows after a reconnect or a resync. The client turns each event into a TanStack Query cache invalidation, so screens update without polling.
- Factory, environment and memory files keep their JSON Schemas in `contracts/definitions/`; the same schemas drive Go validation, TS types and the YAML editor's autocompletion.

## Web app architecture

| Concern | Choice | Why |
| --- | --- | --- |
| Build | Vite, TypeScript strict | Fast, static output, no server to run |
| Routing | TanStack Router, file-based | Type-safe routes and search params; every filter, tab and selection lives in the URL so any view can be linked |
| Server state | TanStack Query | Caching, retries, optimistic updates; SSE events invalidate queries |
| Local state | React state; no global store | Server state and URL state cover nearly everything; add a store only when a measured need appears |
| Styling | Tailwind v4 with `@theme` tokens generated from MASTER.md | One source of truth for palette, type, radii; no hex values in components |
| Components | shadcn/ui on Radix, in `packages/ui` | Accessible primitives we own and can restyle |
| Board drag and drop | dnd-kit with keyboard sensors, plus a Move menu on every card | WCAG 2.2 dragging alternative |
| Factory editor | Monaco with monaco-yaml bound to `contracts/definitions/factory.schema.json`; the line preview is a plain HTML list, and stations reorder with dnd-kit plus ↑ ↓ buttons and Alt+Arrow | Autocompletion and inline errors while editing YAML; a linear line needs no graph canvas, and a list is accessible |
| Charts | Small SVG components in `packages/ui` (hatched bars, bridge, sparkline) | Exactly the design system's marks; no heavy chart library |
| Long lists | TanStack Virtual for traces and big boards | Keeps the main thread free |

The Tests tab (`tests-page.tsx`, the picture `jonah/tests.jpg`, ADR 0039 decision 12) lists the past items kept as tests by station in the line's order, from `keptTestsQuery`, each with who kept it, when, its last result and, when it has a run, a link to the item's Trace tab. With `definition:edit`, a row's menu removes a test (`removeKeptTest`); the item stays. A `learning` stream event (`learningInvalidations`, `shared/stream.tsx`) and a `definition` event refresh the Jonah keys; goald does not send `learning` yet, so a new proposal appears after a definition event, a resync or a focus refetch. `mock/jonah.ts` serves the overview and proposals; `e2e/jonah.spec.ts` covers the overview and the tabs (not run in the box). Vitest covers the pages in `jonah-page.test.tsx`, `jonah-header.test.tsx` and `tests-page.test.tsx`.

Route files stay thin (loader + component); screens live in `features/`. Loaders load through `ensureLoaded` (`api/queries.ts`; `api/loaders.test.ts` refuses a plain `ensureQueryData` or `fetchQuery` in `routes/`), which loads again when the fetch it shares was cancelled by the page being left; the error screen does the same once for a cancelled load instead of saying goald is not answering. Features never import each other; shared code goes to `shared/` or `ui/`. Boundaries are kept in review for now; `dependency-cruiser` arrives with `packages/`, the same way depguard guards the Go engine. `ui/` moves to `packages/ui` when a second app needs it.

### The API module and `@goal/api-client`

### Onboarding

The first-run flow (ADR 0032; the screens are `docs/design/screens/get-started/`). Step keys and labels are one table, `features/onboarding/steps.ts`: `organization` (the Organization step, at `/get-started`), then `code`, `factory`, `line`, `budget`, `intake`, `people` and `first-item` under `/o/$org/get-started/<key>`. Progress comes from data, not a table: a step is done when the data behind it exists (ADR 0032 decision 2).

`OnboardingLayout` (`features/onboarding/onboarding-layout.tsx`) is what every step shares: the Goal mark (`Wordmark`, never the organization's mark) and "Save and finish later" at the top (to the organization's home, or a button that signs out when there is no organization yet), the eight-step stepper with the current step at `aria-current="step"`, the form with Back and the primary action at the bottom, and the dark panel "Your factory, as you build it". The panel has four slots a step fills through `preview` (`organization`, `second`, `line`, `cards`); each falls back to its dashed placeholder. From `xl` (1280 px) the form and the panel sit side by side; below that the panel comes below the form.

Step 1 (`features/onboarding/org-step.tsx`) creates the organization with `useCreateOrg` (`shared/create-org.ts`, the same hook the organization dialog uses): the name, and an address that follows the name until it is edited, checked by `checkSlug` as it is typed. A taken address (`slug-taken`) shows its message on the address and takes focus; any other failure shows the error with Retry. Continue is `aria-busy` while the request runs. On success the chosen uses are saved in this browser under `goal.org-uses.<org id>` (`org-uses.ts`; nothing is sent to goald) and the person goes to `/o/<slug>/get-started/code`.

Step 3 (`features/onboarding/code-step.tsx`, `docs/design/screens/get-started/repository.jpg`, ADR 0041 decision 9) comes after the factory, so it knows the template's `code` (none, read or write). No code asks for nothing; Read only and Read and write ask which repositories (a whole owner, or only some URLs) and a write-only Token. Continue saves the token as a secret open to that one factory (`createSecret`, or `patchSecret` to open an existing secret to it; a 409 `secret-name-taken` offers the existing secret or a new name and never replaces its value), then calls `testFactoryRepository` (`api/repositories.ts`, `POST …/factories/{factory}/repositories/test`) for every URL with the chosen access. Each answer shows in a callout (`resultText`); when all pass, the next Continue writes the `runtime.repositories` entries into the draft's `factory.yaml`.

The choice is the URL's search, parsed by `code-search.ts`: `url` (an https URL with a host and no sign-in in it, at most 300 characters) and `secret` (a secret name by the contract's pattern). `connection`, `owner` and `repos` are no longer read: an old link opens an empty step 2, since every key is set in the parser's result, undefined when refused, because the router would otherwise show the raw value through. The token is never in the URL. Opened with `secret` set, the step can test again without asking for the token. Continue goes to `/o/<slug>/get-started/factory` with `url` and `secret`, which steps 3 and on carry (`repoOf` gives `<owner>/<repo>` for the panel's Code card, whose detail reads "Token <secret>"). Step 3 writes `runtime.repository` as `{url, token: '{{<secret>}}'}` into the new draft through `patchRepository`.

Step 3 (`features/onboarding/factory-step.tsx`, `docs/design/screens/get-started/template.jpg`) picks a template and creates the factory. The cards are the catalog's templates (`useTemplates` from `factory-editor/start/template-picker.tsx`, in the order the catalog returns them; the mock returns them sorted by name, so its first card is Code review, not the picture's Software delivery), each with its line as chips from `templateQuery`, then "Start empty" (the blank template, when the catalog has one). The first card is chosen. Factory name (`suggestedName`, checked by `nameProblem`), What it does and Colour (disabled, "Not available yet") sit below. "Use <title>" calls `createFactory` (`newFactoryRequest`). A name goald refuses as taken shows on the name field and takes focus. With a repository chosen in step 2, the new factory's draft is opened (`DraftSessionProvider`) and one save writes `basics.repository` (`url` from the first repository, `connection` from the URL, through `patchRepository`, the save RepositoryField makes) and `basics.purpose`. A failed save shows Retry on the step; the factory is not created again. Then the step goes to `/o/<slug>/get-started/line` with `connection`, `owner`, `repos` and `factory=<id>`. When the URL already names a factory (Back from step 4), the step offers Continue to step 4 instead of a second create.

Step 4 (`features/onboarding/line-step.tsx`, `docs/design/screens/get-started/line.jpg`) shapes the line of the factory in `factory=<id>`. It mounts `DraftSessionProvider` for that factory and `LineEditorProvider` (place `wizard`), and reads and saves through `useLineEditor` and the draft ops (`setStationName`, `setStationField`, `setAgentField`). Each station is a card: its name, its description, and for an agent station its agent select, Copies and WIP (`WipStepper` from `factory-editor/line/station-row.tsx`). Between the cards, and after the last card that is not Done, an "Add a station here" control (`line-step-controls.tsx`, a 44 px hit target) inserts an agent station named New station there (`addStation`, then `moveStation` for the first place, through `editor.insert`). Each card except Done has Move earlier, Move later (`stepTarget` and `stepBlocked` from `factory-editor/line/reorder.ts`; `editor.move` announces `movedMessage` in a polite live region) and Remove (`removeStation`). Lanes and the gate sentence are read-only. The Models card lists each agent with a model select (`builderMetaQuery` for the models) and the Quality first / Cost first preset is disabled ("Not available yet"). Continue is a button that goes to `/o/<slug>/get-started/budget` and publishes nothing (from Line on, every Back and Continue link carries `url`, `secret`, `template`, `factory` and `access` through `carriedSearch` in `code-search.ts`, so the Code step's choice survives Back); it is disabled, with one sentence beside it, while no station has kind `agent` ("Add a station that runs an agent, then continue.") or while the draft's validation (`useValidation`) reports an error problem ("Fix the problems in this line, then continue."), and while that validation has not answered; publishing is step 5 (ADR 0032 decision 4). Without `factory`, or for a factory that cannot be read, the step links back to step 3.

**Model presets (ADR 0022).** The wizard's Line step (`factory-editor/line/line-section.tsx`, place `wizard`) draws the Models box after its stations: `ModelsBox` (`line/models-box.tsx`, shared with onboarding's Line step, which keeps its preset disabled) with `PresetControl` (`line/model-preset-control.tsx`) on its heading row. The control is a `fieldset` labelled "Model preset" with two buttons, Quality first and Cost first, and `aria-pressed` on the choice. The two model ids and the edits live in one module, `factory-editor/start/model-presets.ts` (`presetModels`, `presetEdit`, `presetOf`, `pressedPreset`); ADR 0022 is the source, and changing an id is an amendment to it. A press saves the draft's `agents` section through the draft session (`setDefaultModel`, and for Cost first `setAgentField(…, 'model', undefined)` per agent). The pressed choice follows the draft: Quality first while no default model is set (goald's default applies and nothing is written until a press), and neither choice for a hand-set model. When the save completes, the choice goes into `?preset=quality|cost` (`validateWizardSearch` keeps those two values and drops the rest). When the server refuses the save, the control puts the previous agents back in the draft and shows the refusal in the box as an alert, since the next successful save would clear the session's error. Onboarding's Line step and the Models box's agent selects are unchanged by this.

Step 5 (`features/onboarding/budget-step.tsx`, `docs/design/screens/get-started/budget.jpg`) sets the budgets and the flow targets of the same factory, at `/o/<slug>/get-started/budget?factory=<id>`. Its fields are in `budget-fields.tsx`: three native range sliders, "A day" ($10–$500, step $5, `review.budget.daily_usd`), "A week" ($50–$2,000, step $50, `weekly_usd`) and "Most per item" ($2–$50, step $1, `per_item_usd`), each labelled and with its value and hint; the estimate; "When a budget runs out" (`on_exhausted`: `drain` as "Finish what's started", `stop` as "Stop everything", through `RadioCards`); and "Target, items a day" (`line.flow.targets.throughput_per_day`) and "Target lead time" in hours (`lead_time_hours`). Each control writes through `setBudget` and `setFlow`-shaped edits (`budget-draft.ts`) on the draft session, coalesced while it changes, and flushes when the person leaves it.

The hints and the estimate are pure functions of the values (`budget-hints.ts`), from one constant, `averageItemUsd` ($3.10, the picture's figure): "fits about N items" is the day ÷ the average, rounded; "covers N full days" is floor(week ÷ day); "N times the average" is the most per item ÷ the average, rounded; the estimate is the target × the average. Goal has no per-model cost and a new organization has no spend history, so these are estimates for a typical item, not the models' real cost. The Budget card in the panel (`budget-gauge.tsx`) draws the day against $500 as a half-circle gauge and reads "$<day> a day, $<week> a week".

Continue (`budget-step.tsx`) writes the picture's defaults ($150, $800, $12, Finish what's started, 10 items, 48 hours) for any field the draft leaves unset, flushes the draft, then calls `publishDraft` once with `expected_current_version_id: null` and `start: true` (ADR 0032 decision 4) and goes to `/o/<slug>/get-started/intake?factory=<id>`. A refusal (`definition-invalid` with its problems, `draft-base-moved`, 412 or an unreachable goald) shows its message on the step, lists the problems, and the step stays. The daily budget is shown and not enforced by goald yet (see the goald contract's `dailyUsd`).

Step 6 (`features/onboarding/intake-step.tsx`, `docs/design/screens/get-started/triggers.jpg`) chooses where work comes from, at `/o/<slug>/get-started/intake?factory=<id>`. It reads the factory's triggers from `getIntake` (`intakeQuery`) and the published model (`versionModelQuery`, `current`). Each starter trigger is a row: its source's tile (`sourceIcon` from `intake/triggers-table.tsx`), its name, its `when` sentence, "Creates a <type> at <station>" ("in the expedite lane" when expedited) and a Switch. A switch starts at the trigger's `enabled`; one that is already on is shown on and cannot be turned off here (Intake does that). A trigger with `problem.kind` `missing_connection` shows "Connect GitHub" or "Connect Webhook", linking to the factory's webhooks page (`/intake/webhooks`), and its switch stays off and disabled. The "Always on:" chips are New item, goal run and The API. The panel's Intake card lists the triggers switched on and "And New item, CLI, API". The step renders loading, error (with Retry), no triggers (a sentence and Continue) and ready.

"Turn on N triggers" (N is the switched-on triggers that were off, and "Continue" when N is 0) calls `setTriggersEnabled` (`intake/set-trigger-enabled.ts`): one `openDraft`, one `putDraftFile` of `factory.yaml` with `withTriggerEnabled` applied per trigger, and one `publishDraft` naming the factory's current version, so a version published in the meantime is a conflict. It then goes to `/o/<slug>/get-started/people?factory=<id>`. An open draft with someone's edits (`OpenDraftError`) or a refused publish shows its message on the step, and the step stays. The mock's code-review template carries the three starter triggers, off; the mock's intake reads the other factories' triggers from their `factory.yaml`.

Step 7 (`features/onboarding/people-step.tsx`, `docs/design/screens/get-started/invite.jpg`) invites people at `/o/<slug>/get-started/people?factory=<id>`. Each row is an address with its own role: Owner, Admin, Builder and Viewer, the picture's labels. Builder is a member with the editor role on the new factory and Viewer one with the viewer role (`people-roles.ts`, `roleGrant`); the API's role names are unchanged, and Owner is offered only to owners. "Send N invites" calls `usePeopleChanges(org).invite`, the Members page's mutation, with one request per row built by `inviteRequestsOf` (`features/members/people.ts`, which the invite dialog also uses). A refused address is named under the form and stays in the list; when none is refused, the step goes to step 8. "Skip for now" goes on without sending, and with no rows the button reads "Continue". The panel's People card (`people-card.tsx`) lists "You, <role>" and "<name>, <role>, invited" for each pending invitation, from `membersQuery` and `invitationsQuery`. The picture's "Or share a link" card is not built: no invite link endpoint exists.

Step 8 (`features/onboarding/first-item-step.tsx`, `docs/design/screens/get-started/first-item.jpg`) watches the first item at `/o/<slug>/get-started/first-item?factory=<id>` (ADR 0032 decision 3). A factory with no items gets its published version's `starter.item` submitted once, through `submitItem`, with its title, type and body. The submission is a query under `['onboarding', 'starter-item', org, factory]` that never refetches on mount, focus or reconnect and is never garbage collected, so a re-render or a remount reads the result instead of submitting again. A factory that already has items shows its newest one, and a factory without a starter item shows the empty state and submits nothing. The item card reads `itemQuery` and `eventsQuery`, under the keys the stream invalidates (`keys.item`, `keys.events`); no query sets a `refetchInterval`. Its timeline lists the item's events in words ("Created from the setup", "<station> accepted", and the other decisions) with the time since creation as m:ss. Run progress is not on it. The panel shows the running item under its cards (`RunningItemCard`) and a badge on its station in the factory card. "Open pull request #N" appears once an output names a pull request.

The panel on steps 3 and 4 (`factory-preview.tsx`) shows the organization, the first chosen repository, and the factory card: its initial, name and purpose, then the line as station nodes (`StationNode`) joined by a rule, each with one small square per WIP slot (at most 12 drawn). Step 3 draws the picked template's line before the factory exists; step 4 draws the draft's stations as they are edited.

`onboardingSearch` (`code-search.ts`) parses every onboarding step's URL: the Code step's choice plus `factory`, a UUID, dropped when malformed.

`/` (`routes/index.tsx`) sends a signed-in person with no organization to `/get-started`. With sign-in off, `/` still shows the page that says how to make one.

The mock starts with no organization on `POST /__mock/reset` with `{"orgs": "none"}`.

The end of onboarding is the Floor's two cards for a new factory, shown only until its first item merges (ADR 0032 decision 2, `docs/design/screens/get-started/ready.jpg`). **Finish setting up** (`setup-card.tsx`, the rules in `setup-progress.ts`) lists nine rows in the picture's order, each done or to do from data the factory already has, with no stored progress:

- Invite people: more than one member, or any invitation (`membersQuery`, `invitationsQuery`). To do links to `/o/<slug>/members`.
- Set up Slack notifications: the organization's notification setting names a Slack secret (`orgNotificationsQuery`, ADR 0037). To do links to the settings page's Notifications section.
- Add knowledge: any knowledge source. To do links to `/o/<slug>/knowledge/new`.
- Organization: always done.
- Code: the factory's code choice from the published definition's `basics.repositories` (`codeChoice`): "No code", "Code, read only, N repositories" (every entry reads) or "Code, read and write, N repositories" (any entry writes; the legacy `basics.repository` counts as one with write). No code is a valid choice (ADR 0041 decision 9), so the row is always done and has no action.
- The line, N stations: the published version's stations, not counting the Done station (`versionModelQuery`, `modelOf`). The picture's "4 stations" is Intake, Spec, Build and Review.
- Budgets and targets: `review.budget` sets a cap, or `line.flow.targets` sets a target. To do links to the Review section of the definition.
- N triggers: every trigger in `intakeQuery`, switched on or off. Done when there is one. To do links to the factory's intake.
- First item done: an item of the factory in state `done` (`itemsQuery`, one item). To do offers New item.

The count reads "N of 9 done" beside a ring (`role=img`). Closing the card (Hide setup) writes `goal.setup-hidden.<factory id>` to localStorage, so it stays closed in that browser only; the card renders nothing when all nine are done. Its loading, error (with Retry, which reads only the failed queries) and ready states are the Floor cards' own.

**How work gets in** (`ways-in-card.tsx`) lists the ways an item arrives. There is no "Label an issue" row: nothing implements it. "Mention @<factory> in Slack" offers Connect only while the organization has no slack connection. "New item, or press C" opens the new-item composer (not drawn without `item:create`); on a phone it is at least 44 px tall (`max-md:min-h-11`), and on touch devices (`pointer-coarse`) the ", or press C" hint is hidden, since a touch phone has no keyboard shortcut. "goal run" copies the CLI command. With no triggers, a line says so under the rows.

**Came from** (`shared/origin.tsx`, the item page's Details card) says where an item came from, from `getItem`'s `came_from`. A follow-up reads "A follow-up by <agent> on <source item>, filed when <item> landed", one line per follow-up, with both refs linked (another factory's included). A check's item reads "The check <name>, <key>" (no key: "The check <name>"), and a schedule's or webhook's reads the trigger's name. A person's reads "<name>, the CLI"; a part's reads "Part of <assembly ref> <title>". Intake's Coming up rows carry no `came_from`, so they keep "Follow-up from <ref>".

### Signing in (phase 3)

With `GOAL_AUTH=session` people sign in on `/sign-in` with an emailed code or Google (spec 3 §10). Only `api/auth.ts` calls the identity service (`/api/auth/*` on goald's origin, Better Auth's own contract, ADR 0007), with `better-auth/client` at the version `apps/auth/` pins (`better-auth: catalog:` in `pnpm-workspace.yaml`) and the email OTP, organization and device client plugins; it is imported only by the sign-in routes, the re-auth dialog and, through `import()`, the account's actions and the keep-alive, so the first bundle never carries it. goald reads the session from its httpOnly cookie; no script holds a token.

### Live updates

`shared/stream.tsx` (`OrgStream`, mounted by the `/o/$org` layout) opens one `EventSource` per open organization, on its stream. Each `item` event invalidates what it can change (`invalidationsFor` in `shared/invalidation.ts`): the organization's attention counts and inboxes, the factory's work keys named one by one (board, metrics, touches, items; only the board for tool calls; never the factory's bare prefix) and that item by ref and by id, batched over 300 ms so a burst of tool calls costs one refetch; the factory overviews at most every 5 s. The item's history refetch asks only for events after the last one cached. `resync`, and every reconnect after the first open, invalidate everything of the organization (`['org', org]`). A `factory` event (an andon pulled or cleared; the client's typed `onFactory`) invalidates the factory's work keys, the attention counts, the inboxes and the overviews (`factoryInvalidations`). A `knowledge` event (a source's sync started or ended) invalidates everything under `['org', org, 'knowledge']` except the searches (`knowledgeInvalidations`; the usage and the documents' uses included), and a definition's `current` event also refreshes `['org', org, 'knowledge']`, since what uses a source is read from the current versions. Other event names are handled through the `streamHandlers` registry; names nobody registered are ignored. Switching organization closes the old stream and opens the new one. `shared/stream-presence.ts` (`followPresence`) decides what `OrgStream` exposes. The shell says "Reconnecting" and the board's line status adds "reconnecting…" only after the stream has been down for 5 s (the grace period) while the page is visible; a short drop is silent, and a hidden page never counts as reconnecting. A return to the page (`visibilitychange`, or `pageshow` from the back/forward cache) reopens the stream at once, without waiting for EventSource's retry, closing the old one first; the reopened stream resyncs (every organization query refetches) so the screens are current without a banner. The board's line status still adds "connecting…" while the first open is pending.

`/o/$org/needs-you` (`routes/o.$org._org.needs-you.tsx`, `features/needs-you/`) lists what waits on a person across the organization's factories. ### Colour theme (dark mode)

Type is IBM Plex Sans (`@fontsource/ibm-plex-sans`, self-hosted) for all text and IBM Plex Mono (`@fontsource/ibm-plex-mono`) for code, paths and commands only (ADR 0036); `html` sets tabular numerals. The scale and weights are in MASTER.md, Typography.

The colors are tokens: `apps/web/src/styles.css` defines the light values in `@theme` and the dark ones (MASTER.md, "Dark theme") under `:root[data-theme="dark"]` and under `prefers-color-scheme: dark` for `:root:not([data-theme="light"])`. Components use token names only, so a theme switches without edits; `apps/web/src/ui/raw-colors.test.ts` fails on a hex, `rgb()`, `rgba()` or `hsl()` outside the allow-list, which is empty now: the Monaco theme reads its colours from the tokens. The text on a run or rework fill is `--color-white` (#FFFFFF in both themes), the primary button is `--color-action` with `--color-action-ink` text, and the selection is `run-tint`. The shadow is one token, `--shadow-pop`, for popovers and dialogs; everything else is a border. Radii are `--radius-dialog` (12), `--radius-card` (8), `--radius-cell` (8), `--radius-control` (6) and `--radius-chip` (4).

The type scale is `--text-meta` (12), `--text-secondary` (13), `--text-body` (14), `--text-heading` (14 at 600), `--text-detail-title` (18 at 600), `--text-page-title` (20 at 600) and `--text-kpi` (24 at 500), each a `text-<role>` utility with its line height and weight; the tracking token is `--tracking-display`. Numbers use tabular figures, not a width axis.

The motion tokens (`--duration-*`, `--ease-*`, and the scale, distance and blur tokens) are in the same ``, so Tailwind offers `duration-*` and `ease-*` utilities. `apps/web/src/ui/motion.test.ts` fails on a raw millisecond duration, `cubic-bezier(` or `transition: all` in a component. The catalogue of what moves is MOTION.md; the reduced-motion block in `styles.css` follows its rule 9. New code uses these and the 4px spacing scale. `apps/web/src/ui/arbitrary-values.test.ts` counts the existing arbitrary font-size, off-scale spacing and radius classes per source file. The counts are one small JSON per file under `apps/web/src/ui/arbitrary-values/`, at the source's path with `.json` added (`features/board/board-card.tsx.json`), so two changes conflict only when they touch the same source file. A file may not gain a use, and a screen that clears its uses lowers its counts in the same change: run `pnpm --filter web baseline:arbitrary` (`apps/web/scripts/baseline-arbitrary.ts`), which rewrites the JSONs for the current counts, deletes those that reach zero, and refuses to raise any count. To settle a baseline conflict, take main's version of the conflicting JSONs and re-run that command.

The choice (Auto, Light or Dark; Auto is stored as `system`) is one localStorage key, `goal-theme`, per browser (`apps/web/src/shared/theme.ts`; a missing or unknown value is Auto). `apps/web/public/theme.js` is a classic script in `index.html`'s `<head>`, before the module, so it sets `data-theme` and `style.colorScheme` on `<html>` before first paint; it reads the same key and must stay in step with `theme.ts`. CSP is `script-src 'self'`, so it cannot be inline, and it must not be a module or deferred. `useTheme()` (in `theme.ts`) gives the choice, the resolved theme and the setter; the account menu's Theme choice sets it, and the toaster in `routes/__root.tsx` takes the resolved theme. `theme.test.ts` checks the persistence, fallbacks, live system changes and that the dark blocks define every token; `theme-boot.test.ts` runs `theme.js` against fake objects and checks its place in `index.html`.

### The Assembly page

An item in state `assembly` (ADR 0012) opens the Assembly page instead of the item page: the route's component reads the item and switches on its state (`ItemRoute` in `routes/o.$org.f.$factory.items.$ref.tsx`); every other state keeps `ItemPage`. ### The intake trigger page

`…/f/$factory/intake/$trigger` (`features/intake/`, ADR 0016's `trigger` screen) shows one trigger of the
factory's current definition: its title with the on/off switch, this week's created, merged and spend,
the When, Only if, Create and Limits blocks, its recent events, and its YAML in the definition. Reads go
through `intakeTriggerQuery` (`GET …/intake/triggers/{trigger}`) and the definition's `factory.yaml`
(the open draft's when there is one, else the running version's).

Save changes writes `spec.board.triggers[name]` and nothing else. `trigger-save.ts` runs the draft files
API in order: open the draft, read `factory.yaml` for its sha256, put the file back with `If-Match`,
validate the draft, publish it. `trigger-yaml.ts` splices only the keys that changed into the text, so
every other line and comment stays byte for byte. A file with no `triggers` key, or an empty one, gets its first
trigger written in place (and `board` under `spec` when that is missing too). The draft-model API cannot carry `board.triggers`
yet (`internal/factorymodel/model.go`), which is why the page does not use it.

The When block picks the sender or one webhook and any GitHub event. The event table (which filters each event
supplies) is `github-events.ts`, mirrored by hand from `internal/catalog/senders/github.yaml` because no API serves
it. The form offers only the filters the chosen event supplies (action, conclusion, branch, repo as a list, label,
paths, authors, skipBots), then payload matches (`filter.match`) and `perHour` next to `perDay`. Legacy `on` keys
(`github.check_run.failed`) read in the schema's current words through `normalizeTrigger` and `readRawTrigger`, and
keep their lines until `on` or `filter` is edited. The model check is not on the page: the form never asks about it,
and a file's `only.modelAgrees` is kept as it is on save (the draft shows its `field-ignored` warning).

A trigger with `check` shows the check layout (`trigger-check-section.tsx`, `trigger-check-log.tsx`). `TriggerForm`
and `CheckSection` take `value` and `onChange` and never fetch, so the New trigger page can mount them. The Check
block has the agent, its tools as chips and the Brief (it shows the `check.brief` value; a `./triggers/<name>.md`
path shows as the path). Remembers shows the open and closed counts and how far the check has read, with Clear
(`clearTriggerState`; a 409 means a check is still running and shows that reason). Limits are `perCheck`, `perDay`,
`maxUsd` and `perHour`. `RecentChecks` reads `triggerChecksQuery` (`listTriggerChecks`): each row has the time, the
status (Filed, Noted, Nothing new, Failed), every filed, noted and skipped key with its reason and item link, and
the cost. The Today line counts the newest 100 checks, since the API has no day total.

Try with a past delivery (ADR 0028, `trigger-try.tsx`) opens a dialog that runs `POST …/intake/triggers/{trigger}/try`
(`tryIntakeTrigger`, through the `intakeTryMutation` key) against one of the trigger's stored deliveries. It tries
the saved trigger, not the open edits: Try is disabled with its reason while the form has unsaved edits and for a
trigger that is not saved yet. A delivery older than 30 days answers `event-not-stored`, and the dialog shows
`notStoredReason`. The result says whether the delivery matched, each step and the item it would create, and that
nothing was created.

Try a check (`TryCheck`, `tryTriggerCheck`) queues one check for the saved trigger and shows it as a row marked as a
try. A 409 (a check is still running) holds the button off with that reason; a 422 (`no-check`) shows its problem.

Rules the page follows:
- A draft with edits of its own blocks the save, with a link to the definition editor: the page never
  publishes someone else's draft. An invalid save leaves this page's own write in the draft, so that write does not
  block the fix; the page clears the mark once a save publishes or a 412 moves the draft.
- A 412 draft conflict keeps the typed edits and reloads the draft; the user saves again.
- The Create lane select offers Standard and Expedite, then the chosen station's route keys (`readBoard`'s `lanes`:
  a lane is a key of the station's `route`, factory.schema.json). A lane the file names stays selectable.
- Validation problems from `validateDraft` are placed by their line: a problem inside a trigger's key
  shows under that block, any other problem above the form. Save stays off while an error stands.
- A name the definition does not have opens a blank trigger when the URL has `?on=<event key>` (the New
  trigger picker's choice). The picker itself is not on this page.
- "+ Add another event" renders disabled with "Not available yet" (ADR 0016, decision 4).

Stream events: a `definition` event and an `item` event both invalidate `intakeKeys.root`, so the
trigger's results and its YAML re-read. The stream has no check event and no query polls, so a queued try shows
Queued until an item event, a definition event or a window-focus refetch. A check event in goald is the backend
follow-up that would fix this.

### Embedding in goald

`apps/web/webui.go` (Go package `web`) serves the build: files as they are (hashed `assets/` with a one-year immutable cache, the rest `no-cache`), `index.html` for every other path so client routes work on reload, and 404 for unknown `/v1`, `/api`, `/mcp` and asset paths. Scrolling up in any scroll region stops it: `useFollowScroll` listens for `scroll` in the capture phase on the document and stops when a `scrollTop` drops, so touch, keyboard and wheel all count. Pressing Watch live again scrolls to the newest step and resumes. The state is local to the page, not in the URL, and resets when the tab changes or the run ends. Without a running run the button is `NotAvailable` with `detail="No run is working on this item"`. On a phone it sits centred in its own card with a 44 px target (the phone picture does not draw it yet).

## PWA

Goal installs to a phone's home screen as its own app (standalone, no browser chrome). It starts from the cached app shell, and it updates itself after a Reload prompt (below). Push notifications come later, so approvals can arrive that way.

**Manifest.** `apps/web/public/manifest.webmanifest` is served from the root and linked from `index.html`. Name and short name "Goal", `id`, `start_url` and `scope` "/", `display` "standalone", and `background_color` and `theme_color` `#FFFFFF` (the light `--color-shell`; the dark `theme-color` meta in `index.html` is `#0E1120`). A manifest takes one colour, so dark mode keeps the media-specific `theme-color` metas in `index.html`. goald serves it as `application/manifest+json` (`apps/web/webui.go` names the type, since Go's mime table lacks `.webmanifest` and the image has no `mime.types`) and revalidates it like the favicon.

**Icons.** `icons/icon-192.png` and `icons/icon-512.png` (purpose `any`) are the favicon itself. `icons/icon-maskable-512.png` (purpose `maskable`) is the mark on a full-bleed `#1d2733` square, the bars at 60% of its height so they sit inside the central 80% safe zone. `apple-touch-icon.png` (180x180) is the same full-bleed design, written as an opaque RGB PNG: iOS rounds the corners itself and shows transparent pixels as black. All of them are rendered from `apps/web/public/favicon.svg`, and only the PNGs are committed. To make them again, from the repository root:

```sh
mkdir -p /tmp/pwa/run && cd /tmp/pwa/run && npm init -y >/dev/null && npm i @resvg/resvg-js@2
# save the script below as /tmp/pwa/run/render.mjs, then from the repository root:
cd <repository root> && node /tmp/pwa/run/render.mjs
```

```js
// render.mjs: renders the home-screen icons from apps/web/public/favicon.svg. Run from the repository root.
import { readFileSync, writeFileSync, mkdirSync } from 'node:fs';
import { deflateSync } from 'node:zlib';
import { Resvg } from '@resvg/resvg-js';

const out = 'apps/web/public';
const favicon = readFileSync(`${out}/favicon.svg`, 'utf8');
// The three bars of the mark, without the rounded square.
const bars = favicon.match(/<rect x="8"[\s\S]*<\/svg>/)[0].replace('</svg>', '');
// A full-bleed #1d2733 square with the bars scaled to 60% of its height (the bars are 14x17 units),
// inside the central 80% that a maskable icon keeps clear.
const full = (size) => {
  const scale = (size * 0.6) / 17;
  return `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 ${size} ${size}"><rect width="${size}" height="${size}" fill="#1d2733"/><g transform="translate(${size / 2} ${size / 2}) scale(${scale}) translate(-15 -14.5)">${bars}</g></svg>`;
};
const render = (svg, size) => new Resvg(svg, { fitTo: { mode: 'width', value: size } }).render();

mkdirSync(`${out}/icons`, { recursive: true });
writeFileSync(`${out}/icons/icon-192.png`, render(favicon, 192).asPng());
writeFileSync(`${out}/icons/icon-512.png`, render(favicon, 512).asPng());
writeFileSync(`${out}/icons/icon-maskable-512.png`, render(full(512), 512).asPng());

// apple-touch-icon.png is opaque: iOS shows transparent pixels as black, so it is written as RGB.
const crcTable = Array.from({ length: 256 }, (_, n) => {
  let c = n;
  for (let k = 0; k < 8; k++) c = c & 1 ? 0xedb88320 ^ (c >>> 1) : c >>> 1;
  return c >>> 0;
});
const crc = (buf) => {
  let c = 0xffffffff;
  for (const b of buf) c = crcTable[(c ^ b) & 0xff] ^ (c >>> 8);
  return (c ^ 0xffffffff) >>> 0;
};
const chunk = (type, data) => {
  const len = Buffer.alloc(4);
  len.writeUInt32BE(data.length);
  const body = Buffer.concat([Buffer.from(type), data]);
  const sum = Buffer.alloc(4);
  sum.writeUInt32BE(crc(body));
  return Buffer.concat([len, body, sum]);
};
const { width, height, pixels } = render(full(180), 180);
const raw = Buffer.alloc((width * 3 + 1) * height);
for (let y = 0; y < height; y++) {
  for (let x = 0; x < width; x++) {
    const s = (y * width + x) * 4;
    const d = y * (width * 3 + 1) + 1 + x * 3;
    raw[d] = pixels[s];
    raw[d + 1] = pixels[s + 1];
    raw[d + 2] = pixels[s + 2];
  }
}
const ihdr = Buffer.alloc(13);
ihdr.writeUInt32BE(width, 0);
ihdr.writeUInt32BE(height, 4);
ihdr[8] = 8; // bit depth
ihdr[9] = 2; // colour type RGB
const signature = Buffer.from([137, 80, 78, 71, 13, 10, 26, 10]);
writeFileSync(
  `${out}/apple-touch-icon.png`,
  Buffer.concat([signature, chunk('IHDR', ihdr), chunk('IDAT', deflateSync(raw)), chunk('IEND', Buffer.alloc(0))]),
);
```

**iOS.** `index.html` carries `apple-mobile-web-app-capable` and `mobile-web-app-capable` (yes), `apple-mobile-web-app-status-bar-style` (black-translucent) and `apple-mobile-web-app-title` (Goal), and the `apple-touch-icon` link. `viewport-fit=cover` lets the page draw under the status bar and the home indicator.

**Service worker.** `apps/web/src/sw/sw.ts` is written by hand (no Workbox, no plugin: no new dependency). `vite build` emits it as `/sw.js` at the root of `dist/`, a self-contained classic script that shares no chunk with the app and imports nothing (a nested build in `apps/web/vite.config.ts`). goald serves it at scope `/` with `Cache-Control: no-cache`, like the other unhashed root files, and the CSP's `worker-src 'self'` allows it. `apps/web/src/pwa/register.ts` registers it from `main.tsx` in production builds only: never under `vite dev`, and never in a `GOAL_API=mock` dev server.

The worker's routing is one pure function, `routeRequest` in `apps/web/src/sw/routes.ts`, tested in `routes.test.ts`. A bypass returns before `respondWith`, so the browser goes to the network as if there were no worker:

| Request | Route | What the worker does |
| --- | --- | --- |
| any non-GET; any cross-origin request | `bypass` | nothing |
| `/v1/*`, `/api/*` (the identity service's `/api/auth/*`, OAuth callbacks included), `/mcp/*`, any navigation to them | `bypass` | nothing: never cached, never answered with the shell |
| `/sw.js`, `/manifest.webmanifest` | `bypass` | nothing |
| a same-origin navigation to any other path (`/`, `/o/acme/f/sre/board`, `/device`, `/sign-in`, `/invite/…`) | `network-first-shell` | fetches it; only when the fetch rejects (offline) answers the cached shell (`/`) |
| `/assets/*` (content-hashed, immutable) | `cache-first` | answers from the cache, fetches and caches on a miss |
| `/favicon.svg`, `/theme.js`, `/icons/*`, `/apple-touch-icon.png` | `stale-while-revalidate` | answers from the cache and refreshes it behind the answer |
| any other same-origin GET | `bypass` | nothing |

Only responses that are `ok` and of type `basic` (same origin, not opaque or redirected) are cached.

**Why the API and auth are never cached.** `/v1` answers are the signed-in user's private data, and `/api/auth/*` is the sign-in, the session and the OAuth callbacks (`/api/auth/callback/google` is a top-level navigation that sets a cookie). A cached answer would show one person's data to the next, and a shell answered for `/api/auth/*` would break the sign-in redirect and the device-code page. So the worker never reads or writes those paths, and offline use of API data does not exist: the app opens offline, and its data needs the network.

**Cache versioning.** The cache is `goal-shell-<build id>`. The build id is a 16-hex-digit hash of every file the build writes (the assets carry their own content hashes, so a change to any file changes it), injected into the worker as `__BUILD_ID__`. `install` precaches `/` (the shell, fetched with `cache: 'reload'`) and does not call `skipWaiting`, so a new build waits. `activate` deletes every other `goal-shell-*` cache, then calls `clients.claim()`. The old build's cache stays until the new worker activates, so an open page keeps running on the build it loaded.

**Build id in the page and the worker.** The build id is computed once, by the `goal-service-worker` plugin in `vite.config.ts`, from every file the build writes with `index.html` as vite emitted it. The plugin then writes it into `dist/index.html` as `<meta name="goal-build" content="<id>">` and into `sw.js` as `__BUILD_ID__`. The id cannot be compiled into the page's bundle, because it is a hash of that bundle. Every page load fetches `index.html` from the network (the worker serves navigations network first, and goald serves the file no-cache), so the meta always names the build the page runs. The worker answers `{type: 'GET_BUILD'}` with `{type: 'BUILD', build}` on the message's port.

**Update prompt.** On load and on every `visibilitychange` to visible, the page calls `registration.update()`, which is how a phone that keeps the app open finds a new build. When a new worker is waiting (or has just finished installing under a controlling worker), the page asks it for its build with `GET_BUILD` (`src/pwa/register.ts`):

- **Same build as the page.** This happens after every deploy: the old worker served the new `index.html`, so the page already runs the new build while the new worker waits. The page posts `{type: 'SKIP_WAITING'}` with no toast, closes any open update toast, and the `controllerchange` that follows does not reload.
- **No answer within 2 seconds** (a worker from before this check, or a page without the meta): a freshly loaded page runs the newest build, so an older waiting worker is not news. The page runs `registration.update()`, waits up to 4 seconds for an install to finish, and decides again for the worker that is waiting then. A same-build worker that arrives takes over quietly. The toast is offered only if the silent worker is still the one waiting.
- **Another build** (or a still-silent worker, as above): a sonner toast says "A new version of Goal is ready" with a **Reload** action, through the app's `Toaster` in `__root.tsx`. Reload posts `{type: 'SKIP_WAITING'}` to the waiting worker; the worker activates, claims the page, and the page reloads once on `controllerchange`. If the worker is no longer waiting when Reload is pressed, Reload calls `window.location.reload()` instead. When the worker the toast was offered for turns `redundant`, the toast closes and the page decides again for the registration's waiting worker, if any.

The first worker a page gets (a first visit) is not an update and reloads nothing.

**Checking it by hand.** Build A, serve it (goald or `pnpm --dir apps/web preview`), open the app in Chrome, and install or add it to the home screen. Leave a build whose worker does not answer waiting and ignore its toast. Build B, deploy it, then open the app again (navigate or reload): the page runs build B and shows no toast, and B's worker activates by itself (its `goal-shell-` cache name changes in DevTools › Application › Cache storage), and no toast remains once the update settles. Deploy build C and bring the tab back to the front without navigating: it shows the toast; tap Reload; the page reloads and runs build C. `apps/web/e2e/pwa-update.spec.ts` runs these steps against copies of the production build under other build ids.

**Safe areas.** With `black-translucent` the page is drawn under the status bar, so the phone's top bar pads its top by `env(safe-area-inset-top)`, the drawer pads its top by that inset on top of its 8 px (`pt-[calc(8px_+_env(safe-area-inset-top))]`), and the shell pads its left and right by `env(safe-area-inset-left)` and `env(safe-area-inset-right)` for landscape. The bottom tab bar, the wizard footer and the drawer pad their bottoms by `env(safe-area-inset-bottom)`. In a browser tab every inset is 0, so nothing moves there. Use `calc()` with spaces around `+` (`calc(8px_+_env(...))`): without them the declaration is invalid CSS and is dropped.

The manifest and icons are checked by `apps/web/src/pwa/manifest.test.ts`, which reads the PNG sizes from their headers, and `apps/web/webui_test.go` checks the manifest's content type.

## Quality gates

- Biome for lint and format; `tsc --noEmit` for types; dependency-cruiser for boundaries (with `packages/`).
- The Biome config and the tsconfig bases come from `packages/config` (`@goal/config`). Each project's `biome.json` and `tsconfig.json` extends one of them and keeps only its own settings: `web`, `auth`, `worker`, `cloudflare` and `api-client` each extend the variant that matches their runtime. `api-client` has no Biome config, so it extends only the tsconfig base.
- Vitest for logic with real behavior (the trace built from events, which decisions an item allows); Testing Library for components when they carry such logic. No snapshot tests of markup.
- Playwright for the critical flows at 375, 768 and 1440 px, with axe accessibility checks.
- Budgets: initial JS under 250 KB gzipped; routes are code-split. Views loaded on first use go through `lazyRetrying` (`apps/web/src/shared/lazy.ts`), not bare `React.lazy`, which keeps a chunk that failed to arrive failed until the page reloads.

## Phone shell

Below 768 px (`phone-chrome.tsx`, MASTER.md "Phones", `screens/mobile/drawer.jpg`), `ShellFrame` draws three things and holds the state they share:

- **The top bar** (`PhoneTopBar`), sticky, 56 px plus `env(safe-area-inset-top)`. On its left a 44 px button with the Goal mark, named "Open menu" (`aria-haspopup="dialog"`, `aria-expanded`). It opens the drawer. Next to it the page's title: the page's last crumb from `TopBarSlot`, else the page's name from `usePageLabel` (the same registry as the desktop bar). On its right the page's actions. There are no factory squares and no crumb.
- **The tab bar** (`PhoneTabBar`), fixed at the bottom on organization pages (not on the New factory wizard, `ShellFrame tabs={false}`), named "Tabs": Needs you, Floor, Board, Items, More. Each target is `min-h-16` (64 px), and the bar pads its bottom by the safe-area inset. `main` leaves room for it (`pb-28`). Needs you is a disabled button with the tooltip "Not available yet" and `aria-disabled` (ADR 0016, decision 4); it is a button, not a span, so a keyboard user reaches the tooltip. Floor, Board and Items go to the open factory, or outside a factory to the last factory visited in this organization (`rememberFactory` and `lastFactory` in `shared/org.ts`, kept per organization id in localStorage, set by the factory route), else the first factory, else the Factories home. The current tab carries `aria-current="page"` from TanStack's Link. More opens the drawer.
- **The drawer** (`PhoneDrawer`), a Radix Dialog from the left, 320 px, labelled by the organization's name. It renders `SidebarContent` (`sidebar.tsx`): the same entries as the 256 px sidebar, with Close in place of Collapse. Focus is trapped while it is open. Escape, Close and the Goal mark return focus to the Goal mark, but a navigation (a link, or a switch of organization) closes it and leaves focus where the new page puts it. Any change of page closes it (`PageWatch`).

`usePhone()` decides which chrome renders, from `matchMedia('(max-width: 767px)')`; without `matchMedia` (jsdom) it is the desktop chrome. Only one top bar and one set of actions is in the DOM at a time. The sidebar and its content stay in the DOM from 768 px, so the drawer's list is a second copy only while it is open.

The phone's tests: `app/phone-chrome.test.tsx` (the title and actions, the drawer's focus and links, the tab targets and the fallbacks), `shared/org.test.ts` (`lastFactory`), and `e2e/phone-shell.spec.ts` plus the phone cases in `flows.spec.ts`, `knowledge.spec.ts` and `definition.spec.ts`.
