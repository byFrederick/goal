# Architecture

Goal is one Go daemon (`goald`), one PostgreSQL database, one object storage bucket for factory definitions and knowledge uploads (no object versions needed), short-lived agent containers and a static React UI. The same code runs on a laptop, on local Docker Compose and on Cloudflare (phase 4, [ADR 0008](../adr/0008-portable-runs-connections-and-knowledge.md); deployed at `goal.byfrederick.work` since 2026-10-25), which replaced the AWS and Vercel targets that were designed and never built. Decisions: [ADR 0001](../adr/0001-technology-stack.md) (stack), [ADR 0003](../adr/0003-hexagonal-architecture-and-deployment.md) (architecture and deployment), [ADR 0005](../adr/0005-factory-definitions-in-object-storage.md) (factory definitions in object storage). The definition format beyond its schema, factory rules among it, is in [factory-definition.md](factory-definition.md).

## Hexagonal core

```
              ┌──────────────────────── goald ────────────────────────┐
  HTTP/SSE ──▶│ adapters/http ──▶  engine  ◀── domain                  │
  (UI, CLI)   │                      │                                 │
              │                    ports: Store  Sandboxes  Secrets    │
              │                           ObjectStore  Clock  CodeHost  │
              │                      │                                 │
              │ adapters: postgres  docker  env  github                 │
              │           s3 (RustFS)  gateway                          │
              └────────────────────────────────────────────────────────┘
  phase 4: Sandboxes (docker as built in 4-7; cloudflare in 4-21) replaced Runner, Workspaces, Checker,
  Reaper and (4-11) Sidecars; new Connections and Minter (awssts, 4-12; both gone with ADR 0037), MasterKey, Knowledge,
  Converter, SourceReader (uploads, gitdocs, confluence); s3 also on R2
```

- **Overlapping files** (assemblies P4, the parts of an assembly and any items of a factory). `domain.PathsOverlap(a, b)` returns the pairs of file globs, one from each list, that could match a common path. Globs follow doublestar: `*`, `?`, `[...]` (`[!...]`/`[^...]` negated) and `\` escapes match within one path segment, `**` as a whole segment matches any number of segments (none included: `web/**` matches `web`), and `{a,b}` expands to alternatives, which may span segments; a leading `./` or `/` is ignored and blank globs match nothing. It is conservative: it may hold too much, never too little. It reports a pair that cannot actually share a path only when a negated class meets another class, or when a glob's braces expand to more than 256 alternatives (that glob then overlaps everything). Each pair is decided by a product of the two globs, segment by segment and then character by character, filled once per pair of suffixes (O(n·m), no backtracking). The factory's policy is `board.flow.assemblies.overlap` (`domain.FlowPolicy.Assemblies.Overlap`, next to the line's other assembly settings): `serialize`, the default, holds an item whose files overlap those of an item in flight; `allow` builds them in parallel. Every item stores its globs (`domain.Item.Paths`, `work_items.paths`, migration 00060, which backfilled existing parts from `part_paths`): `Assemble` sets a part's from its plan and `Transition.Paths` replaces them. A station's output sets them too: `board.flow.dependencies.paths` (`domain.FlowPolicy.Dependencies.Paths`, unset by default) names the output field whose list of globs replaces the item's paths when the station finishes (`domain.PathsFrom`, read in `finish`); an output without that field, or with an empty list, and a line that maps no field leave them as they were. The platform names no field (AGENTS.md rule 1). The overlap hold is built ([ADR 0015](../adr/0015-overlapping-in-flight-work.md) decision 4): on its first turn at an agent station in a tick, before `ClaimNext`, the engine (`holdOverlaps`) reads up to 50 of the station's waiting items (`Store.Waiting`) and, for those with paths, the factory's open items (queued, ready, in progress, waiting for a person or blocked; never an assembly, whose parts carry its paths) numbered below them through `Store.ListItems` in pages of 200. For each pair where the open item is numbered lower, is not a part of the same assembly, is not already needed (`Store.OpenNeeds`) and `domain.PathsOverlap` finds a pair, it adds an `overlap` edge by `system:engine`; an edge the store refuses as a cycle (`domain.ErrCycle`) or as existing (`ErrConflict`) is skipped with a debug log. The claim gate then skips the held item in the same `ClaimNext`, and `domain.WaitingFor` reports it as kind `files`, with each need's ref, title and paths (an assembly's: its parts' `part_paths`) from the one `Store.OpenNeeds` query. With `overlap: allow` nothing is held. Two instances may claim overlapping items in the same instant before either writes its edge; the next claim is still gated. Edges are not removed when an item's paths later change.

an unknown owner wraps `ErrNotFound`): `github` reads `GET /user`, `GET /user/orgs?per_page=100` (organizations show only for a token that may read them, `read:org` on a classic token), then the first page of `ports.MaxRepositories` (100) of the owner's repositories by most recently updated, `GET /user/repos?affiliation=owner` for the account or `GET /orgs/{owner}/repos?type=all` for another owner, with `Truncated` set when GitHub's `Link` header names a `next` page (never followed), and then `GET /repos/{full_name}/languages` for each, 8 at a time (sorted by bytes): up to 103 requests, any failure failing the call, a listing bounded at 8 MiB. Its `Compare` reads `GET /projects/:id/repository/compare?from=<base>&to=<head>&straight=false`, which lists every commit in one answer, oldest first (an order GitLab's API docs do not state), keeps the first 100 with `Truncated` set when there were more, and then reads each kept commit's `GET /projects/:id/repository/commits/:sha/diff?per_page=100` for its files (each `new_path`, and the `old_path` of a rename or delete; not paged past 100), up to 101 requests, any failure failing the call; those answers carry diffs, so they are bounded at 32 MiB instead of 1 MiB, and a longer answer is an error. `gitlab`'s `Repositories` returns an error wrapping `errors.ErrUnsupported` and sends nothing. `RepositoryAccess(repo, token)` (a `ports.RepositoryAccess`: `Read`, `Push` and `CI`, each `{OK, Reason}`) serves the repository test that runs before any factory or connection exists: `github` reads `GET /repos/{owner}/{repo}` (200 reads; `permissions.push` pushes, which for a classic token is the account's role, not the token's scopes), `gitlab` reads `GET /projects/:id` (200 reads; the higher of `project_access` and `group_access` at Developer, 30, or more pushes). `CI` is whether the token can read CI ([ADR 0044](../adr/0044-goald-waits-for-ci.md) decision 10) and never changes `Read` or `Push`: `github` reads `GET …/commits/{default_branch}/check-runs?per_page=1` and `GET …/commits/{default_branch}/status` (both 200 pass; a 403 names the fine-grained permissions Checks and Commit statuses; another answer fails with GitHub's status and message), `gitlab` posts `project(fullPath) { jobsEnabled }` to `/api/graphql` beside `/api/v4` with the token as a Bearer token (true passes; otherwise `builds_access_level` from `GET /projects/:id` decides: `disabled` passes as CI that is off, anything else fails naming `read_api` and a role that can see pipelines). When `Read` fails, `Push` and `CI` fail as not checked. A 401, 403 or 404 is a failed read with the host's message; a repository the adapter refuses wraps `domain.ErrInvalid`; a 5xx or no answer is an error.

### MCP gateway

`internal/gateway` is an inbound HTTP component of `goald`, not an adapter: it reads factory definitions (`config.Factory`), which adapters may not. `gateway.New(Deps, Config)` returns an `http.Handler` that `goald` mounts at its MCP path. Its package comment is the reference; in short:

- **Auth.** Every request carries `Authorization: Bearer <task token>`; a missing, forged or expired token, or one without `aud: goal-gateway`, is 401, an agent the run's definition version does not declare is 403 (except a jonah token's, below), both without detail.
- **Listener.** Without `GOAL_GATEWAY_LISTEN` the gateway is `/mcp`, `/run` (the run bundle) and `/run/tool-approval` on goald's one listener. With it, goald opens a second listener there that serves only those three paths (everything else 404), the main listener answers them with 404, and `GOAL_GATEWAY_URL` defaults to `http://<GOAL_GATEWAY_LISTEN>/mcp` (a wildcard host becomes `127.0.0.1`), the only goald address agent tasks are given; goald refuses a `GOAL_GATEWAY_URL` that names the main listener then. The gateway listener may be off loopback (every request needs a task token) and is required off loopback once `GOAL_LISTEN` may be (phase 3, PR 3-9). Agents never reach that address themselves: they run on a network with no route to the host and reach the gateway through the egress proxy (below, [ADR 0009](../adr/0009-agent-network-isolation.md)), which serves exactly the gateway's path and forwards it to `GOAL_GATEWAY_URL`, a loopback one rewritten to `host.docker.internal`, which only the proxy resolves. Which setting a laptop needs depends on how the proxy reaches the host:
  - *Docker Desktop and OrbStack* forward `host.docker.internal` to the host's loopback, so the default single listener works. `goal up` sets no `GOAL_GATEWAY_LISTEN` (a fixed second port could only collide).
  - *Docker Engine on Linux* resolves `host.docker.internal` (the `host-gateway` extra host) to the bridge address, which a loopback listener does not serve, so runs reach no gateway on the defaults. Set `GOAL_GATEWAY_LISTEN` to the bridge address (`172.17.0.1:8090`, `ip -4 addr show docker0`) and keep `GOAL_LISTEN` on loopback.
- **Factory rules** ([ADR 0014](../adr/0014-factory-rules.md)). The run bundle's `spec.rules` are the rules of the run's pinned definition version whose `appliesTo` matches the run (`definitions.Cache.Rules`, selected with `domain.EffectiveRules` by the token's agent and station and the item's lane and work type; a reviewer's the same way, by the lane and work type of the item it reviews), in declaration order: each with its name, the sha256 of its `rules/` file in the version's manifest, its `paths` and its `content`, the markdown file the worker writes to the agent's rules (a frontmatter with `description` and `paths`, no `appliesTo`, then the body). The first `GET /run` of a run that any rule applies to appends one `rules_applied` item event (run id, station, the agent as actor, data `rules: [{name, sha256}]`); a bundle fetched again finds it among the item's events and appends none.
- **Stateless.** The SDK's stateless streamable-HTTP mode: each request is verified and served on its own, so any `goald` serves any run (4-11 deleted the registry of stdio sidecars, its one piece of state).
- **Notes to a run in progress.** `GET /run?notes_after=<event id>` (0 or a positive integer, else 400; `internal/gateway/notes.go`) answers `{"notes":[{id, at, by, text}]}`: the token's item's `note` events whose id is greater than both the run's own `run_started` and `notes_after`, oldest first, at most 50, read through `Events.ItemEvents` (no note from before the run started). It authorizes like the bundle and records nothing. The worker polls it between the agent's turns, gives each note to the agent as a user message and reports it as a `note_delivered` line, which the engine records as an item event of the run (`domain.EventNoteDelivered`, data `note_id`). Delivery is a poll and not stdin because Cloudflare Containers have no attached stdin; `/run` with its query string already passes the egress proxy and Cloudflare's gateway.
- **No connection proxied.** The organization's connections are the box's (4-11): the gateway lists none of their tools, holds none of their secrets and only describes them in the run bundle. 4-14 deleted the serving of older versions' inline connections (`upstream.go`, `policy.go`, `domain.SecretPolicy`); the endpoint serves Goal's own tools only, and a call of any other tool is refused like an unknown one and audited as denied.
- **Knowledge** (ADR 0038 decisions 7 to 9). The engine pins, at a claim's start (`pinKnowledge`, beside the policy), the newest snapshot of each of the version's `knowledge.sources` whose `appliesTo` matches the run (`domain.ApplyingKnowledge`), through `engine.KnowledgeSnapshots` (`ports.Knowledge.Snapshots`); none for an agent whose `builtins.read` is off (`AgentSpec.ReadsFiles`), and no pin for a source with no snapshot. The pins are on the claim, so a lost box prepared again gets the same ones, and they ride in the task token (`TaskClaims.Knowledge`, `kn`); a draft request's box pins for the request's agent. The bundle's `spec.knowledge` (`internal/gateway/knowledge.go`) holds the run's Knowledge section, from one template (`domain.KnowledgeIndex`: ground rules, one line per pinned source with its `readWhen` or its snapshot's line, its file count and up to six slug top folders read from the zip's central directory in two ranged reads, the sources not synced yet, the factory memory), built by `domain.IndexKnowledge`, and per pin the URL of its zip, none for a draft request: when goald runs boxes on Cloudflare (`GOAL_SANDBOX=cloudflare`, which sets `gateway.Config.KnowledgeURLTTL` to 15 minutes in `cmd/goald`), a signed bucket URL from `ports.ObjectStore.PresignGet`, valid longer than prepare's download and shorter than the claim; otherwise, for local Docker boxes that cannot reach the bucket, `/run/knowledge/<source>`. A URL the store cannot sign falls back to `/run/knowledge/<source>`, logged as `knowledge snapshot url unsigned` with the source and the error; no signed URL is logged. The editor's "What agents see" (`getDraftKnowledgePreview`, `internal/api/knowledge_preview.go`) builds the same section through `domain.IndexKnowledge` from the draft's line (`authoring.Service.DraftLine`) and each source's current snapshot, its top folders read from the source's files, so a run pinned earlier may see another snapshot. `ServeKnowledge` streams the pinned zip from the bucket to local boxes and answers 404 for a source the token did not pin and for a draft request's token. The first bundle with pins appends `knowledge_pinned` once per run, as rules do. The tools `knowledge__search`, `knowledge__read` and `knowledge__verdict` are gone; the gateway serves `question__ask` only. Reads are counted from the trace (decision 10): the worker puts the path of each Read, Grep and Glob call in its `tool_use` event (a Glob with only an absolute pattern reports the pattern's leading folders before its first glob segment), the engine's `agent` loop tallies the calls under `/knowledge/<source>/` of the run's pinned sources (`domain.TouchOfKnowledge`, `domain.KnowledgeTally`: a Read of a file is a read of it, a Grep or Glob a search of the folder or file it names, of the whole source at the path `.`), and once the run ends `countReads` adds them to the day's rollup of the run's factory with one `ports.Knowledge.AddReads`. Before that it appends one `knowledge_read` item event by the run's agent, listing each touched source's files read and paths searched (`KnowledgeTally.Touched`: each once, sorted, at most `domain.MaxKnowledgeTouchedPaths` in all, the rest counted in `more`), scrubbed like the agent's events; a run without an item records none. Both are best effort: on a context of their own bounded to 10 seconds, and a failure is logged (`knowledge reads not counted`, `knowledge read event not recorded`) and changes nothing about the run.
- **Questions** ([ADR 0018](../adr/0018-agents-ask-questions.md)). Every run, with or without knowledge sources, is also served `question__ask {question: 1–500 characters, choices?: 0–4 strings of 1–60 characters}` (`internal/gateway/question.go`), so an agent can ask the person responsible for its item a question with quick-answer choices. The gateway decodes the arguments strictly (an unknown field is refused), trims the question and the choices and checks the limits; input outside them is a tool error with the reason and never reaches the engine. It then passes the token's item, run and agent with the question and the choices to `gateway.Questions` (`Ask(ctx, gateway.Question)`), which goald wires to `engine.Engine.Ask` through `engineQuestions` in `cmd/goald/main.go`: the gateway is built before the engine, so the adapter reads `eng` when a call comes in, and it maps `engine.ErrQuestionOpen`, `ErrNotInProgress` and `ErrBadQuestion` to `*gateway.QuestionRefusedError`. A good call answers a text result that says the question was sent and to stop now: the engine has already ended the run, so the result may not reach the agent. A refusal (such as a second open question) is a tool error with its reason; any other error is a tool error that says to try again, logged as `gateway question failed`, with nothing of the failure shown to the agent. Each call appends `gateway_tool_call` (connection `question`, tool `ask`, outcome `ok`, `tool_error` or `failed`), without the question or its choices.
- **Ask-first tool calls** ([ADR 0031](../adr/0031-tool-calls-ask-first-and-standing-rules.md)). The run bundle gives each MCP server of the agent's environment file its `tool_modes` (`domain.ServerToolModes` of the file's modes, the organization policy's cap and the organization's active standing rules, read through `gateway.Deps.StandingRules` once per bundle and only when a server has an `ask`), where a rule for the token's agent turns an `ask` into `allow` and nothing changes an `off`; it has no `spec.connections`. `spec.granted_calls` lists the `{connection, tool, input}` calls a person approved for the token's run (`domain.GrantedCalls` over the item's events), `[]` when there are none. A run reports a call whose mode is `ask` with `POST /run/tool-approval {connection, tool, input}` (`internal/gateway/toolapproval.go`, `Gateway.ServeToolApproval`), authorized by its task token like `/run`. The body is bounded by `Config.MaxRequestBytes` and decoded strictly; the connection must be one the token grants and the tool a tool's name (`domain.CheckToolName`), and the input is measured as canonical JSON (`domain.CanonicalJSON`), so whitespace does not count. The gateway passes the token's item, run and agent role with the call to `gateway.ToolApprovals` (`RequestToolApproval(ctx, gateway.ToolCall)`), which goald wires to `engine.Engine.RequestToolApproval` through `engineToolApprovals` in `cmd/goald/main.go`; the engine records `tool_approval_requested` and ends the run. The answers are plain text: 202 when the call waits for a person; 401 for a bad token; 403 for a token whose factory, version, agent, station or item the organization does not have; 400 for a malformed body, a connection the token does not grant or a bad name (also `engine.ErrBadToolCall`, mapped to `gateway.ErrBadToolCall`); 413 for an input over 16 KiB as canonical JSON; 409 when the item already has an open tool approval or question (`engine.ErrToolApprovalOpen` or `ErrQuestionOpen`, mapped to `gateway.ErrToolApprovalOpen`), and 409 with another body when the item is no longer in progress, so the run's lease has ended (`engine.ErrNotInProgress` or `ErrItemChanged`, mapped to `gateway.ErrRunEnded`); 503 for any other failure. The input is never logged: the log lines (`tool approval reported`, `tool approval refused`, `tool approval failed`) carry the factory, agent, run, connection, tool and the input's size.
- **Jonah reviews** ([ADR 0034](../adr/0034-jonah-proposals.md) decision 1; `internal/gateway/jonah.go`). A task token of kind `jonah` (`domain.TaskKindJonah`) names no connection and carries the review's window as `ws` and `we` (unix seconds; `WindowStart`, `WindowEnd`) and whether a person asked for it as `jm` (`Manual`); `VerifyTaskToken` refuses a jonah token with a connection or without a window that ends after it starts, and a window or `jm` on any other kind. The gateway reads the events, proposals and evidence through `gateway.Jonah` (`SentBackBetween`, `Proposals`, `EvidenceItems` and `StationRunMedians`, which `ports.JonahStore` satisfies), passed as `Deps.Jonah`; nil answers a jonah token's bundle with 503 and changes nothing for other tokens. - **Checks** ([ADR 0040](../adr/0040-one-door-for-every-source.md) decision 19; `internal/core/engine/checks.go`, `internal/gateway/check.go`). A schedule trigger with `check:` queues a check on each firing instead of filing an item (`queueCheck`, skipped on a paused line and, with `pauseOnBudget`, on a spent budget). `Tick` runs `workChecks` on every instance, outside the schedule lock: it fails the expired checks of every loaded line (`Intake.ExpireChecks`, reason `lease expired`), then leases the queued checks of each claimable line into the slots its claims left (`Intake.ClaimCheck`; a full factory or `MaxRuns` leaves them queued) and runs each in the background under a heartbeat. A run is `engine.RunTask` with `domain.RunKindCheck`: no item, station, lease, repository or knowledge, the agent's environment, `check.timeout` as its time limit within the policy's box limit, and a task token of kind `check` that names the trigger (`tg`). Its spend is the line's, so budgets see it, and a budget stop cancels it as it cancels a station's run. Its answer must pass `domain.ParseCheckAnswer`; `FinishCheck` then records the decisions (the answer without its state) and saves the state, and a failed contract, a failed run, a timeout or a cancellation records the reason and keeps the saved state. `GET /run` with a check token serves `checkBundle`: the agent's prompt and skills, `domain.CheckAnswerSchema` as `agent/output.schema.json`, the check's brief, `spec.check` with the trigger and `Intake.CheckInput` (`Deps.Checks`; 503 when nil), `check.maxUsd` as `max_usd`, the built-ins that edit or run denied, every ask tool off, and no repository, git login, rule or knowledge. Needs you derives `check_failing` (the last three checks failed) and `check_limit` (a check skipped something over the limit that UTC day, once a day) on read from `Intake.CheckAlerts` (`internal/api/inbox.go`, `checkEntries`).
- **Grades** ([ADR 0039](../adr/0039-jonah-learns-from-the-line.md) decision 10; `internal/gateway/grade.go`). A grade is one model call that decides whether a result fixed the reason an item went back. `engine.RunTask` records it as a run of kind `try` with no item, so its cost is Jonah's, on a `domain.TaskKindGrade` bundle: its token (kind `grade`) names the try as `tr` and the result it grades as `g` (`domain.GradeOf`: `try`, `original` or `final`), and no item or connection, and its agent gets the model's access alone; no diff is read and no check runs. `GET /run` with a grade token answers a bundle whose `spec.grade` is `{reason, result: {kind, output, diff}}`, read through `gateway.Grades` (`Deps.Grades`; 503 when it or `Deps.Jonah` is nil), with the token's model and `jonahBudgetLeft` as `max_usd`, and no item, repository, definition, file, connection, knowledge, rule or tool; its MCP session lists no tool and its notes are none. `domain.ParseGradeAnswer` reads the worker's `{reason, verdict}`. `jonah.Grades` (`internal/jonah/grader.go`) implements `Grades` from storage: a try's run output and stored diff, the original run's output, or the output of the item's newest succeeded run at the try's station, each with the `data.reason` of the item's first `rejected` or `gate_rejected` event after the original run started. `internal/jonah`'s `Tries` starts the grades (the `PastTries` row).
- **Egress** ([ADR 0009](../adr/0009-agent-network-isolation.md) and its phase 4 amendment). compose.yaml keeps the agents network (`GOAL_SANDBOX_NETWORK`, default `goal_agents`: internal, no bridge address, so no route to the host, other networks or the internet) and its `goal-egress` service (`cmd/goal-egress`, `task egress:image`), on it and on compose's default network; `goal up` starts it with `GOAL_EGRESS_GATEWAY`, goald's gateway listener as the proxy reaches it (`host.docker.internal` for goald on this machine, `goald:8090` under `goal up --compose`). The Docker adapter checks the network exists and is internal before each container (one inspect) and runs boxes (where agents and command checks run) on it, each with `HTTP(S)_PROXY` naming the proxy and `NO_PROXY` the proxy and the container's loopback. The proxy has one policy for every client: any destination whose resolved addresses are all public, by `CONNECT` or plain-http forwarding, and goald's `/mcp` and `/run` by its reverse path (a container's `gateway_url` is the proxy's: `http://goal-egress:3128/mcp`); it resolves every destination itself and refuses any name with a loopback, private, link-local (metadata), CGNAT or reserved address (`egress.Public`), so rebinding cannot reach the host. Refusals are 403s and `egress refused` log lines in the proxy's container. The proxy belongs to no run, so reaping leaves it alone. The worker turns off Claude Code's nonessential traffic.
- **Sandboxes on Docker** (`docker.Sandboxes`, spec 4 §5.1). One container `goal-box-<run>` per run of the run's image, labelled like task containers, uid 1000, every capability dropped, no new privileges, init, the size's CPU, memory and PID limits (small 1/2 GiB/1024, medium 2/4 GiB/2048, large 4/8 GiB/4096), a writable root filesystem with a tmpfs `/tmp`, nothing mounted, on the agents network; its process sleeps until the deadline, so a box nobody deletes ends by itself. `Exec` is `docker exec` with stdout streamed and the stderr tail kept; Docker cannot end an exec, so each one carries a `GOAL_EXEC_ID` marker and a cancel, a timeout or `Delete` (`rm -f` of every container of the run) kills its processes and their children found by that marker. A cancel or timeout ends the caller's stdout, keeps draining Docker's stream (Docker finishes no exit in the box while an exited command's output waits for a reader) and scans again until Docker reports the exec exited (Docker answers the attach before it starts the command). `List` reads the `goal.run` labels.
- **Tools.** Named `<connection>__<tool>`. `tools.allow` and `tools.deny` entries of the form `<connection>__<pattern>` (`path.Match`) apply to gateway tools; deny wins, and a connection with allow entries serves only what they match.
- **Audit.** Every `tools/call`, denied ones included, appends a `gateway_tool_call` event (connection, tool, outcome, duration, request and response sizes) through `gateway.Events`, which `ports.Store` satisfies. Arguments, results and credentials are never recorded; resolved credentials are scrubbed from results, errors and logs.
- **Upstream protocol.** Upstream sessions negotiate the latest MCP protocol. On the 2026 protocol a server may require `Mcp-Param-*` headers mirroring annotated arguments (`x-mcp-header`; GitHub's server does), which the SDK adds only for tools the session has listed, so a call lists the upstream's tools first. The gateway's own `tools/list` result is `cacheScope: private` (it depends on the task's token).
- **Bounds.** Per-call and list timeouts, a cap on upstream response and agent request sizes, no redirects for credentialed requests.

### Intake as one door

Every item enters through `domain.File` (`internal/core/domain/file.go`, [ADR 0040](../adr/0040-one-door-for-every-source.md) decisions 1 to 3 and 21). It turns a `FileRequest` into a checked `NewItem`: the type against the line's work types, the lane, a trigger's station, the start, and the origin, generation and untrusted flag. The origins are `person`, `plan`, `trigger` and `follow-up`. One store helper writes the item with its `created` event, `item.filed` audit entry and `after` edges, for the API's `CreateItem`, the parts of `Assemble` and `AddPart`, firings, check answers and follow-ups.

`Engine.Tick` (`internal/core/engine/engine.go`) runs the intake loops in this order, on every goald instance, and each loop claims its own rows, so instances share the work:

1. **Notes** (`deliverNotes`, `followupnotes.go`) deliver waiting follow-up notes as `item_note` events.
2. **The follow-up sweep** (`fileFollowUps`, `followupfiling.go`) files, for each item that reached done, the waiting follow-ups that have a `start`, and collects the rest in the factory's triage item, within the daily caps. `DropFollowUp` and `FileFollowUp` are a person's Drop and File.
3. **The evaluation loop** (`evaluateDeliveries`, `deliveries.go`) claims pending `delivery_evaluations` with `FOR UPDATE SKIP LOCKED`, one per factory with an enabled trigger that names the delivery, and runs each factory's matching triggers in one transaction. A failure retries with backoff and is `failed` after five attempts; a lease that runs out is claimed again, and firings replay by their idempotency key, so nothing is created twice. The receiver (`POST /hooks/{webhook id}`, below) only stores the receipt and the evaluation rows.
4. **The start release** (`releaseQueue`, `start.go`) releases a queue station's items only once their `start_at` has passed and no open need holds them; a claim skips an item whose `start_at` is still ahead.
5. **The check loop** (`workChecks`, `checks.go`, [Checks](#mcp-gateway) above) leases queued checks into the slots the claims left.

The senders a webhook can use, and how each signs and names its events, are the catalog in `internal/catalog/senders`, described under "Receiving deliveries" in [access and secrets](../../apps/docs/src/content/docs/concepts/access-and-secrets.md) and in the `POST /hooks/{webhook id}` row of the table below.

### HTTP API

`contracts/api/openapi.yaml` is the contract ([ADR 0004](../adr/0004-frontend-and-monorepo.md)); `task api:gen` regenerates the Go server interface, models and client in `internal/api/gen` (oapi-codegen, pinned in `Taskfile.yml`) and the TypeScript types in `packages/api-client/src/schema.gen.ts` (openapi-typescript); both are committed, and `task check` fails when the TypeScript side is stale. Every operation names the permission it needs in `x-goal-scope`, one of `contracts/api/permissions.yaml` (phase 3, spec 3 §8.2); `tools/permgen`, run by `task api:gen`, checks both files together (an operation without a scope or with an unknown one, a permission whose roles contradict its level, a fresh permission for keys are refused) and generates `internal/api/permissions.gen.go` (`permissionRules`, `operationScopes`), and `task check` (`gen:check`) fails when it is stale. `internal/api` implements the strict server over small interfaces (the engine, the store's reads, the organizations, the definitions cache, the stream feed, the clock, the `Authorizer`) and answers errors as RFC 9457 problem details (`Problem{title, status, detail?, code?}`, `code` kebab-case): 404 for unknown organizations (one identical body, `org-not-found`, for unknown and deleted ones), factories, items and runs (one fixed body each without detail, `factory-not-found`, `item-not-found`, `run-not-found`, which the resolvers also give for one the principal may not see), 400 for invalid requests, 409 when a rule is broken (a taken or reserved slug) or the item's state does not allow the action (a decision on an item not waiting for a human, a retry of an item that is not blocked, a merge away from a merge station or one the pull request refuses), 403 `forbidden` for a refusal of the `Authorizer` or of cross-origin protection.

Every request passes the same layers, outermost first: the `Host` check (`api.CheckHost` around goald's whole mux, SPA included: a `Host` naming none of `localhost`, `127.0.0.1`, `[::1]`, the `GOAL_LISTEN` host and `GOAL_PUBLIC_URL`'s host (default `http://<GOAL_LISTEN>` on loopback), on any port, is 421 Misdirected Request, so a page that rebinds its own name to the loopback address cannot pass cross-origin protection as same-origin; `/v1/health` and the agents' `/mcp`, which the egress proxy reaches as `host.docker.internal` and every request to which carries a task token, are exempt); inside `/v1`, the access log (`internal/api/accesslog.go`: one `api request` line per request with its operationId, status, request id, `principal` `user:<id>`, `service:<key id>` or `none`, `credential` `session`, `key:<id>` or `pat:<id>`, and `org_id`; never a path, cookie, token or email); a 1 MiB body cap; `http.CrossOriginProtection` (an unsafe method from a browser page of another origin is refused; `Sec-Fetch-Site: same-origin`, `Origin` equal to `Host`, and clients that send neither, such as the CLI, pass); a request id (`X-Request-Id`, the caller's when well formed, else new; echoed, and recorded by the audit log); the request's principal and actor (`internal/api/credential.go`: under `GOAL_AUTH=none` `domain.LocalPrincipal`, whose actor is `domain.LocalUser`; under `session` `parseCredential` reads a bearer API key, personal token or session token, else the session cookie of the install's scheme, a malformed one being `domain.ErrUnauthenticated`, and each operation's `scope` resolves it in the database (`identity.go`, `ports.Identity`), the credential first (401), then the organization (404); in every mode an `Authorization` header that is not a bearer API key or session token, an agent's task token above all, is 401 `unauthenticated` with `WWW-Authenticate: Bearer realm="goal"`, never the local user); then, per operation, the org middleware (`internal/api/org.go`: `Tenancy.Org(path {org})`, binding the request with `domain.WithOrg`, so row-level security scopes every store call) and the `Authorizer` seam (`internal/api/authz.go`: `AccessRequest{Principal, Operation, Permission, Org, Factory}`), which the resolvers `s.factory`, `s.definition`, `s.item` and `s.run` pass again with the factory; `refusal` turns a hidden resource into the unknown one's error, `domain.ErrUnauthenticated` into 401 `unauthenticated` (`WWW-Authenticate: Bearer realm="goal"`) and `domain.ErrReauthRequired` into 403 `reauth-required`. goald wires `api.AllowAll` only under `GOAL_AUTH=none`; `api.Permissions` (`internal/api/permissions.go`) is the real `Authorizer` over the generated table (spec 3 §8.4: membership and visibility first, then roles, a key's scopes and ceiling, and the fresh-session rule, `domain.FreshFor`), with the visibility helpers `s.visible(ctx, factory)` and `s.can(ctx, factory)` for lists and `can` fields. `internal/api/testdata/access.golden` records its answer to every operation for every kind of principal in two organizations (`TestAuthorize_TwoOrgMatrix`). Beside `/v1`, under `GOAL_AUTH=session` only, `api.AuthProxy` answers every path under `/api` on the main listener before the mux can redirect it: it forwards the identity service's allowlisted `/api/auth/*` endpoints to `GOAL_AUTH_UPSTREAM` (loopback http) and refuses everything else with 404 `not-found` ([spec 3 §5.5](../history/specs/3-identity-and-access.md): encoded or unclean paths refused, forwarding headers replaced by `X-Goal-Client-Ip` from `GOAL_TRUSTED_PROXIES`, 64 KiB bodies, 2/10/15 s timeouts and 503 `auth-unavailable`, `Set-Auth-Token` stripped, cross-origin protection, no credentials in its log). Under `none`, `/api/…` is the UI's 404.

The docs site (`apps/docs`, a static Astro build with base `/docs`) is served at `/docs` and everything under it. Locally goald serves it from `GOAL_DOCS_DIR` (`api.Docs`, `internal/api/docs.go`, wired in `cmd/goald/main.go`'s `routes`): the directory's files read-only through an `os.Root`, GET and HEAD only, a directory's `index.html` for the directory (a directory asked for without its trailing slash, `/docs` included, is redirected to it), and 404 for a missing file, a directory without an index (never a listing) and a path that leaves the directory by `..` or a symlink. `goal up` sets `GOAL_DOCS_DIR=apps/docs/dist/docs` when that build exists (`task docs:build`), and compose.yaml's goald service mounts it read-only at `/docs`. The `Host` check covers `/docs` like the SPA; the gateway listener never serves it.

A decision's event names the decider (`actor`, the display name) and records `data.actor`, its ref (`user:local`).

**A person's control of an item in progress** (move, pause, send back; `engine.Move`, `Pause`, `Reject`): the transition takes the item's lease (`Transition.TakeLease`, lease outcome `taken`) and appends `lease_taken` (`data.action`) before the person's event, all in one transaction with the audit entry (`item.moved`, `item.paused`, `item.rejected`). The goald running the item stops its run at once when it made the change itself or when `engine.Interrupt`, which `cmd/goald` passes to `api.NewFeed` as a tap of every item notice, hears the `lease_taken` notice of an item it runs at that station under a lease acquired no later than the notice; any other instance finds out at its next heartbeat (`ErrLeaseLost`). Either way the run is finished as `cancelled` and nothing else moves the item. A conflict (the item moved meanwhile) is 409 `item-changed`.

**A person's start** (`engine.SetStart` and `engine.StartNow`, `PUT` and `DELETE /v1/orgs/{org}/items/{item}/start`, `goal start`; ADR 0040 decision 3): `PUT` takes a `Start` (`at`, `in` or `after`); `at` or `in` replaces the item's `start_at`, `after` alone keeps it, and each open after item becomes a `linked` edge by the caller (one it already needs is kept). `DELETE` clears `start_at` (Start now), and the first station releases the item on its next tick unless its needs still hold it. A time without a zone is read in the caller's notification time zone, UTC for an API key. Both refuse a done or cancelled item (409 `item-closed`) and one that has started (`item-started`: it left its line's first station, has `started_at`, or is not waiting there), and the guarded write is 409 `item-changed` when the item moved meanwhile. `POST …/items` takes the same `start`, and `Item.start.at` answers it.

**A person's lane change** (`engine.SetLane`, `POST /v1/orgs/{org}/items/{item}/lane`, `goal lane`): sets `Item.Lane`, which picks the agent at stations that route by lane, with a transition that keeps the item's station and state (`Transition.Lane`), so the same compare-and-set guards it (409 `item-changed`) and the `lane_set` event (from, to, actor) and `item.lane_set` audit entry commit with it. The lane is trimmed; an empty one is 400 `lane-required`, and when any station of the line routes by lane, a lane none of them routes is 400 `unknown-lane`. It refuses a done or cancelled item (409 `item-closed`), the lane the item has (`same-lane`), an assembly (`item-is-assembly`: its parts carry their own lanes) and an item in progress (`item-in-progress`): its running agent was chosen by the old lane, so it takes no lease; pause or move the item first.

**An agent's question** ([ADR 0018](../adr/0018-agents-ask-questions.md); `engine.Ask`, `engine.Answer`, `internal/core/engine/question.go`): `Ask(item, run, agent, question, choices)` takes the lease of the item in progress the same way, with outcome `asked`, and appends `lease_taken` (`data.action` `ask`), `question_asked` (question, choices, agent, run_id) and `waiting_human` in one transition that leaves the item `waiting_human` at its station; the run then stops as above. A question outside 1–500 characters, more than 4 choices or a choice outside 1–60 characters is `ErrBadQuestion`, an item that already has an open question `ErrQuestionOpen`, one not in progress `ErrNotInProgress`; each records nothing. `domain.OpenQuestion` finds the open question in the item's events (read through `ItemEvents`, no query of its own): the latest `question_asked` with no `question_answered`, `moved`, `paused`, `rejected` or `cancelled` after it, so a person's move, pause, send-back or cancel withdraws it. `Answer(item, by, answer, choiceIndex)` records `question_answered` (the picked choice's text as `answer` and its `choice_index`, or free text of 1–2000 characters) and puts the item in its station's arrival state with its rework count unchanged, with the audit entry `item.answered` (the answer's length and `choice_index`, never its text) in the same transition; a done or cancelled item is `ErrItemClosed` before the question is read, no open question is `ErrNoOpenQuestion`, a choice outside the choices or bad free text `ErrBadAnswer`. `Approve` of an item with an open question is `ErrQuestionOpen`. The item's next claim reads `domain.AnswersSinceLastRun` and its brief carries each question and answer under "## Answers from people", after the notes (`feedbackOf`).

**A tool call that asks first** ([ADR 0031](../adr/0031-tool-calls-ask-first-and-standing-rules.md); `engine.RequestToolApproval`, `DecideToolApproval`, `RevokeStandingRule`, `internal/core/engine/toolapproval.go`): `RequestToolApproval(item, run, agent, connection, tool, input)` takes the lease of the item in progress as `Ask` does, with outcome `awaiting_approval` (migration 00076), and appends `lease_taken` (`data.action` `tool_approval`), `tool_approval_requested` (connection, tool, input as canonical JSON, agent, run_id, `always_allow_offered`) and `waiting_human` in one transition; the run then stops. The call's connection is the name of an MCP server in the calling agent's environment file (`agentEnvironment`, `Environment.MCP`), and `always_allow_offered` is true when the file's mode of the tool (`domain.ResolveToolMode` over `MCPServer.ToolModes`) is `ask`, the one mode a standing rule lifts. A malformed connection or tool name, an input that is not one JSON value, or a server the environment does not have, is `ErrBadToolCall`; a line not on secrets `domain.ErrNotOnSecrets`; an open tool approval `ErrToolApprovalOpen`, an open question `ErrQuestionOpen`, an item not in progress `ErrNotInProgress`; each records nothing. An item has at most one open question or tool approval: `Ask` is `ErrToolApprovalOpen` while a tool approval is open, and `Approve` is `ErrQuestionOpen` or `ErrToolApprovalOpen` while either is. `domain.OpenToolApproval` finds the open approval (the latest `tool_approval_requested` with no `tool_approval_granted`, `tool_approval_denied`, `moved`, `paused`, `rejected` or `cancelled` after it), so a person's move, pause, send-back or cancel withdraws it. `DecideToolApproval(item, by, approve, alwaysAllow, note)` records `tool_approval_granted` (`approval_id`, `always_allow`) or `tool_approval_denied` (`approval_id`, and `note`, 1–2000 characters, only when given) and puts the item in its station's arrival state with its rework count unchanged. Always allow with a denial, a note with an approval or a note over 2000 characters is `ErrBadToolDecision`; Always allow where the approval does not offer it `ErrAlwaysAllowNotOffered`; no open approval `ErrNoOpenToolApproval`; a done or cancelled item `ErrItemClosed`. Always allow first creates the standing rule, keyed by the item's factory, the calling agent's environment (`AgentSpec.Environment`, `default` when it names none), the call's server (the approval's connection name), the tool and the agent role through `StandingRules.CreateServerStandingRule` (`engine.Deps.StandingRules`). It returns the active rule of the same key, so a retry after a failed transition leaves one rule. `RevokeStandingRule(id, by)` revokes through `StandingRules.RevokeStandingRule`: `ports.ErrNotFound` for an unknown rule, `ErrStandingRuleRevoked` for one revoked already. The item's next claim reads `domain.ToolDecisionsSinceLastRun`, and its brief lists the approved calls under "## Approved tool calls" and the denied ones with their notes under "## Denied tool calls", after the answers (`feedbackOf`). For the run bundle, `domain.GrantedCalls(events, run)` returns the calls granted before `run` started and after the run before it, and `domain.ServerToolModes(file, limit, rules, factory, environment, server, agent)` the modes of one MCP server of an environment file for an agent role, after the agent's active standing rules for that factory, environment and server lift `ask` to `allow` (Ask-first tool calls above). The one-time conversion to secrets (ADR 0037 decision 19) copied each active connection rule onto every environment whose converted file had a server named after the connection; it ran once, on 2026-11-04, and goald no longer runs it.

An item card is `{id, ref, number, title, type, lane, station, state, class_of_service, rework_count, cost_usd, created_at, updated_at, age_seconds, agent, pr_url}`: `agent` is the lease holder's agent while the item is in progress, `pr_url` the `pull_request` field of the item's latest station output, `age_seconds` the time since creation (created to done for a done item), `slot` the copy working it (1-based) while in progress at a station that runs several, `turn` the turns its running run reported (its `usage` events), `summary` the `summary` field of its latest station output. `board_lane` is the key of the station lane the card belongs to, the one holding it or to pick it up: the lease's agent while in progress, else `Station.AgentFor(lane)` at an agent station, `person` at a human station; null (absent) at queue and done stations, without a route for the item's lane and for a done or cancelled item.

A board station's `lanes` are who works there, sorted by role (`api.lanes`): at an agent station one per distinct agent (its agent, or each agent its route uses: `Station.LaneAgents`, the same list as `agents`), at a human station one `kind: person` lane keyed `person`, none at queue and done stations. An agent lane has `key` (the agent's name), `role` (`domain.Humanize`: "infra-engineer" → "Infra engineer"; the UI never shows numbered copies), `model` (the agent's, else the runtime's; null when neither names one), `model_label` (that model's `GOAL_MODELS` label from the builder meta without a leading "Claude ", else the model id), `slots` (the station's `Capacity`, min(agents, wip), shared by all its lanes until route entries get their own counts) and `busy` (the station's live leases held by that agent, read from the leases, never counted from the shown cards). A person lane's `role` is the station's id humanized, `model`, `model_label` and `slots` are null and `busy` is the items waiting on a person there.

A board station's statistics come from `FlowStats.StationTimes` over the window (the last N UTC days, 1d to 90d): `busy_ratio` (agent stations: lease time over slots × the window, measured from the factory's first lease if that is later, at most 1; null without lease history), `send_back_ratio` (stations with a gate: rejections over the window's verdicts; null without verdicts), `queue_trend` (queue and agent stations: waiting now against 24 h earlier), `oldest_waiting_seconds` (since the longest-waiting item's open span began) and `done_today` (the done station: items done since UTC midnight).

The board's `line` describes the line as a whole: `status` (`stopped` while an andon pull is open, with that pull as `andon`; else `running`), `wip` (items in progress or waiting on a person at the stations with a wip limit, against the sum of those limits), `release` (`policy` push or drum-buffer-rope as configured, `enforced` false: goald releases as push until drum-buffer-rope enforcement, which is later work; the `drum`, its configured `flow.constraint` or else the constraint now, its `buffer` and the items `in_buffer`, queued or ready there), `expedite` (`limit` from `flow.expedite.wip`, shown and not enforced, and `in_use`, the open expedite items past the queue stations; null for a line without an expedite lane) and `budget` (the weekly budget, `Runtime.WeeklyBudget` over `SpendSince` the last 7×24 h; null without one). A card is `in_buffer` when it waits at the drum; `rope_held` is false until the rope is enforced.

The board's `constraint` is the definition's `flow.constraint` when it names a station (`constraint_source: configured`), else the agent station whose slots leases held the largest share of the board's window, measured from the factory's first lease (`detected`), else, before any lease history, the agent station with the most work per slot right now, `(waiting + in_progress) / min(agents, wip)`, ties to the upstream station (`snapshot`; null when no agent station has work): `domain.Line.Candidates` and `ConstraintOf`. The same rule names the drum of the long waits, the cards' `in_buffer`, the bridge's insight and the overviews' `constraint.busy`; it is computed on request from `FlowStats.StationTimes` (no cache: the engine does not use it while drum-buffer-rope is deferred). `GET …/constraint` reports the top three candidates over a range with their time-weighted queue, mean wait and service, and `domain.WaitSaved`, an M/M/c estimate of the wait one more slot would save. Metrics count items that reached done in the range (UTC calendar days, `from` and `to` included: at most 90 days, `to` not after today, the last 7 days by default; `window=Nd` names the last N days) and the cost of agent runs started in it, for one work type with `type` (one the factory declares, else 400); long waits are counted at the definition's `flow.constraint` when it names a station, else at the snapshot constraint; WIP is the items now neither done nor cancelled, the rework rate the share of the items done in the window that were sent back at least once.

Under `GOAL_AUTH=session` (the default) every `/v1` operation but the public ones needs a credential; under `none` goald listens on loopback only. The CLI (`goal run`, `follow`, `item`, `approve`, `reject`, `retry`, `merge`, `deny`, `note`, `answer`, `move`, `pause`, `standing-rules list|revoke`, `andon [pull|clear]`, `factory pull|validate|push|publish|list|versions|restore|ask`, `org list|use|create`, `key list|create|revoke`, `credential list|create|replace|rm|import`, `search`, `runs`, `jonah [show|approve|edit|reject|look|try]`, `agent try-model`, `test keep|list|rm`) uses the generated Go client in one organization: `--org`, else `GOAL_ORG`, else `org` in `$XDG_CONFIG_HOME/goal/config.json` (default `~/.config/goal/config.json`, mode 0600, `{"api_url", "org", "credential_store"}`; `goal org use` writes it), else the install's only organization (with `GOAL_API_KEY` or a key or personal token stored by `goal login --token`, its own, skipping the config file's); with sign-in on, it sends `GOAL_API_KEY` or what `goal login` stored for the API's origin (the OS keychain, or `credentials.json` beside the config with `--store file`; `internal/cli/credentials.go`), only over https or to loopback, and exits 77 on a 401 or 403; a bare item number resolves when exactly one factory of the organization has an item with it (`--factory` otherwise). The web UI uses `@goal/api-client` (`packages/api-client`): `createGoalClient(baseUrl)` (openapi-fetch over the generated types) and `subscribe(baseUrl, {org, factory?}, handlers)` over the stream (`onItem`, `onFactory`, `onEvent` for the other names, `onResync`, `onStatus`).

#### Realtime stream

`GET /v1/orgs/{org}/stream` is `text/event-stream` and carries one organization's events only. Each committed item event is `event: item`, `id:` the event id, `data:` `{org_id, item_id, ref, factory_id, kind, station, state, at}` (`StreamEvent` in the contract); `?factory=` keeps one factory's. An organization's other events (`connection`, `knowledge`, ...) arrive under their own names with their data object, from the `goal_org_events` channel (`pg_notify('goal_org_events', {org_id, event, factory_id?, data})` in the transaction that causes them; `ports.ItemNotice.Org`); a name that is not lowercase letters, digits and dashes is never written. `event: factory` (`FactoryEvent`: `{org_id, factory_id, kind, andon_id, at}`, kind `andon_pulled` or `andon_cleared`) is one of them: the `andon_pulls` trigger of migration 00032 notifies it when a pull is inserted or cleared. `event: connection` (`ConnectionEvent`: `{connection_id, name, change}`, change `created`, `updated`, `deleted` or `tested`) is another: the connections adapter notifies it in each change's transaction, and `postgres.Notices` reads it back from the change's audit entry. `event: knowledge` (`KnowledgeEvent`: `{source_id, name, status}`, 4-17) follows a source's sync starting (the claim) and ending (`FinishSync`), and a verdict on one of its documents (`GiveVerdict`, ADR 0027), each notified in its transaction and read back from the source's row (its name and current status). `event: resync` (`data: {}`) says events may have been missed, so the client re-reads what it shows; a `: heartbeat` comment comes every 15 s and `retry: 3000` opens the stream. There is no replay (`Last-Event-ID` is ignored): a client re-reads on every (re)connection, which `subscribe` signals as a resync.

```
item_events INSERT ── trigger notify_item_event() ── pg_notify('goal_events', {org_id, id, factory_id, item_id, number, kind, station, state, at})
an org's other event (phase 4) ───────────────────── pg_notify('goal_org_events', {org_id, event, factory_id?, data})
        │  (any goald instance, in the transaction that causes it)
        ▼
goald: postgres.Notices.Listen (one connection, both channels, reconnect + Resync) ──▶ api.Feed (fan-out by org) ──▶ each SSE client of that org on this instance
```

Each instance listens once and fans out to its own clients, each receiving only its organization's notices (and every resync), so `goald` stays stateless and any instance serves any client. A client that falls 256 notices behind has its stream ended (it reconnects and re-reads) so it never holds up the others; at shutdown the feed ends every stream before HTTP drains.

#### Merge stations

A human station, or an agent station with a `gate`, may declare `action: merge` (schema: those two only; the secrets check's `merge-needs-code-host` requires a repository token to merge with). `POST /v1/orgs/{org}/items/{item}/merge` (`goal merge <item>`) is `engine.Merge` (spec 4 §4.7, 4-13):

1. The item must be waiting at that station (409 otherwise), and its outputs must name at least one pull request (409 `cannot-merge` otherwise): `domain.Item.PullRequests`, the `pull_request` string and the `pull_requests` array of each station's latest output, https URLs only, in the line's station order, each once.
2. Each URL's host must be one of the organization's code hosts (`domain.ParseCodeRepository` over `engine.Deps.Hosts`), whose listed kind picks the adapter (`engine.Deps.CodeHosts`); an unlisted host refuses the whole merge before anything is opened (409 `no-code-host-connection`, naming the host and Code hosts settings). Each URL then gets its token (`mergeTargets`, ADR 0041 decisions 3 and 5). On a line with `runtime.repositories`, the most specific entry that covers the URL's repository must write (refused with `engine.ErrNoWriteEntry` otherwise, before anything is opened), and its token signs in, opened once per entry. An entry without a token, and a line without `runtime.repositories`, sign in with `runtime.repository.token` (`repositoryTargets`): every such URL must be on the host of `runtime.repository.url`, and `runtime.repository.forge`, when set, must agree with the host's listed kind (409 `no-code-host-connection` otherwise). Each token is opened through `OrgSecrets` for the line's factory, which checks its scope and audits it as `secret.used` with no run.
3. For each pull request in turn, through its `CodeHost`: read it; one already merged is skipped; one closed is refused. Bring its branch up to date with its base at the head just read (`UpdateBranch`, never forced; a branch already up to date is a success, and `github` calls a conflict only a `dirty` `mergeable_state` or a 422 naming a merge conflict, any other 422 being `ErrNotMergeable`) and read it again, which reuses the adapter's mergeability wait. A branch that conflicts with its base (`ports.ErrMergeConflict` from `UpdateBranch`) is a merge conflict: with `board.flow.assemblies.onConflict: rework` (the default) the item goes back to `domain.Line.ReworkTarget` (the gate's `onReject`, else the nearest agent station upstream) with a `merge_conflict` event (actor `engine`) whose reason names the pull request, its base, the files when the host named them and says to merge origin/<base> and resolve; it is no rejection, so `ReworkCount` and the gate's `maxRework` are untouched, a person's `merge` answers 200 with the item back there and no `approved` event, and a gate keeps its `gate_approved` and an `advanced` lease. With `onConflict: human` the conflict is a refusal like the others (it wraps both `ErrMergeConflict` and `ErrNotMergeable`). Otherwise refuse (409 `cannot-merge` naming it, the item does not move) unless it is open and the host reports it mergeable (a `Mergeable` false after the update stays a refusal: the port cannot tell conflicts from failing checks): one whose mergeability the host is still computing after the adapter's wait (`MergeabilityPending`) is refused with a message saying so and to try again, apart from the conflicts or failing required checks refusal. A person's merge reads it once; a gate's merge reads a pending one again after a growing wait on the engine clock (2 s, then doubling), heartbeating the lease, for up to `engine.Config.MergeWait` (default 60 s, which `engine.New` requires to be shorter than `gateMergeTimeout`). Then merge it (squash by default) at the head SHA the second read returned, so the host refuses if the branch moved; never forced. That read can still return the old head while GitHub finishes the update in the background, so `github` retries a 409 "Head branch was modified" at the head it reads again, after each wait of `github.Config.MergeRetries`, before it refuses the merge (`ErrNotMergeable`, not a conflict). Read it again and require `merged`. Then delete its head branch, only when it lives in the repository it merged into and is not its base branch; a failure there is logged, not fatal. Nothing else is ever deleted.
4. Approve the item in one transition with one `merged` event per pull request (`pull_request`, `sha`, `method`, `branch_deleted`) and an `approved` event by the request's actor.

The pull requests merged before a refusal stay merged and are skipped next time, so a retry after a partial failure is safe. Which repositories can be merged is the token's own scope. No credential reaches events, errors or logs.

At a gate station with `action: merge` nobody clicks: when the gate approves, `finish` (`engine.mergeOnApproval`) runs steps 2 and 3 with the engine as the actor (`domain.EngineActor`), over the item's outputs plus the gate's own output, which only the transition holds yet. It runs on a context that survives the run's cancellation (bounded by `gateMergeTimeout`), while the lease is held. The item then moves on in one transition carrying `gate_approved` (the agent), one `merged` event per pull request (actor `engine`) and the arrival events; no person acted, so it is no touch (spec 4 §4.9). A merge conflict reworks as in step 3. A pull request that is open, has no conflict and is only not mergeable yet (still pending after the wait, `Mergeable` false after a clean branch update, a moved head, or `UpdateBranch` or `Merge` refusing it with `ErrNotMergeable`, as GitHub refuses a merge whose required checks have not run on the new head) defers the merge: the item goes back to the gate's arrival state (queued) in one transition carrying `gate_approved` and a `merge_deferred` event (actor `engine`, data `reason`, `pull_request` and `deferrals`, the count in a row) with lease outcome `released`, so the gate's agent runs again, waits for the checks and approves again. The deferrals in a row are the `merge_deferred` events since the item's latest `moved` or `retried` event; the refusal after `engine.Config.MergeDeferrals` of them (default 5) blocks the item, with a reason naming the count and the last refusal. Any other refusal (no pull request, no connection serving a host, a closed pull request, the host unreachable, or a conflict under `onConflict: human`) blocks the item at the gate with the reason in its `blocked` event; it never moves on unmerged. `engine.Retry` queues it at the gate again: the gate runs again and its next approval skips what already merged. A gate rejection merges nothing. A draft pull request is not marked ready first (the `CodeHost` port has no such call), so the host refuses it like any unmergeable one. An item escalated to a person at a merge gate after too many reworks is merged by `engine.Merge` as at a human station.

**Rule violations** ([ADR 0014](../adr/0014-factory-rules.md) §6): `finish` reads the optional `violations` of any accepted station output (`domain.ViolationsFrom`, like `domain.LaneFrom` reads `lane`; no contract is named in Go) and appends one `rule_violated` item event per entry whose `rule` the run's version declares (`domain.Line.Rules`, from `spec.rules`), with data `{rule, reason, station, agent}`, in the same transition that accepts the output, gate rejections and assemblies included. So the events are written once with the acceptance and never for an output that fails its contract or checks, or whose lease was lost. An entry naming no declared rule is logged (`unknown rule violated`) and not counted. Counting `rule_violated` events by `data.rule` gives each rule's violations.

### Factory definitions in object storage

Definitions are content, not code ([ADR 0005](../adr/0005-factory-definitions-in-object-storage.md) and its 2.2 amendment). The content lives in the bucket; the versions and the pointer to the running one live in PostgreSQL:

```
s3://<bucket>/
  orgs/<org-id>/blobs/<sha256>          every definition file (factory.yaml, agents/, skills/, contracts/, environments/, memory.yaml), once per org, never overwritten
  catalog/templates/<name>/<version>/   curated starting points; catalog/skills/ (D) beside it
  orgs/<org-id>/knowledge/<sha256>      uploaded knowledge documents (4-16), written once, deleted with the last document holding them; catalog/connectors/ is dropped
  orgs/<org-id>/knowledge/<source-id>/<snapshot-id>.zip   a source's knowledge snapshot (ADR 0038), one zip of Markdown files per sync that changed something

PostgreSQL
  definition_versions   one row per draft or published version: manifest {path → sha256}, number, revision, author, publisher,
                        and a published version's counts (stations, agents, skills, connections), so the version list reads no files;
                        publish stores them, and the first list computes and stores those of an older version that has none
  definition_blobs      the hashes each org has stored
  factories.current_version_id          the published version that runs; publish and restore move it in one transaction
  agent_runs.definition_version_id      the version a run started on, and finishes on
```

- **Content.** A blob's key is the lowercase hex SHA-256 of its bytes. It is written with a conditional put and never rewritten (an object already at the key is adopted only when it hashes to it, and replaced otherwise), so a version's tree is reproducible from its manifest alone and identical files are stored once across versions and clones. Readers verify the hash of every blob they fetch.
- **Versions.** A factory has at most one open draft, shared by its editors and saved with optimistic concurrency on its revision. Publishing makes it version N+1, moves `current_version_id` and writes the audit row in one transaction; a trigger NOTIFYs `goal_definitions`, and every goald reloads. Published versions never change; restore moves the pointer back, and numbers are never reused.
- **Lifecycle.** A factory starts draft-only (`createFactory`; `deleteFactory` removes it until a version is published), then is published and either running or paused (`pauseFactory`, `resumeFactory`, `factory:manage`), and finally archived. Archiving (`archiveFactory`) takes `factory:archive`, an org permission of owners and admins (and keys and personal tokens that carry it), never of a factory editor. Only a paused factory none of whose items holds a lease is archived: a running one is 409 `factory-running` ("Pause the factory first"), one whose runs still hold leases 409 `factory-busy` ("N items are being worked", N from the store's `*ports.FactoryBusyError`, counted under the same row lock as the refusal). An archived factory keeps its versions, items and history, stays readable by id or name, and `listFactories` leaves it out unless `archived=true`, which lists only the archived ones. Restoring (`restoreFactory`, same permission) lists it again and leaves it paused; `resumeFactory` starts it. Both are idempotent: archiving an archived factory, or restoring a live one, changes nothing, answers 200 and writes no audit entry; otherwise the change is audited `factory.archived` or `factory.restored` with the factory's name. Purging (`purgeFactory`) deletes an archived factory for good and takes `factory:delete`, an org permission of owners and admins (and keys and personal tokens that carry it), never of a factory editor; `deleteFactory` keeps `definition:edit` and only removes a factory never published (409 `factory-published` otherwise). Only an archived factory none of whose items holds a lease is purged: a live one is 409 `factory-not-archived` ("Archive the factory first"), one whose runs still hold leases 409 `factory-busy`. `DeleteArchivedFactory` removes its items, runs, events and versions in one transaction and audits `factory.deleted`; its bucket blobs are left to the organization's retention purge, its audit history stays, and the row delete's notice drops the factory from every goald's cache.
- **Runs.** A run keeps the version it started on (contract, checks, agent files, gateway tools); an item's next step uses the current version.
- `internal/config` loads a definition from any `fs.FS`, built from a manifest and its blobs or, for a local working copy, by `LoadDir`. Paths in `factory.yaml` resolve inside that tree only. `config.Check` reports every finding as a located `domain.DefinitionProblem` (stable kebab-case code, severity, the check that found it, the Visual section and model pointer, file, line and column, and machine-applicable fixes); `Load` fails on the blocking ones but the removed forms (below). Since 4-10 a definition names the organization's connections (`spec.connections` as names, `runtime.modelConnection`, `runtime.repository: {url, connection}`), `runtime.size`, `runtime.tools` (mise tool specs, `tool-spec-invalid`) and `knowledge.sources`; since the cutover (4-14) the forms phase 4 removed are errors, each with a quick fix: `field-removed` (`runtime.runner`, `image`, `auth`, `secrets`, `knowledgeBase`), `env-reference-removed` (`runtime.repository.token`) and `connection-inline-removed` (inline and connector-form connections; the fix puts the organization's connection of the same name in its place). A value outside a schema enum (`schema-enum`) gets one quick fix, "Use <value>", which replaces it with the allowed value nearest by edit distance (the first in the schema's order on a tie); a `const` violation and a non-string value get none. A published version that has one still loads, its line naming each (`domain.Line.Removed`), and does not run.
- `internal/factorymodel` is the Visual editor's model of `factory.yaml` (`GET/PUT …/draft/model/{section}`): it reads each section, applies a section's JSON Patch edits keeping every comment and the file's formatting, formats new keys in the spec's canonical order and diffs two versions into changes by target. The agents section carries `default_model`, `agents`, `skills` and `rules` (ADR 0014's `spec.rules`, `{name, source}`, matched by name like skills: diff target `rule`, pointers under `/agents/rules`, where `config.Check` puts rule problems too). A rule's file, `rules/<name>.md`, is a draft file like any other, written through the draft files API and published as a blob of the version's manifest.
- The line's assembly policy, `domain.FlowPolicy.Assemblies` (`board.flow.assemblies`, spec 4 §4.4), says how runs keep item branches fresh (`FreshBase`: `rebase`, the default, or `merge`) what a merge conflict does (`OnConflict`: `rework`, the default, or `human`) and whether items whose files overlap wait for each other (`Overlap`: `serialize`, the default, or `allow`; see Overlapping files above); whether a station's plan becomes an assembly (`Materialize`, `materialize`: true, the default, or false); and whether plans bind late (`ChangedSince`, `changedSince`: false, the default, or true: a station with `context: [inflight]` that finishes an item records the head of each of the item's repositories' default branches on its `work_item_repositories` row (`Transition.BaseCommits`), read with the token of the `runtime.repositories` entry that covers it, a read entry's first, or else through `mergeTargets`, and the first repository's as `domain.Item.BaseCommit` too ([ADR 0041](../adr/0041-code-and-github-without-an-app.md) decision 5; a line without entries reads `runtime.repository` alone); `Assemble` and `AddPart` copy the assembly's to the parts, per repository. Every later claim compares each repository's base commit (the first's falls back to the item's) with its head (`CodeHost.Compare`) and gets one `domain.ChangedSinceSection`, naming the repository, for the commits whose files overlap the item's paths in that repository (`domain.RepositoryGlobs`), named by the item that merged them (`Store.MergedItems`) or by subject; a code-host error is logged and blocks nothing, ADR 0015 decision 5); `internal/config` applies the defaults. The gateway passes `FreshBase` to the worker as the run bundle's `repository.fresh_base`, and `goal-agent prepare` rebases (or merges) an existing item branch on the default branch with it; on a conflict it aborts, leaves the branch as pushed and reports the files in its `prepared` line and to the agent (`apps/worker/README.md`). goald does not record those yet; the engine acts on `Overlap` with the overlap hold (Overlapping files above). `OnConflict` decides what a conflict found by the update before a merge does (step 3 of the merge above): `rework` sends the item back to be built, `human` refuses the merge. `Materialize`: the engine's `check` reads the current line once (`lineNow`, the line `finish` then moves the item along) and, when it materializes and the output is not a gate's rejection, reads the platform-defined `plan` field with `domain.PlanFrom` (`[{key, title, lane, brief, paths, needs}]`, absent, null or `[]` meaning no plan, validated by `domain.ValidatePlan`); a malformed or refused plan is `domain.ErrBadPlan`, a failed output like a bad verdict: `contract_failed`, one more attempt with the reason, then blocked. `finish` with a non-empty plan calls `Store.Assemble` instead of `Transition`: from `in_progress` to `assembly` at the same station, fenced by the lease, outcome `advanced`, with the output, output station and lane recorded on the assembly; the parts are queued at that station. At a gate only an approval assembles (with its `gate_approved` event) and it merges nothing, even at a merge gate: the parts make the pull requests. A part's plan blocks the part ("a part cannot plan an assembly"). A lost acknowledgement of `Assemble` is only logged: the item is already an assembly, and a retry returns the same parts. With `Materialize` off the plan is ignored and the item moves on as without one. The same `check`, for any output that is not a gate's rejection, resolves the item refs of the output property the line maps to `board.flow.dependencies.after` (`domain.FlowPolicy.Dependencies.After`; unset reads none) with `domain.AfterFrom` and, with reads only, `Store.ItemByNumber` in the item's factory and a walk of `Store.Edges`: a malformed, other-factory, unknown, done or cancelled ref, the item itself or its assembly, or one that already needs the item is `domain.ErrBadAfter`, failed like a bad plan with nothing written. For a single item the engine then adds a `linked` edge by the agent actor to each before `finish` moves it (an edge an earlier attempt added counts; a cycle closed meanwhile fails the output); with a plan, `ports.Assembly.After` and `AfterBy` make `Assemble` add them from every part without in-plan needs in its transaction ([ADR 0015](../adr/0015-overlapping-in-flight-work.md) §2, [factory-definition.md](factory-definition.md#dependencies-boardflowdependenciesafter)).
- **Integration branches** ([ADR 0033](../adr/0033-assembly-integration-branches.md)). `domain.AssemblyPolicy.Integration` (`flow.assemblies.integration`) is `trunk` by default: each part merges into the default branch. In mode `branch`, the engine decides each claim's branch and base once, before its first run (`engine.integrate`, `internal/core/engine/integration.go`), for a part (an item with a parent): it reads the assembly, and when the assembly has no integration branch yet, the part's outputs name no pull request (`Item.PullRequest`) and the assembly has at least `MinParts` parts (`Store.Parts`), it calls `Store.SetIntegrationBranch` with `domain.IntegrationBranch(root)` and `Line.LandingStation(root.Station)` (logged `integration branch set`); a `false` answer (another instance set it first) reads the assembly again. A line whose only merge stations come before the planning station has nowhere to land, so the assembly stays on trunk (logged `integration branch not set`). When the assembly has an integration branch and the part names a pull request, the engine reads the pull request's `BaseBranch` through its host's code host with the token `mergeTargets` picks; a failed read blocks the claim rather than guess. `domain.RunBase(part, root, prBase)` then gives the part's `Item.Branch()` and, as its base, the integration branch, unless the part's pull request was opened against another base (one opened against the default branch before the switch stays there). Every other item, and every item in mode `trunk`, gets an empty base: the default branch. A part with a base gets `Branch` and `Base` in its task token; the gateway puts them in the run bundle's `repository.branch` and `repository.base` (omitted when empty, so a trunk bundle is unchanged), and the workspace note says the branch is new from `<base>`, to open the pull request into `<base>` and the policy's `refresh` (`onLand` or `eachPart`). The integration branch is kept per repository too (ADR 0041 decision 5): a part whose base is the integration branch calls `Store.JoinIntegrationRepositories` with its repositories (`domain.ResolveItemRepositories`), which gives the assembly a `work_item_repositories` row for each one it lacks, joined `filing` with the next ordinal (`domain.JoinIntegration`), and sets `integration_branch` where it is NULL, under the assembly's row lock; repositories past `domain.MaxItemRepositories` are left out (logged `integration repositories left out`). The name is one, `domain.IntegrationBranch(root)`, and `work_items.integration_branch` stays the assembly's switch. Merges do not change: `merge` merges each pull request into its own base. When its last part closes, the store's `closeAssembly` gives the assembly the same rows for every repository of its done parts (`DonePartRepositories`, plan order) in the transaction that moves it to `integration_land_at`, so its landing run's clones (`domain.RunCode` from the assembly's rows) are the union of its parts' repositories; a repository only a cancelled part had gets no row there. A finished assembly lands as a landing root, `domain.Item.Landing` (no parent and an integration branch: the store sets the column only on an assembly's root, so its next claims are its landing at `integration_land_at` and the reworks its gate sends back). At every station, `integrate` gives it `RunBase`'s branch, the integration branch, and an empty base, the default branch, so its token carries `Branch` alone and the bundle's `repository.branch` is the integration branch; a landing the gate rejects to its `onReject` station is reworked there on the same branch, where the engineer reconciles conflicts. Only at its landing station (the claim's station is `Item.IntegrationLandAt`, the station the store sends it to land) does its workspace note say it is landing the whole assembly: first merge the default branch (origin/HEAD) into the integration branch, never rebase it, then, when none is open, open a pull request with `gh pr create --base <default branch> --head <integration branch>` and name it in the output's `pull_request`. At any other station, as at build after a rejection, the note instead says the branch is the assembly's integration branch, which lands on the default branch, and asks to fix what the last rejection asks for, push to it as a plain push and keep its pull request into the default branch open; the rejection reason reaches the brief as the gate's output among the earlier stations' outputs. The landing gate's approval merges it through `mergeOnApproval`, as any gate with action `merge`, and the root advances to done. An integration branch with no commits beyond the default branch lands empty: a landing root whose gate output holds an explicit `pull_requests: []` (`domain.NoPullRequests`), and whose outputs name no pull request, advances with nothing merged (logged `empty landing`); an output without the key, and any item that is not a landing root, still blocks with "no output names a pull_request".
- `internal/adapters/objectstore/s3` implements `ObjectStore` with the AWS SDK for Go v2: a custom endpoint with path-style addressing for RustFS, the standard credential chain on AWS. It uses no versioning API, so RustFS and R2 behave the same (ADR 0005, phase 4 amendment): `List` is `ListObjectsV2`, `Delete` removes for good, `DeletePrefix` removes each list page with one `DeleteObjects`, and `EnsureBucket` (used by `goal storage init`) only creates the bucket; a bucket that still has versioning on keeps working. `PutIfAbsent` is a conditional `PutObject` (`If-None-Match: *`, which S3 and RustFS support; 412 means the object is there and `HeadObject` reports it); a server answering 501 gets `HeadObject` then `PutObject`, harmless for content-addressed keys. `GetRange` is a ranged `GetObject` (416, a range past the end, reads nothing; it skips response checksum validation, since a server may send the whole object's checksum for a range); `PutStream` is one `PutObject` for a stream of at most one 5 MiB part, else a multipart upload of 5 MiB parts (R2 wants every part but the last of one size), aborted when the reader or a part fails.
- `internal/adapters/store/postgres` implements `DefinitionStore` as `postgres.Definitions` (`NewDefinitions(pool, objects, log)`, over the `ObjectStore` port) and `DefinitionNotices` as `NewDefinitionNotices(connConfig, log)`. Blob objects are written before and outside the transaction that records them in `definition_blobs`; every other change locks the factory row first (then its versions, then its items) and checks that every manifest hash is one of the organization's blobs. Triggers keep published versions immutable and undeletable (except by `goal_purge_org`), the pointer on a published version of the same factory, and NOTIFY `goal_definitions` with `{org_id, factory_id, kind, version_id, number, revision, by}` (migration 00010).
- Editing goes through goald's API: the builder and the CLI (`internal/cli/factory.go`) write the draft. `goal factory push <dir>` replaces the draft's tree (`PUT …/draft/tree` with the `expected_revision` it read; a factory the organization lacks is created from the folder, keeping its `metadata.id`) and refuses an open draft with changes unless it holds the folder's last pull or push (`--replace-draft` archives it), or a published version newer than the one `.goal/pulled.json` records unless that version holds the folder's files (`--force`); `--publish` sends the current version id it read as `expected_current_version_id`. `goal factory pull` reads a published version by number (so one pull never mixes two versions) or the draft, checking every file against its sha256. `goal factory validate` validates through goald (the open draft with the folder as overlay, or the folder alone); `goal validate` is the offline `config.Check`, which `task check` runs on the fixtures. The template catalog (`catalog/templates/<name>/<version>/`, `authoring.TemplateCatalog`) is written only by the operator's `goal catalog templates push`: once per version, files first and `template.yaml` last, which is when goald lists it. A repeated push of a version the catalog holds byte for byte (no object missing, changed or extra under its prefix) succeeds and writes nothing, so the push can run on every deploy; any other stored version is refused, because a template version never changes. It refuses a definition with errors, a `metadata.id` other than the nil UUID and a `template.yaml` without `code: none` or `code: read`, the code access the template needs (ADR 0041). goald reports `code: write` for a template whose line has a station with `action: merge`, and `none` for a version pushed before `code` existed.
- **Skills catalog** (`internal/builder`, 2.2-D). `catalog/skills/index.json` lists every skill (`owner/repo/skill`, the commit it is pinned at, its description from SKILL.md, installs, file and byte counts, and a sha256 over its files); `catalog/skills/<owner>/<repo>/<skill>/<commit>/` holds that commit's folder, written once, never overwritten or deleted (drafts may have vendored it). Only the operator's `goal catalog skills sync --file <sources.yaml> [--search q]… [--top n]` writes it, through `ports.SkillSource`: the folder is read from GitHub's git objects of the resolved commit (regular files only, at most 200 files and 1 MiB, valid relative paths, hidden files left out, each blob checked against its tree entry; only the configured hosts, no redirect off them, timeouts, tokens scrubbed from errors), checked again by the builder, then stored. goald only reads it: the parsed index is cached by the object's ETag and re-checked at most every 5 minutes, a malformed index reads as empty (logged `builder.skills_index_invalid`), and every folder served is checked against its index entry's hash. A draft vendors a skill under `skills/<skill>/` with `skills[].origin` (`skills.sh:<owner>/<repo>@<skill>#<commit>`).
- **Transition (2.2-B, ended in 4-3).** The pre-2.2 layout, one prefix of mutable files per factory (`factories/<id>/`, then `orgs/<org-id>/factories/<id>/`), was imported once as v1 of each factory by the releases before phase 4, which read object versions to do it. The import and `internal/factorystore` are gone; the prefixes left in old buckets are never read and can be removed by hand. `postgres.Migrate` refuses (`ErrLegacyImportPending`: "start the previous release of goald once") a database where a live organization's import is still pending (`legacy_import_pending`, 00039) or that is from before 00039, so goald never starts on one; migration 00050 drops the record.

The definitions cache (`internal/definitions`) holds the current published version of every factory of every organization `Tenancy.ActiveOrgs` lists, read from `DefinitionStore` (manifests in PostgreSQL, each file a blob verified against its hash). It reloads an organization's current versions on every `goal_definitions` notice of a publish, restore, pause or resume (`Listen`; every goald within a second), drops a deleted organization's lines on the notice `DeleteOrg` sends in its transaction (kind `org`; the engine then cancels and releases the runs it has there, and `Version` serves no version of an organization that is not live), everything on a resync, every `GOAL_REFRESH_EVERY` (30s) as a safety net, and an organization when the API is asked for a factory it does not know whose current version the store has and the cache lacks (a publish whose notice has not arrived; one reload per organization for the lookups that miss together, a typo or a draft-only factory reloads nothing, and a store failure on that path answers 404). Names match without case, as in authoring. A version that does not load in this goald keeps the previous one in use. Runs pin their version: the engine records `agent_runs.definition_version_id`, the gateway token (`v` claim) carries it, and contracts, the run bundle's agent files and gateway tools are read by version id (`Validate(ctx, version, …)`, `AgentFiles`, `Rules`, `Version`); versions no longer current stay in an LRU bounded by `GOAL_DEFINITION_CACHE_BYTES` (64 MiB) and load from the store on a miss. The next move of an item after its run follows the current line, matched by station id. A paused factory (`factories.paused_at`) is a line with `Paused`: the engine releases and claims nothing there, and its runs in progress finish. An archived factory (`factories.archived_at`, archived only once paused and idle) has no line: the `current` notice its archive sends takes it out of the lines on every goald, so `engine.SetLines` no longer sees it and none of its items is claimed, and the notice of its restore puts the line back, still paused. Its versions stay readable all the while (`Version` for runs and pages that pin one, `Lookup`, `Factories`), and a connection's or knowledge source's `usedBy` (`internal/api`) skips it, so it keeps no connection or source from being renamed or deleted. Every read (`Factories`, `Lookup`, `Version`, contracts, agent files) sees only the organization in its context.

**Jonah reviews** ([ADR 0034](../adr/0034-jonah-proposals.md)). goald builds `jonah.NewReviews` with the postgres store as its `Orgs` and `JonahStore`, the definitions cache as its `ReviewDefinitions` (`CurrentLines`, `Line` of any published version of the organization, `VersionFiles`), the engine as its `TaskRunner` and the clock, and passes the store to `gateway.New` as `Deps.Jonah`, which serves a jonah token its bundle. Each round (`runJonahReviews` in `cmd/goald/jonah.go`, at once and every `GOAL_JONAH_REVIEW_EVERY`, default 1m) runs `Reviews.Sweep`, which queues the daily reviews that are due, only inside `Intake.WithScheduleLock`, the session advisory lock the schedules use, so one goald sweeps; a goald that finds the lock held logs `jonah review sweep skipped` at debug and skips its sweep. `Reviews.Work` then runs on every goald: `ClaimJonahReview` takes a review with `FOR UPDATE SKIP LOCKED` and a lease of `GOAL_JONAH_REVIEW_TIMEOUT` (default 30m, the review run's own time limit) plus `GOAL_JONAH_REVIEW_LEASE_MARGIN` (default 5m), so two goald never run one review, and a review whose goald died is claimed again when the lease ends; the old claim's finish is refused with `ErrLeaseLost`. Manual reviews (the overview's "Look for improvements now", `goal jonah look`) are queued by the API and run by the same `Work`.

**Engine across organizations.** Each `domain.Line` carries its `OrgID`, and every store call the engine makes for a line, the run's included, is bound to it (`domain.WithOrg`); `Submit` and the decisions find only factories of the organization in their context (another's is `ErrNotFound`). `Tick` releases queue stations line by line, then claims with two-level round-robin: in each pass every organization with work claims at most one item, trying its factories in turn and their agent stations in line order, until nothing more can be claimed or the instance runs `GOAL_MAX_RUNS` runs (0: no cap). The order of organizations and of each one's factories rotates every tick; the tick counter and the run count are local scheduling hints, not state. `SweepLeases` requeues expired leases once per organization `ActiveOrgs` lists, so leases on factories no longer loaded are swept too.

**Polling CI.** `engine.PollCI`, which `engine.Run` calls on every iteration, polls CI for the open CI waits of every active organization ([ADR 0044](../adr/0044-goald-waits-for-ci.md), decision 9). It leases the due commit polls one at a time under the engine's holder for one minute (`LeaseDueCIPolls`), well above the 20 s bound of one `CodeHost.Checks` call, up to `SweepLimit` per organization. Each poll makes one `Checks` call, whatever the number of waits on its commit, with the adapter of the repository's host kind and the token `repositoryHost` reads with (the covering `runtime.repositories` entry's, else `runtime.repository.token`), taken from the line of the first wait whose factory is loaded, and with the first wait's pull request URL. From that one answer it decides every open wait on the commit (`OpenCIWaitsOnPoll`), with its station's `waitFor` grace and max (the defaults when the line or station is gone): every check finished ends it `passed`, or `failed` when one failed; max passed since it started ends it `timed_out`; no check seen within grace ends it `no_ci`; an error wrapping `ports.ErrCINotReadable` ends it `unreadable`, as does a repository no loaded line can sign in to. A pull request whose head moved moves its waits to the new head (`ReplaceCIWaitSHA`), whose poll is due at once. A `ports.RateLimitedError` keeps every wait and makes the poll due at its `RetryAt`; any other error keeps them and backs the poll off. The interval resets to 15 s when the checks change and doubles up to 2 min while they do not. Each wait the poller ends goes to `ciWaitEnded`, which logs `ci wait ended`; the poller holds no item lease, so the item's next claim acts on the outcome under its lease (`ciGate`). A before wait gates the run. An after wait holds the run whose output would move the item forward after it pushed (`holdForCI`, decision 3): once CI passed or got none, the claim applies that output without a run (`applyHeld`, through `finish` and so `mergeOnApproval`); once it failed or timed out, the station runs again with the `## CI` section; past the station's `rounds` in one visit (counted per visit key `after@` plus the latest move or retry), the item blocks. At a merge station, `holdTurns` makes an item with an open after wait its target's turn holder. A dead instance's leased poll is due again once its lease ends, and any instance takes it.

**Reaping.** A claim's box is deleted when the claim ends, however it ends; a goald that dies leaves it behind. Several goald instances may share one sandbox backend (two on a laptop, or one restarted next to another), so no instance removes what another may still be using. `engine.ReapOrphans` lists every box (`Sandboxes.List`) and asks the store which of their runs are over (`Store.RunsOver`, in the organization the box is labelled with); only those boxes are deleted. A run is over once it no longer runs and no longer holds its lease (the lease, fenced by `AcquiredAt`, is the source of truth; checks and a retry run under it after the first run ended, in the box named after it). A succeeded run is not over either while a newer lease holds its item at its station and no newer run of the item started: a claim that resumes it (Lost boxes, below) runs its checks in a new box named after it. Another live instance's runs heartbeat their leases, so they are never over. A dead instance's leases expire and `SweepLeases` requeues them and fails their runs, so any instance reaps their leftovers at its next reap; a run whose lease a person took is over once `FinishLostRuns` cancelled it. Boxes of runs the store does not know (another deployment's on a shared host), of an organization that is not active or of none, and of an organization the store fails to answer for are left alone. `engine.Run` reaps right after its first sweep at startup and then every `ReapEvery` (`LeaseTTL`/2, one minute by default), so a dead instance's orphans go within about `LeaseTTL` + `ReapEvery` of its last heartbeat, and a restarted instance's own earlier orphans the same way (instances keep no identity across restarts). A deleted organization's leftovers from an instance that died before it noticed the deletion stay until removed by hand.

**Lost boxes.** A box lost to its infrastructure (a redeploy of the control Worker, a box restart, a network blip) is not the item's fault. An adapter wraps such a failure in `ports.ErrSandboxLost`: the Cloudflare one for a request the Worker never answered, a 5xx, a 404 on an exec or an attach (the box or its command is gone), a stream still cut after its last attach and the Worker's `the command's outcome is unknown` line; never for a command's own exit, another refusal or a broken protocol. Lost during create, prepare, the agent's exec or a check, the run fails with the reason (a run whose agent had finished keeps its result), the claim deletes the box and records `run_retried {reason, attempt, max}`, waits `engine.Config.TransientBackoff` (15 s, doubling with each loss) in steps of at most `HeartbeatEvery`, heartbeating the lease after each, then runs the item again at the same station in a new box (a fresh prepare; the branch keeps what was pushed). The retry stays inside the claim, under its lease, so no other instance takes the item halfway and the count needs no column; the loss that reaches the line's `board.flow.retry.transient.attempts` (default 3; a definition without the key keeps 3) blocks the item with the last reason (`the sandbox was lost N times: …`), and `run_retried`'s `max` is that setting. A goald restart ends the claim, so its successor counts again from zero. A lost lease, a shutdown or a person's move during the wait ends the claim as during a run. A prepare that exits non-zero or prints no `prepared` line, before the agent starts, is retried the same way: `open` wraps the engine's `errPrepareFailed` around prepare's scrubbed stderr tail, and the claim deletes the box, records `run_retried` and runs again in a new box, counting toward the same limit. Most such failures are the network's (a tool download that timed out, the run bundle fetch from the gateway); one that never passes (a bad tool version, a commit that is gone) blocks after the backoff, at no cost, with `prepare failed N times: …`. A stale draft, a merge conflict (reported in a successful `prepared` line), a create refused without `ErrSandboxLost` and Jonah's try runs keep their own handling. `scrubber.err` keeps both sentinels while scrubbing the message. Agent-caused failures (a worker exit without a result, a timeout, the budget) still block at once, and a broken contract or failed check keeps its one retry. The Docker adapter maps nothing to it yet. A shutdown or unload that cuts a claim after its run succeeded (most often while the station's checks run) does not throw the run away. At the next claim, `ready` looks for a resumable run first (`resumableRun`, `internal/core/engine/resume.go`): the item's latest run, at this station, succeeded, with nothing after its `run_finished` but its own events (no `check_failed`), claims, releases with reason `shutdown` or `unloaded` and lease expiries, and no CI wait holding it. The claim is admitted as usual, and when the head of the item's branch on the code host is still each pushed head of the run (`headsKept`, `CodeHost.BranchHead`), no agent starts: the output is checked against the current line, a leftover box of the run is deleted, and the station's checks run again in a new box prepared under the run's ID with a fresh task token, their events on that run, under the lease's heartbeat (`resume`). On pass the run settles as it would have (`holdForCI`'s after wait, or `finish`). A failed check is the claim's first attempt: the station's agent runs as its second, with the rejection in its brief. A moved head, a head that cannot be read, a box that cannot be opened or a check that cannot be run reuses nothing, and the claim goes on through `ciGate` and the agent as for any claim.

**Weekly budget.** A line whose `runtime.budget.weeklyUsd` is set has its spend read once per tick (`Store.SpendSince(factory, now − 7×24h)`: the cost of the runs started in the rolling window, UTC, no time zone; `dailyUsd` is display-only). At or over the cap (`domain.Runtime.WeeklyBudget`) its agent stations claim nothing, while queue stations still release and human decisions still move; `onExhausted: stop` also cancels the runs this instance has in progress there (a per-run cancel the engine keeps for its own runs), and their items return to their queue with `agent_cancelled {reason: budget}`. Claims resume when the window moves past old runs or a publish raises the cap. It is not an andon pull: nobody clears it. A line without a weekly budget reads nothing. Transitions log `budget_exhausted` / `budget_resumed` (factory, spend, cap, policy) with the gauge `goal_factory_budget_exhausted` (1/0) as an attribute until goald exports OpenTelemetry metrics. Since when a budget is used up is state the screens read, so it lives in PostgreSQL (00134's `factory_budget_exhaustions`, one row per factory under row-level security): the engine marks it with the tick's time when it finds the budget used up (`MarkBudgetExhausted`, `ON CONFLICT DO NOTHING`, so the first since stays whichever instance marks it again) and clears it once the budget has room again, through a lower spend, a raised cap or a removed budget (`ClearBudgetExhausted`). An instance writes when the state differs from what it last wrote, and on the first tick it sees a line, so a restart clears a stale row; a failed write logs `budget_record_failed` and is tried again on the next tick. When the line resumes is computed, never stored: `domain.BudgetResumesAt` over `RunCostsSince` (the start and cost of the runs `SpendSince` sums) returns the earliest start + `BudgetWindow` at which the remaining spend falls below the cap. A spend read that fails skips that line's claims for the tick. Spend is the cost runs record when they finish and nothing is reserved at claim time, so a line can overshoot its cap by at most its agent-station slots × 2 (a run and its retry) × the per-run cap (`perItemUsd`, or an agent's own); D §4.2 has the example. A run whose box was lost (Lost boxes, above) records only what its worker reported before the loss, usually nothing, so a lost run's partial usage may go uncounted, and its retries in new boxes add runs.

**Andon cord.** A person pulls it (`engine.PullAndon`, a reason of 1–500 characters) to stop a factory's line and clears it (`ClearAndon`, an optional note) to restart it; nothing pulls or clears it automatically in 2.2 (the rework-rate pull is later work; the API shows each gate's tally and warning). Each tick reads every running line's open pull (`Store.OpenAndon`) and a stopped line releases and claims nothing; its runs in progress finish and move on, submissions still enter the first station and every human decision still acts. A pull that cannot be read counts as open for that tick. A pause, an open pull and a used-up weekly budget combine without precedence, none lifting another: pause and pull each stop releases and claims, the budget stops claims only, and its stop policy cancels runs even on a paused or stopped line. The pull and the clear log `andon pulled` / `andon cleared` (factory, kind, reason, by).

### One run, end to end

One lifecycle runs every agent run: `engine.RunTask(ctx, domain.RunRequest)` (`internal/core/engine/runtask.go`), from `StartRun` to `Sandbox.Delete` below. A `domain.RunRequest` names the run's organization, factory, version, kind (`domain.RunKind`: `station` or `jonah`), station and item, agent and model, the brief goald adds (`GOAL_FEEDBACK`), the task-token kind the gateway serves its bundle by, the repository to clone, the model key and the agent's environment, and an optional lease to heartbeat. A line's claim runs through it (`runOnce` in `work.go`) under its lease, with a box its attempts share and its output's checks under the same heartbeat. A Jonah run (`kind jonah`, [ADR 0034](../adr/0034-jonah-proposals.md) decision 1) leaves out the lease, the repository clone and the code-host credential, gets only the model key (no environment of the factory's agents), works no item and writes no item events: its run row has no `item_id` (00077), and its agent's events are only logged. `RunRequest.Check` refuses a Jonah request that names any of them (`domain.ErrBadRunRequest`).

A run gets its keys from secrets alone, so its pinned version must be on secrets (`domain.Line.OnSecrets`). A version on secrets ([ADR 0037](../adr/0037-secrets-and-environment-files.md)) has `environments/` or `runtime.modelKey`; its request carries the model key and the agent's environment (its own, or `default`) and no connection. `runEnv` then opens every `{{secret}}` of the model key and of the environment's `env` once, through `OrgSecrets.Resolve`, which checks each scope against the run's factory, writes one `secret.used` per secret and sets `last_used_at`. The agent gets the `env` with each value filled in, whole or part of a value, and the model key in `CLAUDE_CODE_OAUTH_TOKEN` (a value starting `sk-ant-oat`) or `ANTHROPIC_API_KEY`. Every opened value joins the scrub list. A missing secret, one outside its scope, or an environment the version has no file for blocks the item before a box opens, naming the secret or environment and no value. A station run also opens `runtime.repository.token` in the same call and gives it to prepare alone, as `GOAL_REPOSITORY_TOKEN`; the agent gets it only when its environment names the secret too. With `runtime.repositories`, it also opens the token the agent's `code` picks for each entry (`domain.Line.RunCode`), once each, and gives each one to prepare alone as `GOAL_REPOSITORY_TOKEN_<NAME>`; `GOAL_REPOSITORY_TOKEN` then holds the token picked for the item's first repository. The bundle's code fields are in [apps/worker/README.md](../../apps/worker/README.md#prepare-and-the-run-bundle). The bundle's `git_credentials` then has one login for the repository URL's host with `store: true` (user `x-access-token` on GitHub, `oauth2` on GitLab, by `runtime.repository.forge` or the host), and prepare saves it in git's credential store, `~/.git-credentials` with mode 0600, so the clone, a new base branch's push and the agent's own push sign in; the workspace note says git signs in with the repository token. A connection's login keeps the helper that reads its variable and is never written to disk. Jonah and draft-request runs get the model key alone, and the policy's Use credentials `off` empties the environment's `env` but keeps the key and the repository token. A version published before ADR 0037 has neither: its items are blocked with `domain.Line.Refusal`, and a Jonah run, grade, check or draft request of it fails with `domain.ErrNotOnSecrets` before a box opens, opening no connection or credential. On secrets, the environment's `files`, `setup` and `mcp` and the prompt's list of what the box has are not built yet (software#513).

```

### One draft request, end to end

A draft request ([ADR 0021](../adr/0021-asked-definition-changes-draft-requests.md)) runs in a box with no repository and no item. What is built is the box half: `engine.(*Engine).RunDefinition` (`internal/core/engine/definitionrun.go`, the port `ports.DefinitionRunner`) and the gateway's definition bundle. The loop that claims a queued request, keeps its lease, writes the result into the draft and finishes the request is not built yet, so nothing calls `RunDefinition` today.

```
RunDefinition(request, draft revision)   ctx in the request's organization, its factory's loaded line
  weekly budget used up    → ports.ErrBudgetExhausted, no box
  resolve runtime.modelConnection alone   no repository, git login, agent connection or agent credential
  task token               kind draft_request: the line's version, the request id and the draft revision,
                           no item, station or connection (domain.TaskClaims.checkKind refuses them)
  Sandboxes.Create         run id = request id, empty item and station, deadline task timeout + lease TTL
  exec goal-agent prepare  env GOAL_GATEWAY_TOKEN only: GET /run → the definition bundle
                           (spec.draft_request, definition.files = every draft file, no repository,
                           git_credentials [] and tools []); 409 once the draft moved past the revision,
                           which RunDefinition returns wrapping ports.ErrConflict
  exec goal-agent run      env the model key's alone (no GOAL_GATEWAY_TOKEN: definition mode has no MCP)
  finished line            → DefinitionResult: summary, changed (path, sha256, content), deleted, rejected,
                           cost_usd, turns; failed with the scrubbed error when the worker failed, and
                           failed when a changed file holds a secret value of the run
  Sandbox.Delete           on every path; the reaper never sees the box (its run id is not an agent run),
                           so the sandbox deadline is the only backstop after a crash
```

A draft-request token gets only its bundle: the notes, tool-approval and MCP endpoints answer 403. The gateway reads the request through `gateway.DraftRequests` (`ports.DraftRequests`) and the draft through `gateway.Drafts` (`ports.DefinitionStore`'s `Draft` and `Blob`), which `cmd/goald` wires; it never writes a draft.

### Identity and access (phase 3, as built)

[Phase 3](../history/specs/3-identity-and-access.md) and [ADR 0007](../adr/0007-identity-better-auth.md) add people. Sign-in is on by default (`GOAL_AUTH=session`, `defaultAuth` in `cmd/goald/settings.go`, which `goal up` follows).

- **Two processes, one origin.** `apps/auth/` (Node 22, Hono + Better Auth pinned exactly, four plugins: email one-time codes, organizations with members and invitations, the device flow for `goal login`, bearer; Google optional) listens on loopback (`GOAL_AUTH_LISTEN`, default `127.0.0.1:8081`) beside goald on a laptop (`goal up` runs `node apps/auth/dist/server.js` and Mailpit), and on every interface of a container of its own on Cloudflare (4-21), which only goald reaches, as `http://auth.internal` through the control Worker. goald serves everything on `GOAL_PUBLIC_URL` and `api.AuthProxy` forwards an exact allowlist of Better Auth paths under `/api/auth/*` to `GOAL_AUTH_UPSTREAM` (forwarding headers dropped, `X-Goal-Client-Ip` written by goald from `GOAL_TRUSTED_PROXIES`, `X-Goal-Proxy-Secret` with `GOAL_AUTH_PROXY_SECRET`, without which the service answers nothing but its health check, encoded and unclean paths refused, 64 KiB, timeouts and 503 `auth-unavailable`, `Set-Auth-Token` stripped, Goal bearers answered 401 and never forwarded, no secrets in its log). The organization paths Better Auth would own (`/organization/create`, `/update`, `/delete`) are disabled in it. Its origin and CSRF checks are on whatever `NODE_ENV` says. The SPA gets a Content-Security-Policy (`apps/web/csp.txt`).
- **Credentials, checked in PostgreSQL per request.** `credential.go` reads a bearer value (an API key `goal_sk_…`, a personal token `goal_pat_…`, or the Better Auth session token `goal login` holds) or else the session cookie of the install's scheme (`goal.session_token`, `__Secure-` over https); an agent's task token, or anything else, is 401. `postgres.Identity` resolves it through `SECURITY DEFINER` functions (`goal_principal`, `goal_api_key`, `goal_personal_token`) for the path's organization: the user or key, the session times, the org role and factory roles, a key's scopes, ceiling and factories, a token's scopes. No JWT and no cache: a removal, demotion, revocation or expiry applies on the next request, and streams end on `goal_access` notices, at expiry and on resync. goald holds no Better Auth secret.
- **Authorization from one table.** `contracts/api/permissions.yaml` defines every permission (who holds it, whether keys may, whether a personal token may (`pat`), whether it needs a sign-in within 10 minutes); `tools/permgen` generates goald's table and `apps/auth/src/access.gen.ts`, and each OpenAPI operation names its permission in `x-goal-scope`. `api.Permissions` checks a personal token's scopes first and fails closed, then membership and visibility, then roles, a key's scopes and ceiling, and the fresh rule (403 `reauth-required`; never for a token, which gets `forbidden`); a factory permission's fresh rule is asked only in the resolver's pass, after the factory's visibility, so an invisible factory stays the unknown one's 404. Owners and admins hold every factory permission; members only what their factory roles (viewer ⊂ approver ⊂ editor) give. Unknown or invisible organizations, factories and items are the unknown one's 404; missing credentials 401; missing permissions 403. `internal/api/testdata/access.golden` records every operation's answer for every kind of principal in two organizations.
- **Keys and personal tokens.** An API key is an organization's service account (`service:<key id>`, "<name> (API key)"), within its creator's rights and a role ceiling, optionally restricted to factories, ≤ 90 days. A personal token is a member's own credential in one organization, at most the owner's current roles ∩ its scopes, never fresh, never platform admin, created only from a fresh browser session (403 `browser-session-required` otherwise); its writes record `via: pat:<id>`. Both are shown once (`Cache-Control: no-store`), stored as SHA-256, revoked at once, and refused at `/api/auth` and at the gateway.
- **Ownership of data.** Better Auth's tables live in schema `auth` (generated SQL committed as goose migrations `00040`–`00041`; `task auth:schema-check` fails on drift; `auth migrate` is never run), written only by the role `goal_auth`; `goal_app` reads them only through definer functions. goald alone creates, renames, deletes and purges organizations (both rows in one transaction, `goal_provision_org`); any person signed in with a session creates them and becomes the owner, but no API key or personal token does ([ADR 0032](../adr/0032-self-serve-onboarding.md)). Factory roles, API keys and personal tokens are Goal tables under RLS. Membership changes reach `audit_log` through triggers with the actor the auth service stamps from the session; sign-ins, codes and device approvals go to the install's `auth_events` (`goal admin events`), cleaned daily by `goal.auth.cleanup` under an advisory lock.
- **Bootstrap and recovery.** While no user exists only `GOAL_BOOTSTRAP_OWNER_EMAIL` may sign in; that first user becomes a platform admin and owner of every live organization (`goal_claim_bootstrap`). Rows from before sign-in keep `user:local` and read "Local user (before sign-in)". `goal db recover-admin <email>` and `recover-owner <org> <email>` need only the database (goald may be stopped), create the user if needed and are audited.
- **Who may sign up.** One gate creates users, for codes and Google alike: `allowOnlyInvitedOrBootstrap` in `apps/auth/src/signin.ts`, Better Auth's user-create `before` hook. It admits a verified email with a pending, unexpired invitation to a live organization (`goal_is_invitee`), then the bootstrap owner's email while no user exists, then an email exactly at a live organization's sign-up domain (`goal_signup_domain_org`, [ADR 0023](../adr/0023-notifications-and-sign-up-by-domain.md) decision 7: no subdomains, never a domain of `public_email_domains`), and refuses and logs (`sign_up.refused`) everyone else; only those addresses are sent codes. The user-create `after` hook (`recordUser`) then joins a domain sign-up through `goal_apply_signup_domain`: an organization `member` with the domain's join role on every factory that exists then, audited as `member.added` and `factory_role.granted` with `via: signup-domain`; an invitee of that organization is left to their invitation. The setting is `org_signup_domains` (one row per organization, under RLS), shown on `GET /v1/orgs/{org}/settings` and changed only by an owner with a fresh sign-in (`org:signup_domain`, `PUT`/`DELETE /v1/orgs/{org}/settings/signup-domain`) through `goal_set_signup_domain`, which accepts only the domain of the owner's own sign-in email, refuses webmail domains and another live organization's domain, and takes over a deleted organization's.
- **Logs.** One `api request` line per `/v1` request names its principal and credential by id (`user:<id>`, `service:<key id>`, `pat:<id>`, `key:<id>`) with its operation, status, organization and request id, never a path, cookie, token or email; refused keys and tokens are counted (`goal_api_key_verifications_total`), not written to `auth_events`.
- **Fail closed.** `GOAL_AUTH=none` (the single local user, everything allowed) is chosen explicitly, only for a loopback listen, and warns at startup that every request, agents' included, is the local user; it never comes from an invalid credential. A non-loopback listen needs `session`, an https `GOAL_PUBLIC_URL` and a separate listener that serves only the agents' `/mcp` gateway, whose task tokens carry `aud: goal-gateway` and are accepted nowhere else. Under `session` goald refuses to start unless the identity self-check passes, and, without stopping, follows the auth service from its start: it logs that it waits for it, warns only when it still does not answer after 30 seconds (signed-in people keep working through an auth outage), and once it answers logs who signs in first while nobody has. `goal up` starts the auth service again, with a backoff, when it stops by itself. `goal up` refuses, before it starts goald or the auth service, without `BETTER_AUTH_SECRET` (distinct from `GOAL_GATEWAY_KEY`), without `GOAL_BOOTSTRAP_OWNER_EMAIL` while nobody has signed in, or without the auth service's build, naming `GOAL_AUTH=none` as the way to keep the local user. A `Host` other than the public URL's is refused (DNS rebinding). goald and the auth service each get only their own variables, and goald's reserved list keeps the auth service's, `GOAL_API_KEY` and `GOAL_DATABASE_ADMIN_URL` out of factory definitions. The threat model with the test of each control is spec 3 §11.1; dependency policy and the patch SLA are in `SECURITY.md`.

### Jonah: learning from the line (as built)

Jonah ([ADR 0039](../adr/0039-jonah-learns-from-the-line.md), which builds on [ADR 0034](../adr/0034-jonah-proposals.md) and replaces the retro runs of the [phase 5 plan](../history/specs/5-continuous-learning.md)) has four parts. Each is a loop or a read in goald over ports; `internal/jonah` is a goald loop, not a service, and none of it changes a definition without a person. The product view is the docs site's Jonah concept page (`apps/docs/src/content/docs/concepts/jonah.md`).

- **The evidence builder** (decisions 1 and 2). `domain.BuildEvidence` (`internal/core/domain/evidence.go`) writes the evidence folder, `items/<number>.md`, `README.md` and `versions.md`, with no I/O and no model call. Its comment lists the event kinds that make an item evidence and defines a gate and person disagreement. `internal/gateway/jonah.go` (`jonahEvidence`) feeds it from `JonahStore.EvidenceItems` over the review's window (milestone events only, never `domain.PerTurnKinds`), `StationRunMedians` over the 30 days before the window's end (`domain.EvidenceMedianWindow`; an outlier is `domain.OutlierFactor`, three times a median) and the factory's latest versions, and serves it under `evidence/` of a jonah token's bundle ("Jonah reviews" under [MCP gateway](#mcp-gateway)).
- **The review box** (decisions 3 to 7). `Reviews.Sweep` (`internal/jonah/reviews.go`) queues one review a day for each factory with Jonah on and new evidence, at an hour set by its id, and the API queues a manual one. `Reviews.Work` claims a review under a lease and makes one `engine.RunTask` of kind `jonah` (`domain.TaskKindJonah`): a small box with no item, repository, secret or MCP server, the model key only, and goal-agent's jonah mode (`apps/worker/src/jonah.ts`), which allows Read, Grep and Glob inside the box and nothing else, at most 40 turns, under the review's cap from `JonahPolicy.Budget`. The reply is checked before anything is stored (`internal/jonah/review_output.go`): edits outside the allowlist (`internal/jonah/allowlist.go`, `domain.ProposalPathAllowed`) or that do not apply or validate drop their proposal with `jonah proposal dropped`, and memory facts that do not quote a person's event word for word drop with `jonah fact dropped` (`internal/jonah/memory.go` checks them). Deciding a proposal is `jonah.Decider` (`internal/jonah/decide.go`).
- **The try loop** (decisions 8 to 13). `Tries.Sweep` (`internal/jonah/tries.go`) queues each new proposal's tries once, all or none, through `ports.PastTries`: one per cited item at the stations it reaches whose agent `domain.Line.TriableAgent` accepts, at most `domain.MaxPastTryItems` newest first, plus one of each kept test there (`ports.KeptTests`). A model proposal (`internal/jonah/modelproposal.go`) queues its own tries, three per item, when it is written. `Tries.Work` claims them fairly across organizations, none for a factory whose Jonah budget is used or that has an item waiting at an agent station, and at most `GOAL_JONAH_TRIES_PER_FACTORY` running per factory. Each try is a `RunTask` of kind `try` (`domain.RunKindTry`, bundle `domain.TaskKindTry`) on the item's recorded brief and commit, in a box with only the model key; an infrastructure failure or a commit that is gone is `error`. Code grades first: the station's contract, as the proposal changes it, and its checks. `jonah.TriedOf` (`internal/jonah/tried.go`) summarises a proposal's tries for the API. Try again (`internal/jonah/tryagain.go`) adds attempts, and `jonah.KeptDrafts` (`internal/jonah/keptdraft.go`) queues the kept tests a draft reaches when the publish dialog opens, reusing a try of the same content key.
- **The watch** (decisions 14 and 15). `Watcher.Sweep` (`internal/jonah/watch.go`) recomputes, every 15 minutes (`watchEvery` in `cmd/goald/jonah.go`) under the schedule lock, the watch of each published version at each station it reaches: a proposal's own number, or a person's publish's send-back rate and cost per item. Outcomes come from `ports.Watches.StationOutcomes`, each credited to the version of the run at that station. The interval and the verdict are `domain.Watch` (`internal/core/domain/watch.go`); a watch closes at `domain.WatchMaxAge` (14 days) or `domain.WatchMaxItems` (150), and the sweep is idempotent. `WorseProposalWatches` feeds Needs you, and Undo this change is `Decider`'s reversed replacements as a new proposal.

Every part spends Jonah's budget, `learning.jonah.share` of the line's last 7 days (`JonahPolicy.Budget`, `JonahStore.JonahSpendSince`), and none of it counts toward `runtime.budget.weeklyUsd`.

### Migrations and tenancy

- **Tenancy.** The organization is the tenant boundary. Every org-owned table carries `org_id uuid NOT NULL` referencing `organizations(id)` and has row-level security: `USING` and `WITH CHECK (org_id = current_setting('goal.org_id')::uuid)`. goald connects as `goal_app` (no BYPASSRLS), migrations run as `goal_owner`, and each request or engine transaction runs `SET LOCAL goal.org_id`. `TestSchema_EveryOrgTableHasRLS` checks it.
- **Numbering.** Migrations are forward-only goose files in `db/migrations/`. A new file takes the highest number there plus one, named `NNNNN_what_it_does.sql`. goose refuses a number below one already applied, so the gaps below the highest number (`00008–00009`, `00012–00029`, `00034`) are retired and never used. Never edit or renumber an applied file. Two files never share a version: `TestFS_VersionsAreUnique` (`db/migrations/migrations_test.go`, run by `task test`) rejects a reused one, so a branch that takes a number main already has fails its own checks after a rebase. The phases' old number ranges are in git history (`docs/history/specs/README.md` before it was cut to one line).
- **Intake triggers (00071).** `webhook_endpoints` (id, the address `/hooks/{id}`; factory, name unique per factory, kind, the sealed secret as `key_id`, `nonce`, `ciphertext`, `created_at`, `rotated_at`), `webhook_deliveries` (endpoint, `received_at`, `headers` jsonb whose CHECK refuses `x-goal-signature`, `x-hub-signature-256` and `x-hub-signature`, `body` up to 1 MiB, `outcome` refused, accepted or created, `reason`, `item_id`; indexed on (endpoint, `received_at` DESC); deleted after 30 days by `goal_prune_webhook_deliveries`, which goald's schedule job calls) and `trigger_firings` (factory, trigger, source schedule, webhook or github, `event_key`, `idempotency_key` unique per (factory, trigger), `dedupe`, outcome created or skipped, `reason`, `item_id`, `at`). All three are org rows under row-level security with composite keys to their factory and item; goal_app may only rotate an endpoint's secret and never change or delete a delivery or a firing. `goal_webhook_endpoint_org` maps an endpoint id to its organization. `work_items` gains `trigger` (the trigger that created the item) and `source` (people, cli, api, schedule, webhook, github), NULL until the item's creator passes them in `domain.NewItem`.
- **Organization webhooks (00115, ADR 0040 decisions 12 and 15).** A `webhook_endpoints` row with a null `factory_id` is the organization's webhook: its name is unique in the organization (a partial unique index) and none of the sender names, `schedule` or `webhook` (a CHECK); it has `sender` (`github`, `gitlab`, `standard`, `pagerduty`, `sentry`, `token`), `secret_id` (a foreign key to `secrets` with `ON UPDATE CASCADE` and NO ACTION on delete, so a used secret is not deleted alone and an organization's purge removes both), `enabled` and the token sender's `token_header`, `token_event_path` and `token_id_path`; `kind` and the sealed `key_id`, `nonce` and `ciphertext` become nullable, all three set or none. `webhook_openings` (webhook, factory, `repositories` or null for every one) is an org row under row-level security. `secrets` gains `previous_key_id`, `previous_nonce`, `previous_ciphertext` and `previous_until`: a replace of a secret a webhook uses keeps the old sealed value for 24 hours; `goal db rekey` reseals it and drops lapsed ones. `goal_connection_key_ids()` lists the previous key ids and skips null endpoint key ids. goal_app may update an endpoint's `name` and `enabled` and an opening's `repositories`.
- **The webhook receiver (00118, ADR 0040 decisions 12 and 13).** `webhook_deliveries` gains `delivery_id` (1 to 200 characters, unique per (organization, endpoint); null for a refused delivery and for rows recorded before the receiver), `event`, `receipt` (`accepted`, `duplicate`, `refused`; null for the older rows) and `duplicates`, the only column goal_app may update; a refused row has no id, event or body, and the headers CHECK refuses every sender's signature or token header (`x-hub-signature-256`, `x-hub-signature`, `x-goal-signature`, `x-gitlab-token`, `webhook-signature`, `x-pagerduty-signature`, `sentry-hook-signature`, `authorization`). `webhook_delivery_ids` is the ledger: every accepted delivery id of a webhook with its `received_at`, primary key (organization, webhook, id), without bodies, kept a year (goal_app may select, insert and delete). `webhook_delivery_counts` counts per webhook and UTC day the accepted deliveries no enabled trigger named, which keep no row (goal_app may select, insert and update `count`). Both are org rows under row-level security with a foreign key to their webhook. `goal_prune_webhook_ledger` deletes the ledger ids and the counts older than an instant across organizations, as goald's schedule job does with a year.
- **Intake triggers in the engine (ADR 0026).** `config.Factory.Line` carries `board.triggers` as `domain.Line.Triggers`. `Engine.Intake(ctx, domain.IntakeEvent)` hands an event (factory, source, event key, fields by dotted name, changed paths, author, bot, idempotency key) to the factory's current line and returns one `domain.TriggerFiring` per trigger it reached, for the webhook part to log: every enabled trigger whose `on` equals the key (or, for `webhook.<endpoint>`, prefixes it up to a dot) and whose filter matches (`domain.Trigger.Matches`; schedule triggers never match an event). A firing already recorded for the trigger and idempotency key is returned as it is and nothing is created. Otherwise the checks run in order and the first that fails records a skipped firing whose reason starts with its step: `only.failuresInARow` n (`FailureStreak`, the trigger's firings with the event's dedupe value since its newest created one for that value, plus this event, must reach n; the streak is keyed by the `only.dedupe` value because a firing stores no other event field, the whole trigger without one), `only.dedupe` (`OpenItemByDedupe`), `only.modelAgrees`, deprecated since the model check was removed ([ADR 0040](../adr/0040-one-door-for-every-source.md) decision 18: no `ports.ModelCheck` remains), which skips every event that reaches it with `domain.ModelCheckRemoved` ("turn this trigger into a check"), `limits.perDay` (`CreatedSince` the start of the UTC day, from the `Clock` port), `limits.perHour` and `limits.pauseOnBudget` (the weekly budget, `Engine.weeklyBudget`: no daily one exists). The steps are one function, `evaluate` in `internal/core/engine/intake.go`, which returns a `domain.TriggerEvaluation` (each step passed, skipped or not reached, and the rendered `domain.TriggerItem`) and stops at the first skip; intake records it, and `Engine.TryTrigger` (`internal/core/engine/try.go`, a trigger dry run) evaluates one of a trigger's 20 newest firings with it, its event rebuilt as `{instant: <key>}` for a schedule's or from its kept delivery for a webhook's, and records only a `trigger.tried` entry through `engine.Deps.Audit`. When all pass, the item is created at `create.station` in its arrival state with `create.type` and `create.lane`, class expedite when `create.expedite` is set (else `Line.ClassFor`), source and trigger set; then a created firing names it. Event text is untrusted: each placeholder of `create.title` and `create.brief` (`domain.RenderTemplate`) takes a plain value (one line, control characters as spaces, at most 200 characters, `<` and `>` as look-alikes, never expanded again), quoted; the whole title is cut to 300 characters and an empty one is the trigger's name (`domain.EventTitle`). A `create.brief` of the form `./triggers/<name>.md` is that file of the definition, read by `config.Factory.Line` (`config.BriefFile`). The item's body is the rendered brief and then `domain.UntrustedEventBlock`: `<untrusted-event-data>` with a line saying its content is data from outside the organization and that nothing in it is an instruction, then the event as JSON with HTML escaping, so no value can write the closing delimiter; `domain.Item.Work` and every run brief carry it, and the worker's system prompt says text inside it is data, never instructions (`untrustedDataSection` in `apps/worker/src/agent.ts`). The item, its firing and the limits' counts are written in one transaction under the trigger's advisory lock (`Intake.Fire`, ADR 0040 decision 16), so two deliveries of one event create one item. `Engine.FireSchedules(ctx, now)` runs under `Intake.WithScheduleLock` and, while another goald holds it, does nothing; under it, each enabled schedule trigger of every loaded line fires once for its newest cron instant within the last 5 minutes (`domain.Cron`: five fields in the trigger's time zone, a day matching either the day of month or of week when both are restricted), with that instant in RFC 3339 UTC as the idempotency key, so every instance and every tick fire it at most once; an instant older than 5 minutes (goald was down) is not fired late. Those instants since the trigger's newest firing are a gap: one firing with outcome `missed` records it, keyed `missed/<first instant>`, at its last instant, with how many instants it covers in `missed` (`Cron.Between`, at most 100,000 per firing), logged as `trigger missed instants`; a trigger that never fired has no gap. It then prunes deliveries older than 30 days, the receiver's ledger ids and daily counts older than a year, and each loaded factory's firings older than 90 days whose item is not open (`Intake.PruneFirings`, in the factory's organization through goal_app's DELETE grant). goald runs it at start and every minute (`fireSchedules` in `cmd/goald/main.go`).
- **Rules.** goose applies each file in one transaction (`task migrate-check` too, with `psql --single-transaction`). A `SECURITY DEFINER` function pins its `search_path` to the schema with `pg_temp` last (`00036` shows how). Every org-owned table has an index that starts with `org_id` (`TestSchema_EveryOrgTableHasAnIndexOnOrgID`). A new constraint on a large table is added `NOT VALID` and then validated.

## Scale and failure

| Concern | Approach |
| --- | --- |
| Horizontal scale | `goald` is stateless; run N instances behind a load balancer. |
| Work distribution | Each instance claims items with `FOR UPDATE SKIP LOCKED`; leases with heartbeats; expired leases return to the queue. |
| Singletons | Constraint detection, intake schedules and Jonah's sweeps run under `pg_try_advisory_lock(<job key>)`, so exactly one instance runs each. Jonah's review sweep, try sweep and watch sweep take `Intake.WithScheduleLock`; the queued reviews and tries are claimed under leases on every goald. Intake schedules are built: `Engine.FireSchedules` under `Intake.WithScheduleLock`, a session lock on a direct connection, and idempotent on (trigger, instant) besides. So is the daily digest: each round of `notify.DigestJob` runs under `Digests.WithDigestLock`, the same kind of lock, and the `digests` table's unique key on (person, local date, channel, organization) makes it idempotent besides. |
| Realtime | Each instance `LISTEN`s on `goal_events` and streams to its own SSE clients; no sticky sessions needed. |
| Idempotency | Every engine step is keyed by (item, station, attempt) and safe to retry. |
| Connections | `pgxpool` per instance; RDS Proxy or PgBouncer in transaction mode when instances × pool size grows. |
| Event volume | `item_events` is append-only; partition by month when it passes ~50 M rows. |
| IDs | Generated in Go as UUIDv7, so the schema works on managed PostgreSQL versions without `uuidv7()`; the column default is a convenience for manual SQL only. |
| Shutdown | SIGTERM stops claiming, finishes or releases leases, then exits within the platform's grace period. |
| Observability | Structured `slog` JSON to stdout, OpenTelemetry traces and metrics; Claude Code's OTel events are joined to item traces. |
