## Workspaces and state

- One root module (`deploy/terraform/`), one Terraform CLI workspace: `production`. A workspace without a key in `local.environments` fails every plan, so nothing is created in `default` by mistake.
- State: `s3://goal-terraform-state/env:/production/terraform.tfstate` in R2 (the s3 backend, `use_lockfile = true`). It holds every secret in plain text, the generated ones only there (Secrets Store values are write-only at Cloudflare), and also the master keys (the SOPS data source and the store secrets' values are saved in it) and goal db init's administrator URL (BYPASSRLS, CREATEROLE): **the state bucket is as sensitive as the master key**, since with the two together every organization's credentials can be decrypted. The bucket and its token are the operator's alone: a token of its own (neither the Cloudflare API token nor goald's R2 token), Object Read & Write on `goal-terraform-state` only, with an expiry (renew it rather than keep a long-lived one), kept in the password manager and exported only for the shell that runs Terraform, never into `.env`. Revoke it at once if it may have leaked, then rotate every secret (Other rotations) and the master key.
- Before every plan, apply, import or state command: confirm the directory is `deploy/terraform/` and `terraform workspace show` says `production`. The `tf:*` tasks select and check it for you.
- Never copy state between workspaces, never edit it by hand, never delete a workspace. Adopt an existing object with an `import {}` block, never by deleting and recreating it; delete the block after the apply that used it and note it in the commit (the branch's block in `database.tf` went after the bootstrap's apply; Restore says when to put it back).
- Never commit state, plans, `*.tfvars`, `override.tf` or a decrypted secrets file (`.gitignore` keeps them out). Commit `.terraform.lock.hcl` only when a provider change is intended (`terraform providers lock -platform=darwin_arm64 -platform=darwin_amd64 -platform=linux_amd64 -platform=linux_arm64`); the tasks init with `-lockfile=readonly`.

### GitHub environments (ADR 0010)

The workflows that plan and apply `deploy/terraform/` run the same `task tf:plan` and `task tf:apply`, with `GITHUB_ACTIONS=true` and credentials from one GitHub environment of `byFrederick/goal`, `production`, used by both the pull request plan and the apply on merge. Its secrets are the operator's existing credentials (Credentials, above): the same write tokens the laptop uses. Any branch pushed to this repository can change a pull request's workflow and so read and use them: the state token reads every platform secret, the age key opens the master keys, and the Cloudflare, PlanetScale and Google credentials can change production. The owner accepted this on 2026-10-25 (ADR 0010, amendment) because only the owner and the factory push branches here; a fork's pull request gets no secrets. Revoking one of these credentials breaks the laptop too: renew it in both places.

Optional required reviewers (the owner). | [`.github/workflows/terraform-plan.yml`](../../.github/workflows/terraform-plan.yml): the plan of a pull request from this repository, never a fork: `task tf:check`, then `task tf:plan -- -lock=false -input=false -no-color` (by choice: a pull request's plan never holds the state lock against an apply). **The plan workflow.** `.github/workflows/terraform-plan.yml` runs on every pull request that changes `deploy/terraform/` or the workflow itself, only when the pull request's branch is in this repository (a fork's gets no job and no secrets; a maintainer pushes its change to a branch here). Its one job, in `production`, runs `task tf:check`, takes Google's token (below), writes `SOPS_AGE_KEY` to a mode-0600 file under `$RUNNER_TEMP` for `SOPS_AGE_KEY_FILE`, and runs `task tf:plan -- -lock=false -input=false -no-color`. It posts the result as **one** pull request comment, marked `<!-- goal:terraform-plan -->`, that every push edits (never a new comment per push): the commit, the plan's summary line and the plan in a collapsible block, truncated with a note past GitHub's comment limit (the whole plan stays in the run's log). A failed check or plan replaces the comment's content with what failed and fails the job; a newer push cancels the plan in flight. Its token adds only `id-token: write` (the OIDC exchange) and `pull-requests: write` (the comment). Because any branch here can rewrite this workflow and read `production`'s write secrets (ADR 0010, The risk we accept), the owner may set **required reviewers** on `production` (Settings › Environments): each plan job then waits for a person's approval before it receives the credentials.

Google needs no secret: the workflow's `google-github-actions/auth` step (`workload_identity_provider`, `service_account`, `token_format: access_token`) exchanges the job's OIDC token for the service account's access token (a masked step output, valid one hour), which the workflow passes to the `tf:*` steps as `GOOGLE_OAUTH_ACCESS_TOKEN`. Both values are environment **variables**, not secrets, from `terraform output`: `GOAL_GCP_WORKLOAD_IDENTITY_PROVIDER` (`ci_workload_identity_provider`) and `GOAL_GCP_SERVICE_ACCOUNT` (`ci_apply_service_account`). The provider admits a token only from this repository (by repository and owner id) and its `production` environment, which alone can impersonate `terraform-apply`.

No secret reaches a log: GitHub masks every environment secret in the job's output, the tasks pass them only as environment variables, and plans show sensitive values as `(sensitive value)`. Never `terraform output -raw`, `sops decrypt` or `env` in a workflow.

**Identifiers in the repository are not credentials.** The account id (in `GOAL_S3_ENDPOINT` and `GOAL_EMBED_URL`) and the Secrets Store id (every `store_id`) in `deploy/cloudflare/wrangler.jsonc`, the zone and host `goal.byfrederick.work`, the PlanetScale organization, the Google project id and the age recipient in `.sops.yaml` are committed on purpose: each is useless without one of the credentials above, and Cloudflare calls its account and zone ids non-secret values for a Wrangler config's `vars`. Anything that grants access stays out: the history scan and its allowlist are in [public-readiness.md](public-readiness.md) (`gitleaks git --redact --log-opts=--all .` reads `.gitleaks.toml` and reports no leaks).

## Secrets

Every secret comes from the one place that makes it, and nobody copies one by hand. `deploy/terraform/secrets.tf` maps each into one Secrets Store secret, named by the environment variable its consumers read, and `local.secret_consumers` says which container gets which; the plan fails when a secret has no consumer or a consumer names a missing one (`terraform test` checks both, and each container's set).

| Secret | Made by | Consumers |
| --- | --- | --- |
| `GOAL_MASTER_KEYS` | the operator, SOPS `master_key` (`k1:$(openssl rand -base64 32)`; escrow first, below) | goald |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Google's console (bootstrap step 5), SOPS `google` | auth |
| `GOAL_SMTP_URL` | the mail provider (`smtps://<user>:<password>@<host>:465`), SOPS `smtp`; optional, see Sign-in methods | auth |
| `GOAL_GATEWAY_KEY`, `GOAL_SANDBOX_KEY`, `GOAL_AUTH_PROXY_SECRET`, `BETTER_AUTH_SECRET` | `random_password` | goald; goald and the Worker; goald and auth; auth |
| `GOAL_S3_ACCESS_KEY`, `GOAL_S3_SECRET_KEY` | the R2 account token: its id, and the SHA-256 of its value | goald |
| `GOAL_EMBED_KEY` | the Workers AI account token | goald |
| `GOAL_DATABASE_URL`, `GOAL_MIGRATE_DATABASE_URL` | `modules/database-urls` | goald |
| `GOAL_AUTH_DATABASE_URL` | `modules/database-urls` | auth |

`goal db init`'s administrator URL (`GOAL_DATABASE_ADMIN_URL`: BYPASSRLS, CREATEROLE) and the role passwords (`GOAL_PG_OWNER_PASSWORD`, `GOAL_PG_APP_PASSWORD`, `GOAL_PG_AUTH_PASSWORD`; the PlanetScale role and `random_password`) are not store secrets: nothing on Cloudflare runs `goal db init`, and the store is account-wide, so any other Worker of the account (or a token that may edit Workers scripts) could bind one. They are sensitive Terraform outputs that only `task db:production` reads. A Cloudflare-side `goal db init` runner, if one is ever built, adds them back with that runner as their one consumer.

The master keys stay in SOPS, not `random_password`, on purpose: they must be escrowed outside the state (losing them loses every organization's credentials), they rotate as a list (`k2:<new>,k1:<old>`, then `goal db rekey`), and a generated one would be replaced, with no way back, by any `-replace` or recreation of its resource. Everything else Goal can make again: a lost generated secret is rotated, not recovered.

The URLs follow prototype 4-2 (`modules/database-urls`): port 5432 (never PgBouncer's 6432, which drops notifications and session advisory locks), the PostgreSQL database `goal`, users `<role>.<branch-id>` with the branch id of the administrator's user name, `sslmode=verify-full&sslrootcert=system` for goald and goal db init (pgx; goald's image carries a CA bundle), `sslmode=verify-full` alone for the auth service (node-postgres reads `sslrootcert` as a file), goald's pool capped at `pool_max_conns=8` (PS-5 leaves 22 connections: goald's pool and listeners, auth's pool of 10, migrations), passwords URL-encoded.

`deploy/terraform/secrets/production.sops.yaml` is committed, encrypted with age to `age1kttpj5ev6g08st6s20nezlqjdaa75l30z08nxhudpe2eapcv7fwqsv47mz` (`.sops.yaml`); keys stay readable, values are encrypted. The plan refuses any value still empty, but the SMTP URL.

**Sign-in methods.** The install signs in with Google only for now: it has no mail server, `smtp.GOAL_SMTP_URL` stays empty, so Terraform makes no `GOAL_SMTP_URL` store secret and gives the auth service none (`secret_consumers`), and the wrangler config sets `GOAL_AUTH_EMAIL=off` (goald and the auth service: no email codes, the sign-in page shows Google alone, invitations are made but mailed to nobody, so tell an invitee to sign in with Google at `https://goal.byfrederick.work` with the invited address). The bootstrap owner signs in with Google too. To add email codes later: the SMTP URL into `smtp` (`task secrets:edit`), `task tf:apply -- -target=module.secrets`, then in the wrangler config `GOAL_AUTH_EMAIL` on, a `GOAL_SMTP_FROM` var (`Goal <goal@byfrederick.work>`) and the `GOAL_SMTP_URL` binding (`goal-production-GOAL_SMTP_URL`), and redeploy (its config test then needs the same change).

| Task | What |
| --- | --- |
| `task secrets:edit` | `sops edit` in `$EDITOR`, decrypted in memory only. Preferred. |
| `task secrets:decrypt` / `task secrets:encrypt` | For bulk edits: a mode-0600 `production.decrypted.yaml` (git-ignored), encrypted back over the SOPS file through a temporary file, then deleted. |
| `task db:production -- <command>` | `goal db <command>` (init, migrate, rekey, recover-admin, recover-owner) on the install's database: the administrator's URL, goal_owner's URL and the role passwords from the state (`terraform output -raw`), the master keys from SOPS, in its environment only. |

Rules: never `sops decrypt` or `terraform output -raw` to the terminal; after every SOPS edit `git diff` the file and check only the keys you meant changed; a value that leaked is rotated at its source first, then here. To add a secret: make it in Terraform when Goal can generate it, in SOPS only when it comes from outside; then a line in `local.secret_values`, its consumers in `local.secret_consumers`, the binding in the wrangler config.

## Bootstrap (first install)

**Done for `goal.byfrederick.work` on 2026-10-25** (Workers Paid with R2; every step below, each one's outcome in *Done:*). The steps stay for a reinstall or a new account; a reinstall first puts the branch's `import` block back (Restore).

1. **Hand-made prerequisites.** The state bucket: dashboard › R2 (or `wrangler r2 bucket create goal-terraform-state --location enam`), then an R2 API token with Object Read & Write on that bucket only (`GOAL_TF_STATE_*`). The Cloudflare API token and the PlanetScale service token of the table above. Terraform never creates or manages the state bucket.
2. **Secrets Store.** The account has exactly one store; if Secrets Store was never opened, create it once (dashboard › Secrets Store, or `wrangler secrets-store store create default --remote`). Terraform reads it and adds only Goal's secrets.
3. **What needs no outside value.** `task tf:plan -- -target=cloudflare_r2_bucket.main -target=google_project.sign_in -target=planetscale_postgres_branch_role.admin -target=random_password.generated`: the branch shows as an import with no changes (if not, stop: the configuration differs from the live branch), the rest as creates. Then `task tf:apply` with the same targets. Targeting skips the store secrets, whose SOPS values do not exist yet. If `goal-byfrederick` is taken (project ids are global), change `google_project_id` in `deploy/terraform/locals.tf` first. The project keeps `auto_create_network = true`: with no billing account the Compute API is off, and turning it off would need it. *Done:* `goal-production`, `goal-byfrederick`, `goal_db_admin`, the generated passwords; the branch imported with no changes.
4. **The database.** Connected as the new administrator to the branch's default database (`terraform output -raw goal_database_admin_url` with `/goal` changed to `/postgres`, into `psql` without echoing it): `CREATE DATABASE goal OWNER postgres;` unless prototype 4-2 left it there (Goal's own database, owned by `postgres`, not by a credential's role, which can be deleted with its password). If an earlier administrator created goal_owner, goal_app and goal_auth (the API-made `goal_admin`, user `pscale_api_…`, of prototype 4-2), hand them over first, connected as that one on `goal`: `GRANT goal_owner, goal_app, goal_auth TO <terraform output database_admin_role> WITH ADMIN OPTION;` (only the role that created them may alter them on PostgreSQL 16+). Then `task db:production -- init`: it creates the three roles if missing with the generated passwords (or sets them), grants the database and schema, revokes PUBLIC's CONNECT and TEMPORARY, creates `vector`, and grants goal_owner to the administrator `WITH INHERIT TRUE, SET TRUE`. goald migrates at its first start (or `task db:production -- migrate` first). *Done:* `goal` created, `goal db init`, migrated to 00056; pgvector 0.8.5, RLS on 22 tables, no `SECURITY DEFINER` function without a pinned `search_path`.
5. **Google sign-in (console, project `goal-byfrederick`, Google Auth Platform).** Branding: app name Goal, the owner's support and developer contact address, authorized domain `byfrederick.work`. Audience: External; Publish app (in production; openid, email and profile need no verification) once others sign in, or stay in testing with each person who signs in added as a test user. Data access: `openid`, `.../auth/userinfo.email`, `.../auth/userinfo.profile`. Clients › Create client › Web application, name `goal-web`, authorized JavaScript origin `https://goal.byfrederick.work`, authorized redirect URI `https://goal.byfrederick.work/api/auth/callback/google` (`terraform output google_redirect_uri`). Put the client id and secret into `google` (`task secrets:edit`); the auth service runs with `GOAL_AUTH_GOOGLE=on` (a Worker var). *Done:* External, in testing with the owner as the one test user; client `goal-web` with the production redirect and the local install's `http://127.0.0.1:8080/api/auth/callback/google`; its id and secret in SOPS.
6. **The outside values.** `task secrets:edit`: the master key (escrow it and the age key first, below), and the SMTP URL only when the install mails (Sign-in methods; empty for now). `task tf:plan` now passes with no empty-value error. *Done:* master key and Google client in SOPS, SMTP empty.
7. **Secrets, tokens and DNS.** `task tf:apply -- -target=module.secrets -target=cloudflare_dns_record.goal`. *Done:* 14 Secrets Store secrets (no `GOAL_SMTP_URL`), the scoped R2 and Workers AI tokens, the DNS record.
8. **Worker.** Deploy `deploy/cloudflare` with wrangler (4-21): its `secrets_store_secrets` bindings take `store_id = terraform output secrets_store_id` and each `secret_name` from `terraform output secret_names`, passed to each container as `terraform output secret_consumers` says; its vars take `GOAL_PUBLIC_URL` (`public_url`), `GOAL_S3_BUCKET` (`bucket`) and `GOAL_S3_ENDPOINT` (`s3_endpoint`). The wrangler config declares no routes. The first owner's address is no config value: from `deploy/cloudflare`, `wrangler deploy --var GOAL_BOOTSTRAP_OWNER_EMAIL:<the owner's address>` (pass it on every deploy until the owner has signed in; after that nobody signs in by it). The deploy makes the container applications `goal-goald`, `goal-auth` and `goal-runbox`; if it stops with a 408 while "applying Container application settings", run the same deploy again: it finishes what the first one started. *Done:* deployed, the three applications running.
9. **Network gate (blocks the route).** Spec 4 threat row 5 holds on Cloudflare only once it is shown there: a box must reach the internet and nothing private. Before the route serves anyone, from `deploy/cloudflare`, deploy sandboxtest's Worker on its own with a throwaway key: `key=$(openssl rand -hex 32)`, `wrangler deploy --config test/sandboxtest/wrangler.jsonc`, `printf %s "$key" | wrangler secret put GOAL_SANDBOX_KEY --config test/sandboxtest/wrangler.jsonc`; then from the repository root `GOAL_TEST_SANDBOX_URL=https://goal-sandboxtest.<subdomain>.workers.dev GOAL_TEST_SANDBOX_KEY="$key" GOAL_TEST_SANDBOX_IMAGE=sandboxtest GOAL_TEST_SANDBOX_NETWORK=on go test -tags cloudflare -count=1 -run TestSandboxes_Conformance -v ./internal/adapters/cloudflare`; then `wrangler delete --config test/sandboxtest/wrangler.jsonc`, and delete the container application it leaves behind: `wrangler delete` removes the Worker but not `goal-sandboxtest-runbox`, and the next sandboxtest deploy then fails with "could not finish applying … Container application settings". `wrangler containers list` shows its id; `wrangler containers delete <id>` deletes it, or the API: `curl -fsS -X DELETE -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/containers/applications/<id>"` (`GET` on `…/containers/applications` lists the applications with their names and ids). Every case must pass, `169.254.169.254`, RFC 1918, loopback and `fd00::/8` unreachable from a box above all. **If one fails, stop: do not apply the route** (nobody can sign in, so no factory runs) and fix the Worker's box networking first. Record the result in spec 4 §5.12 (staging check 1) and threat row 5. Run the gate again before deploying any change to `src/sandbox.ts`, the outbound handlers or the containers' network settings. *Done:* all 11 cases passed on Cloudflare, `Network_PublicHTTPSReachable` and `Network_NoPrivateAddress` among them; the leftover application deleted.
10. **Route.** `task tf:apply`: Cloudflare refuses a route to a Worker that does not exist, so the route comes last; the plan shows only it. ## Deploys

- **Infrastructure** (ADR 0010): a pull request changing `deploy/terraform/` passes `task check` (it runs `task tf:check`: fmt, validate, tflint, `terraform test` on mock providers), and its plan comes from the terraform-plan workflow's comment on the pull request (Credentials › GitHub environments). A person reviews the plan and merges; do not merge a change whose plan needs fixes. The merge starts the apply-on-merge workflow, [`.github/workflows/terraform-apply.yml`](../../.github/workflows/terraform-apply.yml), in the `production` environment: it plans the merged commit to a saved file, applies that file, then plans again with `-detailed-exitcode` and fails if anything is left. Runs go one at a time; one in flight is never cancelled. Only a push touching `deploy/terraform/**` starts it. Agents never run `task tf:apply`.
  - **A failed run** (a red `terraform-apply` on main) may have applied part of the plan; its last step names what is left (changes, or the error). The fix is a new pull request, merged like any other, never a manual apply by an agent. An auth error or a 403 at its first steps is usually an expired CI token or a missing environment value (GitHub environments).
  - **The owner applies by hand** (`task tf:apply` from a laptop, as before) only in these cases: the bootstrap's targeted applies (Bootstrap, step 13 included); a `-replace` the workflow cannot pass (Other rotations); and break-glass, when the workflow itself cannot run (its credentials are broken or Actions is down) and the change cannot wait. Even then the change is on main first, and the next merge's workflow run must show nothing left.
- **Code: on merge to main.** `.github/workflows/deploy.yml` deploys production once `ci` has passed for a push to main that changed the app: a file under `cmd/`, `internal/`, `apps/web/`, `apps/worker/`, `apps/auth/`, `packages/`, `deploy/cloudflare/`, `db/migrations/`, `contracts/`, or `go.mod`, `go.sum`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` (the Dockerfiles live in those folders) differs between that commit and the one the last successful deploy job deployed (its run name, `deploy <sha>`). A `deploy/terraform/`-only or docs-only push deploys nothing. Its `changes` job decides; the `deploy` job, in the `production` environment, checks out that commit and runs the same tasks a person runs:
  - `task deploy:worker`: `deploy/cloudflare/scripts/deploy.sh`. It builds the goald, auth and goal-agent images itself, pushes them, then runs `wrangler deploy --config wrangler.deploy.jsonc`, with `--var GOAL_BOOTSTRAP_OWNER_EMAIL:<address>` when that variable is set. wrangler's own build is a plain `docker build` that takes no cache flags, so on a fresh runner it rebuilt every image from scratch and gave goal-agent a new digest even when `apps/worker/` had not changed. Cloudflare then had to prepare that image again, and in run 40269545311 (2026-10-26, a web-only commit) wrangler timed out doing so.
    - **Built** with `docker buildx build --platform linux/amd64` on a docker-container builder: setup-buildx-action's in CI (buildx and BuildKit pinned in `deploy.yml`), or a `goal-deploy` builder the script creates locally. `scripts/images.mjs` reads `wrangler.jsonc`, lists each Dockerfile under wrangler's own repository names (`goal-goald`, `goal-auth`, `goal-runbox-goal-agent`) and names its inputs: the paths it copies, its Dockerfile and its `.dockerignore`. A test fails when a Dockerfile copies a path its inputs miss.
    - **Reproducible.** Each build has `SOURCE_DATE_EPOCH` set to the last commit of that image's inputs (`git log -1 --format=%ct -- <inputs>`, not HEAD, so the job checks out the full history), `rewrite-timestamp=true`, and no provenance or SBOM attestation (both carry the build's time). Its tag is that commit's short sha. The Dockerfiles keep the slow steps (apt, mise, pnpm install from the manifests, go mod download) before any source `COPY`, and no layer keeps apt's lists or logs, a package manager's cache, or pnpm's dated `node_modules/.modules.yaml`. So a deploy that changes nothing in an image pushes the digest already there, and Cloudflare has nothing new to prepare. That holds only on a cache hit: a cold rebuild of goal-agent reruns apt and mise against live mirrors and can still give a new digest.
    - **Cached** in CI (`GOAL_IMAGE_CACHE=registry`): a `:buildcache` tag beside each image in Cloudflare's registry (`type=registry,mode=max,image-manifest=true,oci-mediatypes=true`), read with `--cache-from`. It is one tag per repository, overwritten by each deploy, so it adds no repository and no named image. It does count toward the account's 50 GB of image storage, which Cloudflare never prunes by itself (`wrangler containers images delete`). A cache that fails to export (`ignore-error=true`) never fails the deploy; the build log then shows the error and the next build reports no `CACHED` steps. If Cloudflare's registry turns out to refuse cache manifests, switch to `GOAL_IMAGE_CACHE=gha` (the GitHub Actions cache, one scope per image), which also needs `actions: write` on the deploy job. Locally the default is `none`: no cache flag.
    - **Pushed and pinned.** The script logs docker in to `registry.cloudflare.com` with a 60-minute push and pull credential that `wrangler containers registries credentials` mints from the same token (masked in CI, `docker logout` at exit), and pushes each image straight from buildx. It then writes the git-ignored `deploy/cloudflare/wrangler.deploy.jsonc`: `wrangler.jsonc` with Goald's and Auth's `image`, and RunBox's `images.goal-agent.image`, set to `registry.cloudflare.com/<account>/<repository>@sha256:<digest>`. The durable_object policy needs that digest-pinned form for goal-agent. Every other key stays as it is (`node --test scripts/`, part of `task cloudflare:check`). `wrangler.jsonc` keeps the Dockerfile paths, so `wrangler dev` builds as before. The log shows, per image, `Building <repository> at <commit> (SOURCE_DATE_EPOCH <epoch>, cache <cache>)` and `Pushed <repository>@sha256:<digest> in <n> s`: compare two runs' lines to see that a digest held.
    - **Permissions.** `goal-deploy-ci` (Workers Containers Write, Cloudchamber Write) already pushed wrangler's images, and the same credential pushes the cache: no new token.
  - `task deploy:health`: polls `GET https://goal.byfrederick.work/v1/health` every 10 s until it answers `{"status":"ok"}`; after 5 minutes (`DEPLOY_HEALTH_TIMEOUT`, seconds) the job fails. A cold goald takes about 47 s. It shows the public host is healthy, not which version answers.
  - **Only the newest push deploys; a rollback is never cancelled.** Each event has its own concurrency group, `deploy-production-workflow_run` and `deploy-production-workflow_dispatch`, with `cancel-in-progress` true only for `workflow_run`: a newer push deploy cancels the push deploy in flight (or waiting) and starts at once. A rollback is never cancelled by a push, and a later rollback waits for the one in flight. One shared group cannot do this, because a push run with `cancel-in-progress` true would cancel a rollback in flight.
  - **Never two `wrangler deploy` at once.** The two groups could run a rollback and a push deploy side by side, so the deploy job's guard step ("Wait while a deploy of the other event runs", before the wrangler step) reads this workflow's runs (`gh run list`, `gh run view --json jobs`, with `actions: read`). It waits while a run of the other event has its deploy job past the guard step. It also waits for a run of the other event that has not passed its guard yet (no deploy job yet, queued, or before or in its guard) when that run's id is smaller. Of two runs that wait at once, the older proceeds, so they cannot deadlock or pass together. The guard logs "Waiting for deploy run <id> of the other event" every 20 s and fails after 30 minutes; the job's timeout is 75 minutes so a deploy still fits after the longest wait. The guard matches the step by its exact name, so a rename changes `GUARD_STEP` too. A job-level concurrency group with `cancel-in-progress: false` was rejected: GitHub keeps one pending run per group, so a push queued behind a pending rollback would silently replace it. A push deploy waiting behind a rollback is still cancelled by a newer push, and a push deploy after a rollback redeploys main and so undoes the rollback.
  - **Why cancelling is safe.** The `changes` job diffs against the commit of the last deploy job that *succeeded*, so whatever a cancelled deploy carried, the next one carries. ci on main runs one at a time and is never cancelled in flight (below), so `workflow_run` events arrive in push order. A newer deploy only ever cancels an older one, so an older commit never deploys after a newer one.
  - **A cancel during `wrangler deploy`** can leave the new Worker version live with the previous container images, or a container rollout started but not finished: wrangler uploads and activates the Worker version before it processes the containers. The next deploy recovers it: it diffs against the last successful deploy, so it redeploys every changed path, and `wrangler deploy` reconciles the Worker version and the container application settings to the config. Until it finishes, production runs that mix; if no newer push is coming, re-run the cancelled run's jobs or roll forward by hand.
  - **ci on main is never cancelled in flight**: only pull requests cancel superseded ci runs (`cancel-in-progress` is true only for `pull_request`), so when merges come faster than ci, main's runs queue and finish one at a time in push order. GitHub keeps one pending run per group, so during a burst of merges a middle commit may show a ci run cancelled before it started: that is expected, since the newest commit's ci covers its tree. The newest commit's ci completes and triggers one deploy; during a long burst the deploy can lag the newest merge by up to two ci durations.
  - What it reads from `production` (the environment admits every branch, for the pull request plans; the workflow itself runs only for main, and a manual run only from main):

    | Name | Kind | Where its value comes from |
    | --- | --- | --- |
    | `CLOUDFLARE_DEPLOY_API_TOKEN` | secret | the hand-made account token `goal-deploy-ci` (GitHub environments, above); passed only to the step that builds, pushes and runs wrangler, as `CLOUDFLARE_API_TOKEN`. It holds Secrets Store Write, which binding the Worker's Secrets Store secrets needs. The deploy never reads the environment's `CLOUDFLARE_API_TOKEN` (terraform's) |
    | `CLOUDFLARE_ACCOUNT_ID` | secret | the account id, the same secret terraform's apply reads (GitHub environments, above) |
    | `GOAL_BOOTSTRAP_OWNER_EMAIL` | variable, optional | the first owner's address (bootstrap step 8); leave it unset once the owner has signed in, as now |

  - **When it fails.** `task deploy:worker` retries `wrangler deploy` once, only when its output contains "Timed out while preparing the container image on Cloudflare's network" (transient); any other failure fails at once. A second timeout fails the job: re-run the failed job. A 408 while "applying Container application settings": re-run the failed job (bootstrap step 8). A 401 or 403 from wrangler: the token expired or lacks a permission; renew it or add that permission by hand, never by widening another token. `Secrets store binding authorization failed [code: 10021]` at `wrangler deploy`: the deploy token lacks Secrets Store Write (first seen in run 40247103998, 2026-10-26, when `goal-deploy-ci` could only read the Secrets Store); edit `goal-deploy-ci` in place in the dashboard (Manage Account › Account API Tokens) to Secrets Store Write and re-run the failed job. Health not ok: read the Worker's logs (`wrangler tail`, or the dashboard) and What the first deploy showed, then roll back.
  - **Rollback.** Actions › deploy › Run workflow, from `main`, with the sha of an earlier commit of main that `ci` passed for (`gh workflow run deploy.yml --ref main -f sha=<sha>`). It checks both, then deploys that commit without the paths check, and it becomes the commit the next push is compared with. Re-running an earlier deploy run (Re-run all jobs) does the same within GitHub's 30-day re-run window. Only commits that have `task deploy:production` can be deployed this way; for older ones, deploy by hand. A rollback does not undo migrations: goald's migrations are forward-only, so an older goald must still run on the newer schema.
  - By hand (the same steps, from a laptop with Docker and buildx): `CLOUDFLARE_API_TOKEN=<the deploy token> CLOUDFLARE_ACCOUNT_ID=<id> task deploy:production` on a clean, full (not shallow) checkout of the commit. No layer cache is used unless you set `GOAL_IMAGE_CACHE=registry`.
- **Before merging** a change to the boxes' networking (`src/sandbox.ts`, the outbound handlers, the containers' network settings): pass the network gate (bootstrap step 9) first, since the merge deploys it. goald migrates at start as goal_owner. A goald redeploy ends its runs in flight; their leases expire and the items are claimed again (spec 4 §11.3). A redeploy that cuts a box under a live goald (the Worker's, or a box restart) retries the run by itself in a new box (`run_retried`), with no manual `goal retry`; only the loss in one claim that reaches the factory's `board.flow.retry.transient.attempts` (default 3) blocks the item.
- **A secret's new value** reaches a container when it starts: once the workflow has applied it, redeploy (or restart) the containers that consume it.

## Master key: escrow and rotation

`GOAL_MASTER_KEYS` seals every organization's connection credentials (AES-256-GCM, key id in the AAD). Secrets Store cannot give a value back, and without the key every stored credential is lost (spec 4 §11.3 risk 6).

- **Escrow.** Before a key is first used, keep it offline in two places (the owner's password manager and a printed or hardware copy). Escrow the age private key the same way: it is what opens `production.sops.yaml`, which holds every master key in use.
- **Rotation** (yearly, or at once if a key may have leaked):
  1. `task secrets:edit`: put the new key first, `k2:<new>,k1:<old>`; escrow `k2`.
  2. Open a pull request with the re-encrypted SOPS file; once a person merges it and the apply-on-merge workflow has applied it, restart goald so it seals with `k2` and still opens `k1`.
  3. `task db:production -- rekey`: reseals every credential under `k2`.
  4. Remove `k1` from the value in a second pull request; once it is merged and applied, restart goald. Backups keep `k1`'s ciphertext until they expire; keep `k1` escrowed until then.
  5. If a key leaked, also revoke the credentials it protected at their providers: the ciphertext may have leaked with it.

## Other rotations

Each change below that edits `deploy/terraform/` or its SOPS file goes in a pull request with its plan; a person merges it and the apply-on-merge workflow applies it. A `-replace` is no change to the files, so the workflow cannot make it: the owner runs those from a laptop on main (Deploys), and the next workflow run must show nothing left.

- **A generated secret:** the owner runs `task tf:apply -- -replace='random_password.generated["<name>"]'`, then redeploy its consumers in one go. `gateway_key` ends the task tokens in flight (their runs fail and are claimed again); `better_auth_secret` signs everyone out; `sandbox_key` and `auth_proxy_secret` change for both consumers at once. A role password (`goal_owner`, `goal_app`, `goal_auth`): replace it, `task db:production -- init` (sets it), then redeploy goald and auth.
- **The administrator:** only the role that created goal_owner, goal_app and goal_auth may alter them, so the old one hands them over before it goes: add a second role resource (`admin_next`, another `name`), apply it, connect as the old administrator and `GRANT goal_owner, goal_app, goal_auth TO <the new base user name> WITH ADMIN OPTION;`, point `module.database_urls` at `admin_next` and apply (the URLs change), `task db:production -- init`, then remove the old resource and apply (what it owns goes to `postgres`). Each "apply" is a merged pull request applied by the workflow.
- **A Cloudflare token:** the owner runs `task tf:apply -- -replace='module.r2_token.cloudflare_account_token.this'` (or `module.workers_ai_token`), then restart goald.
- **From outside:** SMTP (when there is one) and the Google client secret: make the new one at the provider, `task secrets:edit`, a pull request with the SOPS file, merged and applied by the workflow, redeploy auth, then revoke the old one.

## Restore

- **No failover.** PS-5 is a single node with no replica: while PlanetScale restarts it (maintenance) or it is down, goald's queries fail, and once it is back goald's listeners reconnect and resync on their own; nothing to do. Availability beyond that needs a PlanetScale plan with replicas.
- **Database.** PlanetScale's backups restore into a new branch, which changes the branch id of every user name. Adopt it without touching the old one: set `planetscale.branch` in `deploy/terraform/locals.tf` to its name, `terraform state rm planetscale_postgres_branch.main planetscale_postgres_branch_role.admin` (forgets both, deletes nothing), put the `import` block back in `database.tf` (`import { to = planetscale_postgres_branch.main` with `id = jsonencode({ organization = local.settings.planetscale.organization, database = local.settings.planetscale.database, id = local.settings.planetscale.branch }) }`), `task tf:apply` (a new administrator on the new branch, new URLs), hand the three roles to it as in bootstrap step 4, `task db:production -- init`, redeploy goald and auth, then delete the old branch's administrator in the console. From a dump (including moving a local install, spec 4 §14 step 7): `task db:production -- init` on the empty `goal` database first, then `pg_restore --no-owner` connected as goal_owner (`GOAL_MIGRATE_DATABASE_URL`, `terraform output -raw goal_migrate_database_url`), then start goald with the same master keys the dump was sealed with.
- **Bucket.** R2 keeps no object versions: a restore is a copy from a copy. Blobs are immutable and content-addressed, so `rclone sync` (or any S3 copy) from the backup or from a local install's RustFS into `goal-production` restores definitions and uploads; nothing else is needed.
- **Terraform state** lost or damaged: recreate the workspace and adopt the bucket, the DNS record, the route, the branch and the project with `import {}` blocks (each resource's import id is in its provider's documentation), plan, then delete the blocks. The generated secrets, the administrator and the tokens existed only there: let the plan make new ones, then run `task db:production -- init` and redeploy every container, as for a rotation of all of them. The master keys are safe in SOPS, which is why they live there. Never `terraform destroy` to start over: the bucket, the branch and the project are protected for that reason.
- **age key lost:** the deployed secrets keep working, but `production.sops.yaml` cannot be read: restore the key from escrow. If it is gone, make a new age key and a new SOPS file with every value made again, the master keys from escrow; a lost master key means every organization re-enters its credentials.
