# 2.2 E — Work screens and flow metrics

Status: draft for review · Depends on A (organizations, RLS, audit, the request actor) and C (app shell, org stream) · Tag `work` · Migrations `00030–00034`

## 1. Summary

Phase E makes the Floor, Board, Item and Agent screens tell the truth over time instead of from a snapshot: goald starts recording how long every item spends at each station and state (`item_spans`) and how long every WIP slot is held (`lease_spans`), and derives from them throughput against target, the lead-time bridge, the constraint's busy share over the window, station and agent statistics. The engine gains the manual flow control the Board shows (pulling and clearing the andon cord stops and restarts the line) and the human controls the Item and Board screens offer (Move, Pause, send back while running, notes for the agent). Drum-buffer-rope release, the expedite-lane limit, the automatic rework-rate andon pull and full run transcripts are deferred (section 2), and the org-wide "Waiting on you" inbox C creates is extended with E's kinds for the Floor's Needs you card and the Phone board. (review)

## 4. Domain and engine changes

### 4.1 Flow policy and targets in the definition

`schema/factory.schema.json`, `$defs/board/properties/flow` gains `targets` (all optional):

```yaml
spec:
  board:
    stations:
      - { id: investigate, kind: agent, agent: investigator, agents: 3, wip: 3, buffer: 2 }   # buffer exists today
    flow:
      release: drum-buffer-rope          # exists
      constraint: auto                   # exists: auto | <station id>
      expedite: { types: [incident], wip: 1 }   # exists
      andon: { reworkRate: 0.4, window: 10 }    # exists
      targets:                                   # new
        throughputPerDay: 8              # number > 0
        leadTimeHours: 6                 # p85 of created → done, number > 0
        expediteLeadTimeMinutes: 60      # integer ≥ 1, per expedite item
```

Targets live in the definition (versioned with it, B) and are edited in the Definition editor's Line section, "Flow and targets" panel (D), or `goal factory push`. Nothing in the database stores them.

`internal/config` maps them; `internal/domain`:

```go
// domain/line.go additions

    // existing fields …
    OrgID OrgID          // from A: every line belongs to one organization
    Flow  FlowPolicy

    // existing fields …

type ReleasePolicy string

    ReleasePush ReleasePolicy = "push"              // default: queue stations release everything
    ReleaseDBR  ReleasePolicy = "drum-buffer-rope"

type FlowPolicy struct {
    Release     ReleasePolicy
    Constraint  string      // "" or "auto" = detected; otherwise a station id
    ExpediteWIP int         // 0 = unlimited

}

type AndonPolicy struct {
    ReworkRate float64 // share of gate verdicts that reject, 0..1
    Window     int     // over the last N verdicts at one gate station
}

type Targets struct {

    LeadTime         time.Duration // p85; 0 = none

func (l Line) ItemTarget(c ClassOfService) time.Duration
```

`Line.ExpediteTypes` stays. `config` validation: `flow.constraint` names an agent station; a non-zero `buffer` outside the drum is a warning, not an error.

As built in E1 (build note): `flow.constraint` must name a station of any kind (`unknown-station` otherwise), not only an agent station: a line whose known bottleneck is a person (a human writing step) declares that station today, and refusing it would break a working definition. A non-zero `buffer` on any other station than a declared constraint is the warning `buffer-not-at-constraint`; with `constraint: auto` no buffer is flagged. Targets are `domain.FlowPolicy.Targets`; an unset release maps to `ReleasePush`.

### 4.2 History: spans and lease outcomes

```go
// domain/flowstats.go (new file)
type Span struct {
    Station     string
    State       ItemState
    ReworkRound int    // the item's rework_count while in this span
    ReworkBy    string // station that sent the item back for this round; "" in round 0
    EnteredAt   time.Time
    LeftAt      time.Time // zero while open
}

type LeaseOutcome string
const (
    LeaseAdvanced  LeaseOutcome = "advanced"  // output accepted: next station or gate approved
    LeaseRejected  LeaseOutcome = "rejected"  // this station's gate rejected it (rework upstream)
    LeaseEscalated LeaseOutcome = "escalated" // gate rejected past maxRework → waiting for a human
    LeaseBlocked   LeaseOutcome = "blocked"
    LeaseReleased  LeaseOutcome = "released"  // shutdown
    LeaseExpired   LeaseOutcome = "expired"
    LeaseTaken     LeaseOutcome = "taken"     // a human moved, paused or sent it back mid-run

// Finished reports whether the agent completed its task (advanced, rejected, escalated).
func (o LeaseOutcome) Finished() bool
```

`ports.Transition` gains `Outcome domain.LeaseOutcome` (required whenever `Lease` is set or `TakeLease` is true; the store writes a `lease_spans` row) and `TakeLease bool` (section 4.5). The engine sets the outcome on every path: `finish` → advanced or rejected or escalated, `block` → blocked, `release` → released; `RequeueExpiredLeases` writes expired.

Spans are maintained by a database trigger (section 6) so no code path can forget them; the in-memory fake maintains them in its transition helper and the conformance suite proves both agree.

### 4.3 Drum-buffer-rope release and the expedite lane (deferred to later, review; kept as the design for when it is scheduled)

Today `releaseQueue` moves every waiting item from a queue station to the next one each tick. With `release: drum-buffer-rope` and a drum (the configured `flow.constraint`, or the detected constraint when `auto`) that has `buffer > 0`:

- A queue station upstream of the drum releases a **standard** item only while `waiting(drum) + open(between)` < `drum.Buffer`, where `open(between)` counts items in any open state at stations strictly between the queue station and the drum. Items held this way are "Waiting for buffer room"; items queued or ready at the drum are "Ready in buffer".
- **Expedite** items bypass the rope while `open expedite items past the release station` < `flow.expedite.wip` (0 = unlimited). Past the limit they wait at the queue station, ahead of standard items, until a lane slot frees. `ClaimNext` already pulls expedite first.
- Release is one atomic store call, so concurrent goald instances never overshoot the buffer:

```go
// ports.Store addition
// ReleaseUpTo moves up to r.Max items waiting at r.From (pull order) to r.To, appending moved
// events, while the rope allows it. It takes pg_advisory_xact_lock on the factory's release key,
// counts what r.Counted holds, and releases min(r.Max, room) standard items plus expedite items
// within r.ExpediteRoom. A zero Rope releases everything (push).
ReleaseUpTo(ctx context.Context, r Release) ([]domain.Item, error)

type Release struct {
    FactoryID    domain.FactoryID
    From, To     domain.Station
    Max          int
    Rope         *Rope
    ExpediteWIP  int // 0 = unlimited
}
type Rope struct {
    Drum    string
    Buffer  int
    Counted []string // station ids strictly between From and Drum
}
```

Detected constraint for `auto`: the engine refreshes, per factory, the top candidate of `FlowStats.StationTimes` over the last 7 days every `ConstraintEvery` (default 1 min, `engine.Config`), falling back to `Line.Constraint(loads)` (snapshot) when there is no lease history. It is a cache of derived data (any instance recomputes the same answer), so goald stays stateless.

### 4.4 Andon

```go
type AndonKind string
const (AndonManual AndonKind = "manual"; AndonRework AndonKind = "rework")

type AndonPull struct {
    ID        int64
    FactoryID FactoryID
    Kind      AndonKind
    Station   string // the gate that triggered a rework pull; "" for manual
    Reason    string
    PulledBy  string // A's Actor.Ref(): "user:local" or "system:engine" (no-auth)
    PulledAt  time.Time
    ClearedBy string
    ClearedAt time.Time // zero while open
    Note      string    // clearing note
    Data      map[string]any // rework: {"rejected": 4, "window": 10, "top_reason": "…"}
}

// ports.Store additions
PullAndon(ctx context.Context, p domain.AndonPull) (domain.AndonPull, error) // ErrConflict when one is open
ClearAndon(ctx context.Context, factory domain.FactoryID, by, note string, at time.Time) // by = Actor.Ref()
    (domain.AndonPull, error) // ErrNotFound when none is open
OpenAndon(ctx context.Context, factory domain.FactoryID) (*domain.AndonPull, error)
AndonPulls(ctx context.Context, factory domain.FactoryID, limit int) ([]domain.AndonPull, error)
```

Rules:

- While a pull is open the engine releases nothing from queue stations and claims nothing new at that factory (2.2). Runs in progress finish and move on; humans still approve, reject, merge, retry, move and pause; submissions still enter the first station.
- **Rework trigger (deferred to later, review).** After every gate verdict (`finish` with a verdict) the engine reads `FlowStats.GateDecisions(factory, station, after = last clear, n = andon.Window)`. When at least `Window` verdicts exist and `rejected / Window ≥ ReworkRate`, it pulls with kind `rework`, the station, reason "<station> sent back <k> of the last <n>" and the most frequent rejection category or reason in `Data`. Concurrent pulls collide on the unique open index; `ErrConflict` is ignored. Only verdicts after the last clear count, so clearing does not immediately re-pull.
- **Warning** (no engine action): the inbox shows `rework_warning` when one more rejection would pull the cord (`rejected ≥ ceil(ReworkRate × Window) − 1` over the last `Window` verdicts).
- A human pulls (`manual`, reason required) and clears (note optional). No automatic clear.

### 4.5 Human control of items

New engine methods (`internal/engine/human.go`); `by` is the request's actor from A (`domain.ActorFrom`; always the local user in 2.2, no-auth), recorded in events and the audit log.

```go
// Move puts an item at another station of its line, in that station's arrival state.
// Allowed from queued, ready, blocked, waiting_human and in_progress (the run is stopped).
// Moving upstream counts as rework (rework_count+1, reason required); moving to a done station
// is refused (use approve or merge); moving to the item's own station is refused.
func (e *Engine) Move(ctx context.Context, id domain.ItemID, to string, by domain.Actor, reason string) (domain.Item, error) // (review) by is A's Actor everywhere below

// Pause stops an open item where it is: it becomes blocked with a paused event (reason optional).
// Retry resumes it. In progress, the run is stopped.
func (e *Engine) Pause(ctx context.Context, id domain.ItemID, by domain.Actor, reason string) (domain.Item, error)

// Reject (existing) now also accepts in_progress and blocked items: the item goes to
// Line.ReworkTarget(station) with rework_count+1; an in-progress run is stopped.
func (e *Engine) Reject(ctx context.Context, id domain.ItemID, by domain.Actor, reason string) (domain.Item, error)

// Note records a person's note for the agent working the item (event kind note). A running
// agent receives it live when its task supports input; otherwise the next run's brief carries
// every note since the item's last run started, under "Notes from people".
func (e *Engine) Note(ctx context.Context, id domain.ItemID, by domain.Actor, text string) (domain.Event, error)

func (e *Engine) PullAndon(ctx context.Context, f domain.FactoryID, by domain.Actor, reason string) (domain.AndonPull, error)
func (e *Engine) ClearAndon(ctx context.Context, f domain.FactoryID, by domain.Actor, note string) (domain.AndonPull, error)

// Interrupt is told every committed item notice (cmd/goald wires it to api.Feed). For a
// lease_taken notice of an item this instance is running, it cancels that run at once; for a
// note notice it delivers the note to the running task. Other instances ignore the notice.
func (e *Engine) Interrupt(n ports.ItemNotice)
```

Stopping a run without shared state: a human transition on an in-progress item uses `Transition{TakeLease: true, Outcome: LeaseTaken}`, which deletes the item's lease whatever its `AcquiredAt` and appends `lease_taken`. The instance running it learns at once through `Interrupt` (it keeps an in-memory map of its own running items to cancel funcs, like the gateway's sidecar registry) and, as a fallback, at its next heartbeat (`ErrLeaseLost`, within `HeartbeatEvery`). The cancelled run is finished as `cancelled`; its workspace and sidecars are removed as today.

New event kinds (`domain.Event*`): `paused`, `lease_taken`, `note`, `note_delivered`, `tool_denied`, `andon_pulled` and `andon_cleared` (factory notices, section 8.4). Manual moves reuse `moved` with `data.manual = true` and `data.reason`.

As built in E10 (build note): `ports.Transition` gains `TakeLease` (exclusive with `Lease`, needs `Outcome`; nothing is recorded when the item holds no lease) and `Audit` (an audit entry written in the transition's transaction, so `item.moved`, `item.paused` and `item.rejected` need no separate call). `Interrupt` stops a run only when the notice's station is the run's and its lease was acquired no later than the notice's time, so an old notice never stops a later claim of the same item; the instance that made the change stops its own run at once without waiting for the notice. `cmd/goald` passes `eng.Interrupt` to `api.NewFeed` as a tap of every item notice. The refusals have their own errors and Problem codes: `unknown-station` and `reason-required` (400), `item-closed`, `same-station`, `done-station`, `already-blocked`, `cannot-send-back` and `item-changed` (409). Runs whose lease a person takes stay with their instance, which finishes them as `cancelled` with their real cost; a run whose instance died before it heard stays `running` (no store sweep finishes runs without a lease yet).

### 4.6 Gate verdict category

`domain.Verdict` gains `Category string \`json:"category,omitempty"\``. A reviewer's contract may declare it (an enum is recommended); the engine copies it into `gate_rejected.data.category`. "Why review sent work back" groups by category, falling back to the normalised reason text (trimmed, lower-cased, first 120 characters). Nothing in Go names a category.

### 4.7 Transcripts (deferred, review: bucket rule 3; see section 2)

After `task.Wait()`, if the task implements `ports.TranscriptSource`, the engine reads the transcript, writes it to `ObjectStore` at `domain.RunTranscriptKey(line.OrgID, runID)` and records it with `Store.SetRunTranscript`. Upload failures are logged and never fail the run. `engine.Deps` gains `Objects ports.ObjectStore` (nil disables transcripts).

## 5. Ports and adapters

### 5.1 `ports.FlowStats` (new)

A read model, separate from `Store` so the write-side port stays focused; the postgres adapter implements both on one pool, `porttest.Store` implements both over the same in-memory state. Name added to the registry under E. All methods read within the caller's organization (A's tenancy context; RLS in PostgreSQL).

```go
type FlowQuery struct {
    FactoryID domain.FactoryID
    Since, Until time.Time // [since, until)
    Type      string       // "" = every work type
}

type FlowStats interface {
    // FlowMetrics: done per UTC day, items done, reworked, lead-time p50/p85, WIP now, spend of
    // runs started in the window, and the items whose waiting span at station longWaitsAt lasted
    // over 24 h and ended or is still open in the window. Moved from Store.FlowMetrics (deleted).
    FlowMetrics(ctx context.Context, q FlowQuery, longWaitsAt string) (domain.FlowMetrics, error)

    // DoneByBucket counts items done in n consecutive buckets of length d ending at until,
    // oldest first.
    DoneByBucket(ctx context.Context, q FlowQuery, d time.Duration, n int) ([]int, error)

    // ItemTimes returns, per item done in the window, its lead time and its time per component.
    ItemTimes(ctx context.Context, q FlowQuery) ([]domain.ItemTime, error)

    // StationTimes measures every station over the window: lease-held seconds (spans plus live
    // leases, clipped to the window), lease count and mean lease duration, waiting item-seconds
    // (time-weighted queue), mean wait per item, waiting now and 24 h before until, gate
    // verdicts and rejections, done count, and the earliest lease span (coverage).
    StationTimes(ctx context.Context, f domain.FactoryID, since, until time.Time) ([]domain.StationTimes, time.Time, error)

    // GateDecisions counts the last n verdicts at a gate station after `after`, the rejections
    // among them and the most frequent rejection category or reason.
    GateDecisions(ctx context.Context, f domain.FactoryID, station string, after time.Time, n int) (domain.GateTally, error)

    // AgentStats measures one agent over the window (section 6.6).
    AgentStats(ctx context.Context, f domain.FactoryID, agent string, since, until time.Time) (domain.AgentStats, error)

    // ItemSpans returns an item's spans in order.
    ItemSpans(ctx context.Context, id domain.ItemID) ([]domain.Span, error)

    // InboxItems returns the organization's open items that may need a person: waiting_human,
```

### 6.1 `00030_item_spans.sql`

```sql
CREATE TABLE item_spans (
  id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id           uuid NOT NULL REFERENCES organizations (id),
  factory_id       uuid NOT NULL REFERENCES factories (id),
  item_id          uuid NOT NULL REFERENCES work_items (id) ON DELETE CASCADE,
  type             text NOT NULL,
  class_of_service text NOT NULL,
  station          text NOT NULL,
  state            text NOT NULL CHECK (state IN ('queued','ready','in_progress','waiting_human','blocked')),
  rework_round     integer NOT NULL CHECK (rework_round >= 0),
  rework_by        text,
  entered_at       timestamptz NOT NULL,
  left_at          timestamptz,
  CHECK (left_at IS NULL OR left_at >= entered_at)
);
CREATE UNIQUE INDEX item_spans_open_key ON item_spans (item_id) WHERE left_at IS NULL;
CREATE INDEX item_spans_item_idx ON item_spans (item_id, entered_at);
CREATE INDEX item_spans_window_idx ON item_spans (factory_id, left_at);   -- NULLs (open) included
CREATE INDEX item_spans_station_idx ON item_spans (factory_id, station, entered_at);
-- RLS policy + GRANT SELECT, INSERT, UPDATE ON item_spans TO goal_app

-- +goose StatementBegin
CREATE FUNCTION track_item_span() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE prev_by text;
BEGIN
  IF TG_OP = 'UPDATE' THEN
    IF NEW.station = OLD.station AND NEW.state = OLD.state AND NEW.rework_count = OLD.rework_count THEN
      RETURN NEW;
    END IF;
    UPDATE item_spans SET left_at = NEW.updated_at
     WHERE item_id = NEW.id AND left_at IS NULL
    RETURNING rework_by INTO prev_by;
  END IF;
  IF NEW.state IN ('done', 'cancelled') THEN RETURN NEW; END IF;
  INSERT INTO item_spans (org_id, factory_id, item_id, type, class_of_service, station, state,
                          rework_round, rework_by, entered_at)
  VALUES (NEW.org_id, NEW.factory_id, NEW.id, NEW.type, NEW.class_of_service, NEW.station, NEW.state,
          NEW.rework_count,
          CASE WHEN TG_OP = 'UPDATE' AND NEW.rework_count > OLD.rework_count THEN OLD.station ELSE prev_by END,
          CASE WHEN TG_OP = 'INSERT' THEN NEW.created_at ELSE NEW.updated_at END);
  RETURN NEW;
END $$;
-- +goose StatementEnd
CREATE TRIGGER work_items_spans AFTER INSERT OR UPDATE OF station, state, rework_count ON work_items
  FOR EACH ROW EXECUTE FUNCTION track_item_span();
```

Every store path that changes station or state already sets `updated_at` to the engine clock's `At` (`StartItem`, `MoveItem`, `RequeueLeases`); the conformance suite asserts span boundaries equal transition times. `SECURITY INVOKER` (default): inserts pass RLS because `NEW.org_id` is the session's org.

**Backfill** (same migration, runs as `goal_owner`, bypassing RLS): rebuild spans for every item from `item_events` ordered by `id`. Position-changing kinds map to `(station, state)`: `created` → (event station, arrival state of its kind), `moved` → (`data.to`, arrival state of that station's kind read from `factories.definition->'spec'->'board'->'stations'`; B no longer fills that column for factories created through its API, so where it is NULL the state is `waiting_human` when the item's next event there is a human decision, else `queued`; B keeps the column until 2.3 for this backfill) (review), `claimed` → in_progress, `blocked` → blocked, `retried` / `released` / `lease_expired` → queued, `done` → closes the last span. `rework_round` = number of `gate_rejected`/`rejected` events followed by a `moved` up to that point; `rework_by` = station of the latest such rejection. `left_at` = `lead(at)`. Items with events the mapping cannot place are skipped (their bridge contribution is missing; they still count in throughput). Written as one `INSERT … SELECT` with window functions; tested by an integration test that compares backfilled spans with trigger-made spans for the same scripted history.

As built in E2 (build note): the backfill reads events only, not `factories.definition`. Since phase 1 the engine records every arrival at a human station with a `waiting_human` event and at the done station with a `done` event right after `moved`, so `moved` is skipped when the next event places the item there; `created` and `moved` read `waiting_human` when a decision (approved, rejected, merged) follows at that station and `moved` reads `blocked` when a retry follows (a publish moves blocked items as they are), else `queued`; `agent_cancelled` (D1) requeues like `released`. The item row is the truth for the open span's state (an item a publish moved onto a human station); items whose last position does not match their station and rework count, and cancelled items, get no spans. The trigger closes a span at `greatest(updated_at, entered_at)` so a clock behind (another goald) never breaks `left_at ≥ entered_at`, and the backfill keeps times monotonic the same way. Verified on a copy of a real database (2 items, 352 events). `Item.flow` is filled on `GET …/items/{item}` only (optional on `Item`); `current_run` comes from `FlowStats.CurrentRun(item)` (the running run under the item's lease, its slot and its `usage` events), so E2 needs neither `Store.Runs` nor `LiveTurns` (E13, E7); `current_run.slot` is 1-based like `ItemCard.slot`; `budget` is the limits of the item's station's agent (its own, else the runtime's); `checks` are display labels (`schema`, `2+ evidence links`, a command line). `Station` in the contract gains `description` for the Path card.

**Lead-time bridge** (`domain.BridgeLeadTime`): components per item are `waiting@station` (queued/ready, round 0), `rework@rework_by` (any state while `rework_by` is set), `waiting_on_you` (waiting_human, round 0), `blocked@station` (round 0), `working@station` (in_progress, round 0). Let *slow* be items done in the window with lead time over the target and *fast* the rest. For each component, `excess = mean(slow) − mean(fast)` (when no fast items: `mean(slow)` for delay components, 0 for working); negatives drop; `step = gap × excess / Σexcess`, where `gap = actual p85 − target`. Steps under 3% of the gap merge into `other`; the rest are ordered by size; `items` is the number of slow items with time in the component. The steps sum exactly to the gap, so Target + steps = Actual on the chart.

### 6.7 Why plain tables and queries, not materialized views

| Data | Expected volume (busy factory) | Read pattern |
| --- | --- | --- |
| `work_items` done | 10–500 per day | ≤ 90 days per query, `work_items_done_at_idx` |
| `item_spans` | 10–40 per item → ≤ 20 k per day, ~7 M per year at the high end | window range on `(factory_id, left_at)` |
| `lease_spans` | 2–8 per item → ≤ 4 k per day | window range on `(factory_id, station, ended_at)` |
| `item_events` | 50–500 per item (tool calls dominate) | never scanned for metrics; only partial indexes on verdicts and rejections, and per-item lookups |

Every metric query touches at most a 90-day slice of the narrow span tables through an index: tens of thousands of rows, single-digit milliseconds. Materialized views are rejected because PostgreSQL does not apply row-level security to them (they would need a wrapper per org to stay isolated), they need a refresh job under an advisory lock and they would show stale numbers next to a live stream. No new plain views either: the queries live in `queries/flow.sql`. If a factory outgrows this, `item_spans` partitions by month like `item_events` (architecture "Event volume").

### 6.8 Conformance suite (`porttest/storetest`)

New cases, run against the fake and PostgreSQL: spans open and close at every transition (create, release, claim, gate approve, gate reject with `rework_by`, escalate, human approve/reject/retry/move/pause, requeue, done); lease spans carry the outcome given and `expired` on requeue; `TakeLease` removes a lease with any `AcquiredAt` and fails with `ErrConflict` when the item is not where `From` says; `ReleaseUpTo` never exceeds the rope with concurrent callers and lets expedite through within its limit; one open andon per factory; `FlowStats` results on a scripted history equal hand-computed values (busy share clipped to the window, time-weighted waiting, p85, sent-back attribution, gate tallies after a clear); `Attention` returns only the caller org's items.

As built in E4 (build note): the weekly operation is `getWeeklyThroughput`; `Metrics.window` is the range's length (`7d`), and `from`, `to`, `type`, `throughput_per_day`, `previous`, `targets` and `long_waits` are always present (null when not asked for or not set). A range's end is `min(to + 1 day, now)`. Spend for a type counts the runs of items of that type. `long_waits` is counted at the definition's `flow.constraint` when it names a station, else at the snapshot constraint (`Line.Constraint`), and is null when there is neither; E6 puts the detected constraint in between. A wait counts when its queued or ready span at that station overlaps the range and had lasted over 24 h (`domain.LongWait`) by the range's end. Range and type errors are plain 400 problems, like every other malformed request. The Floor's `DaysCard` became the Weekly card; "Where work waits" keeps the bridge's place until E5; on phones the header is the caption "Oct 17 to 23, vs the week before" (Mobile-Floor) and the URL's range applies.

As built in E5 (build note): the operation is `getLeadTimeBridge`; `status` is `no_target` first (no target in the definition), then `not_enough_data` (under 5 items), then on or over target, so steps, `gap_hours` and `over_target_items` exist only over target. The actual p85 is computed from `ItemTimes`' lead times (`domain.Percentile`, as `percentile_cont`). `ItemTimes` reads closed spans only (an item done has no open one) and gives a component every span's time: `rework` whenever `rework_by` is set, else by state. A slow set without any positive excess yields one `other` step of the whole gap, so the steps always sum to it (rounding goes to the largest step). `constraint.busy_ratio` is nullable (null before the factory's first lease, as the board's busy shares); the constraint is the board's drum (configured, else the snapshot) until E6. `BridgeStep` is its own schema; the bridge's queries live in `queries/flow_reports.sql`. "Where work waits" left the Floor.

## 11. Security and tenancy

- Every new table has `org_id` and the RLS policy; goald queries run under `SET LOCAL goal.org_id` (A). The engine's per-factory transactions set the line's org.
- (Deferred with transcripts.) The transcript endpoint reads the key from `agent_runs` under RLS and never builds a key from the URL; a run of another org is 404. Transcripts are redacted by the runner (the run's resolved `Env` values and the gateway token) before they leave the host; the worker never receives bucket credentials.
- Notes are data for the agent, not instructions from Goal: the brief and the live message frame them as "Note from <actor name>"; their text is stored as an event and is visible on the item. Notes are capped at 2000 characters.
- (no-auth) No role checks: the local user may move, pause, send back, note, pull and clear. Handlers reach factories and items through A's resolvers, so phase 3 adds checks at A's `Authorizer` seam.
- Audit entries (A's `Audit` port; A's action format, review): `andon.pulled`, `andon.cleared`, `item.moved`, `item.paused`, `item.rejected`, `item.noted` (length only, not the text).

## 17. Open questions

1. **Day boundaries.** Metrics use UTC days. Should organizations get a time zone (Org settings, C) so "today" and weekly buckets follow it?
2. **Capacity history.** Busy share divides by the station's current capacity; after a definition change mid-window the share is approximate. Acceptable, or should lease spans record the capacity at the time (B's version id would allow it)?
3. **"1 of 3"** on the constraint card is read as the top three candidate constraints. Is it meant to page through insights instead?
4. **Live draft output.** The canvas's "Draft diagnosis" while the agent is still running would need a structured draft from the agent (for example a gateway tool `goal__draft`). E shows the agent's latest message until the output is submitted. Build the draft tool in phase 4, or keep the fallback?
5. **Live notes.** E14 adds stdin delivery and the SDK's streaming input to the worker. If that proves fragile, ship notes as next-run only and drop the `TaskInput` interface?
6. **Who may pull the andon cord.** Moot in 2.2 (no-auth: the local user); Phase 3.
7. **Move to done / cancel.** Moving to a done station is refused (approve or merge finish work). Should the Move menu offer "Cancel item" (state `cancelled`) as well?
8. **Transcript retention.** Moot in 2.2: transcripts are deferred.
