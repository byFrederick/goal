# 2.2-B — Definitions and versions

Status: draft for review · Depends on [A](2.2-a-organizations.md) · Provides to C, E, F, G

## 1. Summary

Factory definitions stop being "whatever object versions a bucket listing returned": file content is stored once per organization as immutable, content-addressed blobs (`orgs/<org-id>/blobs/<sha256>`), and PostgreSQL records every draft and published version as a manifest (path → sha256) with a current-version pointer on the factory that one transaction moves and a NOTIFY announces to every goald. On top of that store, goald gets an authoring API: one shared, autosaved draft per factory with optimistic concurrency, validation that returns located problems with machine-applicable fixes, a structured factory model the Visual editor edits that round-trips with `factory.yaml` (comments and key order kept), semantic compare, restore, templates and the four ways to start a factory. Runs pin the version they started on, the CLI's `factory pull/push/validate/list` move onto the API, and every factory in today's `factories/<id>/` prefix becomes v1 of itself without losing anything.

### 4.2 Versions, drafts and publishing — the rules

1. A factory has at most one open draft (`state = draft`), shared by its editors. It is "Draft of v(N+1)" where N is `factories.last_version_number`.
2. Published versions are immutable: manifest, number and revision never change. Only the factory's `current_version_id` moves.
3. `archived` is a discarded draft. It keeps its manifest for audit and compare, and can never be published.
4. Publishing makes the draft version `N+1`, points the factory at it, records `published_by/at/message`, applies station moves (§4.3) and writes the audit row — one transaction. A trigger NOTIFYs `goal_definitions`.
5. Restore (rollback) moves `current_version_id` to an older published version in one transaction; numbers are not reused. An open draft stays open; its `base` no longer equals current, which the next publish must acknowledge (§8, `draft-base-moved`).
6. Validation is a function of the draft's exact revision. Publish carries the revision it validated; the transaction refuses if the draft moved (`draft-conflict`) or if current moved (`draft-base-moved`).
7. Drafts may be invalid (that is the point of problems). Only `error` problems block publish; `warning` (e.g. a connection with no credential yet, "Azure is blocked") does not.

### 4.3 Runs keep their version

- The engine's line per factory is the current version's line. When the engine starts a run it records `agent_runs.definition_version_id = line.VersionID` and puts the id in `TaskSpec.DefinitionVersionID` and the task token's `v` claim. The run's goroutine already keeps the line it started with ("Runs already started keep the line they started with"), so its contract, command checks, agent files and gateway tools all come from that version.
- When the run finishes, the item's *next* move uses the current line, matched by station id. Items are not pinned to versions: an item waiting at Review when v9 publishes is claimed under v9.
- A goald that dies mid-run loses nothing: the lease expires, the item is re-queued and re-run on the then-current version.
- **Removed stations.** If the new version drops a station id that open items sit at: items `in_progress` there make publish fail (`items-at-removed-station`, 409, lists them; the run must finish or be stopped first); other open items (queued, ready, waiting_human, blocked) must be mapped by the publish request's `station_moves: {"qa": "review"}` to a station of the new version. The moves happen in the publish transaction with a `moved` event (`data: {from, to, reason: "definition v9"}`). Validation reports unmapped ones as an `error` problem with one fix per candidate station.
- **Paused factory.** `factories.paused_at` set ⇒ `Line.Paused` ⇒ the engine claims nothing and releases nothing at that factory; runs in progress finish. Publishing v1 with `start: false` (New-Review checkbox unticked) creates the factory paused; `POST …/resume` starts it.

### 4.4 Model ↔ YAML round-trip (`internal/factorymodel`)

The Visual editor never sends YAML; it sends one **section** of the factory model (§8.3). The server applies it to the draft's `factory.yaml` *as a patch on the YAML node tree*, so everything the section does not own is untouched.

Sections and the YAML they own:

| Section | Owns (paths under `spec` unless noted) |
| --- | --- |
| `basics` | `metadata.name`, `metadata.title`, `metadata.purpose` (or legacy `metadata.description`), `board.workTypes`, `runtime.repository` |
| `line` | `board.stations`, `board.intake`, `board.flow`, `learning.librarian.agent` (shown as the Done station's worker) |
| `agents` | `agents`, `skills`, `runtime.model`; the agents' prompt files |
| `connections` | `connections` |
| `review` | `runtime.budget` |

Everything else (`apiVersion`, `metadata.id`, `metadata.owner`, `runtime.runner/image/auth`, `knowledgeBase`, `contracts`, `learning.*` except the librarian agent, unknown keys) is preserved verbatim and edited in YAML mode only.

**Apply algorithm** (`factorymodel.Apply(doc []byte, s Section, v json.RawMessage) ([]byte, error)`), on `go.yaml.in/yaml/v3` `yaml.Node` (already in `go.sum`; becomes a direct dependency):
1. Parse; a document that does not parse makes Visual read-only for that draft (`yaml-invalid`, 409, with line/column) until it is fixed in YAML mode.
2. Merge the section value into the owned nodes:
   - mappings: change scalar values in place (keeps `Style`, head/line/foot comments); insert new keys after the nearest existing sibling in canonical key order; delete removed keys with their comments.
   - sequences with an identity are matched by it, never by index — stations by `id`, agents by `name`, connections by `name`, skills by `name`, route entries by lane, tools by tool name; reordering moves the existing nodes (their comments travel with them); new items copy the style of their siblings (a flow `{ … }` station stays flow while its encoding fits 100 columns, otherwise becomes block).
   - a renamed key keeps its node and comments (`description` → `purpose` when the user edits Purpose).
   - strings are written plain unless YAML requires quotes; an existing quote style is kept.
3. Encode with the document's own indentation (detected from the first nested mapping: 2 or 4) and sequence style (`CompactSeqIndent` when the source writes `- ` at the parent's column).
4. Blank lines between block entries are kept with a sentinel: before parsing, each blank line becomes a `#goal:blank` comment line, which yaml.v3 attaches to the next node; after encoding, sentinel lines become blank again. Sentinels never reach storage.
5. Safety net: re-parse the output and require `model(output)` to equal the requested section and every other section to equal its value before the save. A mismatch is a 500 and nothing is saved.

**Guarantee (answers the orchestrator's question): feasible.** Kept on Visual saves: comments (head, line and foot), key order, flow/block style, quote style, anchors and aliases, blank lines between entries, indentation width. Normalized: trailing whitespace, irregular indentation inside one document, comments in unusual positions (inside flow collections, between a key and its value) may move to the nearest node. A save that changes nothing semantically does not rewrite the file (byte-identical). YAML-mode saves store the text exactly as typed. "Format" applies steps 3–4 to the whole file, so a formatted file never churns. The test corpus (§13) pins this.

**Model ← YAML** (`factorymodel.FromYAML(doc []byte, files fs.FS) (Model, Ranges, error)`) reads leniently: unknown or invalid values appear as they are and as problems, so a half-written draft still opens in Visual where it parses. `Ranges` maps model pointers to `[firstLine, lastLine]` in `factory.yaml`.

Agents with a legacy `tools: {allow, deny}` block show their built-in tools as read-only "Custom rules — edit in YAML" until the user switches them to `builtins` (which then replaces the block).

### 4.5 Semantic diff (`factorymodel.Diff`)

`Diff(from, to Snapshot) Comparison` where a snapshot is a manifest plus file bytes:

- **Files**: added / removed / modified / unchanged per path, with both hashes.
- **Changes**: one per meaningful difference, grouped by section, each `{section, op: added|removed|changed|moved, target: {kind: station|agent|connection|tool|field, id}, field, from, to, summary, from_lines, to_lines}`. Stations and agents compare by identity, so a reorder is one `moved` change, not N edits. A changed prompt file is an `agents` change on its agent ("Prompt of frontend-engineer changed"); skill and contract files map to the agents and line sections; other files are section `files`.
- `summary` is a short English sentence built from the data ("Build also runs pnpm test", "Merge becomes a merge step", "browser gets frontend-engineer and two write tools").
- Counts: `changes` and `sections` ("3 changes in 2 sections").
- Line-level hunks are computed in the browser from the two files (both are immutable blobs, fetched once); the `from_lines/to_lines` of changes label the hunks ("@@ Line: build station @@").

Field-level "Edited" markers are the same diff restricted to one section and flattened to pointers: `edited: {"/stations/3/checks": <base value>, "/stations/5/action": null}` (null = absent in the base).

```yaml
      browser__click:     { agents: [frontend-engineer], scope: preview }
```

Tool entry keys: `enabled` (bool), `agents` (subset of the connection's agents), `approval` (`required | none`), `scope` (a scope name the connector declares). `access` is accepted and must equal the catalog's class (problem otherwise) but is never required — the catalog is the source of truth. `ask` in `builtins` validates, and is served as `off` with a `builtin-ask-unavailable` warning until G's tool approvals cover built-in tools.

### 4.7 Validation

`authoring.Validate(ctx, draft, overlay)` runs, in order, and returns `Validation{ok, checks[], problems[], counts}`:

| Check id | Section | What | Provider |
| --- | --- | --- | --- |
| `yaml` | files | every YAML/JSON file parses (line/column of the error) | B |
| `schema` | by pointer | `factory.schema.json`; the JSON Schema instance location is mapped to the YAML node, so the problem gets a line and a model pointer | B |
| `line` | line | starts with a queue, ends with done, every agent station has an agent or route, gates point upstream, WIP ≥ agents | B (`config`) |
| `references` | per target | agents, skills, contracts, connections, prompts, local skill folders exist | B (`config`) |
| `name` | basics | name free in the org (`name-taken`) | B |
| `items` | line | open items at stations this draft removes (§4.3) | B (reads `Store.StationLoads`) |
| `images` | connections | connection images pinned (today's warning, now located) | B |
| `secrets` | connections | a header/env value that is a literal, not a reference (`literal-secret`, warning) | B |
| `credentials` | basics, agents, connections | every credential reference (`runtime.modelCredential`, `runtime.repository.credential`, `credential:` words, connection `credential:`) resolves for this factory: C's `Vault.Check` reasons map to codes `credential-not-found` and `credential-not-granted` (error), `credential-expired`/`credential-revoked` (warning) | B's logic over C's `Vault.Check` (review) |
| `connections` | connections | everything connector-specific (G §4.3): unknown connector, settings, scopes, tools, `write-tool-unruled` (error, fixes "Require approval" / "Limit to <scope>"), `connection-blocked` (warning: needs a credential and has none), `merge-needs-github` on the line | G's `connectors.Checker`, registered as an `authoring.Check` (review) |
| (more) | any | extra checks registered by other phases (`authoring.Check`) | C, G |

The `config` package changes from "join every error" to `config.Check(files fs.FS) (*Factory, []domain.DefinitionProblem)`; `Load` keeps its signature (it returns an error when any `error` problem exists) so callers and fixtures stay as they are. `checks[]` carries the green lines of Review & publish: `{id, section, status: passed|failed|warning, summary}` with summaries built from counts ("7 stations, ends with Done, every agent station has an agent"). When C or G is not wired yet, their checks are omitted, not faked.

Budget: validate p95 < 150 ms for a 50 KB `factory.yaml` and 50 files with warm blob cache (C/G lookups are batched: one call each per validation).

## 5. Ports and adapters

### 5.1 New ports (`internal/ports`)

```go
// DefinitionStore keeps factory definitions: file content as immutable blobs in the bucket,
// versions (drafts and published manifests) and the current-version pointer in PostgreSQL.
// Every method acts in the organization of ctx (A's org context helper); the adapter sets
// goal.org_id from it and returns an error when ctx carries none.
type DefinitionStore interface {
	CreateFactory(ctx context.Context, n NewFactory) (FactoryRecord, domain.DefinitionVersion, error) // factory + its first draft; ErrNameTaken
	FactoryRecord(ctx context.Context, id domain.FactoryID) (FactoryRecord, error)
	FactoryRecords(ctx context.Context) ([]FactoryRecord, error)
	DeleteUnpublished(ctx context.Context, id domain.FactoryID, by domain.UserID) error // ErrConflict once published
	SetPaused(ctx context.Context, id domain.FactoryID, paused bool, by domain.UserID) error

	// PutBlobs stores files under their hashes (only hashes the org lacks are uploaded) and returns them.
	PutBlobs(ctx context.Context, files map[string][]byte) (domain.Manifest, error)
	// Blob returns a blob's content, verified against its hash; ErrNotFound when the org has no such blob.
	Blob(ctx context.Context, h domain.BlobHash) ([]byte, error)

	Version(ctx context.Context, id domain.DefinitionVersionID) (domain.DefinitionVersion, error)
	VersionByNumber(ctx context.Context, f domain.FactoryID, n int) (domain.DefinitionVersion, error)
	Draft(ctx context.Context, f domain.FactoryID) (domain.DefinitionVersion, error) // ErrNotFound when none
	Versions(ctx context.Context, f domain.FactoryID, before, limit int) ([]domain.DefinitionVersion, error) // published, newest first
	CurrentVersions(ctx context.Context) ([]domain.DefinitionVersion, error) // the org's factories' current versions

	OpenDraft(ctx context.Context, d OpenDraft) (domain.DefinitionVersion, bool, error) // existing draft returned with created=false
	SaveDraft(ctx context.Context, c DraftChange) (domain.DefinitionVersion, error)     // CAS on revision: ErrConflict
	DiscardDraft(ctx context.Context, f domain.FactoryID, revision int64, by domain.UserID) error
	Publish(ctx context.Context, p Publish) (domain.DefinitionVersion, error)            // one transaction, §4.2
	Restore(ctx context.Context, r Restore) error
}

type NewFactory struct {
	ID          domain.FactoryID // metadata.id of the draft's factory.yaml
	Name, Title string
	Manifest    domain.Manifest
	Source      domain.VersionSource
	By          domain.UserID
}

type FactoryRecord struct {
	ID                domain.FactoryID
	OrgID             domain.OrgID
	Name, Title       string
	CurrentVersionID  domain.DefinitionVersionID // "" when never published
	CurrentNumber     int
	LastVersionNumber int
	DraftID           domain.DefinitionVersionID // "" when no open draft
	PausedAt          time.Time
	CreatedAt         time.Time
}

type OpenDraft struct {
	Factory domain.FactoryID
	Base    domain.DefinitionVersionID // "" = current
	Replace bool                       // archive an open draft first (CLI push --replace-draft)
	By      domain.UserID
}

type DraftChange struct {
	Factory          domain.FactoryID
	ExpectedRevision int64
	Set              domain.Manifest // path → hash, added or replaced
	Remove           []string
	Replace          bool            // Set is the whole tree (push, import)
	By               domain.UserID
}

type Publish struct {
	Factory          domain.FactoryID
	DraftRevision    int64
	ExpectedCurrent  domain.DefinitionVersionID // "" for a first publish
	Name, Title      string                     // from the validated factory.yaml, copied to the row
	Message          string
	StationMoves     map[string]string
	RemovedStations  []string                   // station ids the new version drops
	Start            bool                       // first publish only: false creates the factory paused
	By               domain.UserID
	// (review) G's connection resolution, computed before the transaction by authoring's optional
	// Resolver: stored as definition_versions.resolved (runs on this version read it) and
	// projected into G's `connections` rows (upsert present names, delete removed ones) in the
	// same transaction. Empty until G wires a Resolver.
	Resolved json.RawMessage
	Bindings []domain.ConnectionBinding
}

type Restore struct {
	Factory         domain.FactoryID
	Version         domain.DefinitionVersionID
	ExpectedCurrent domain.DefinitionVersionID
	By              domain.UserID
}
```

```sql
CREATE FUNCTION definition_versions_guard() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN

  IF NEW.factory_id <> OLD.factory_id OR NEW.org_id <> OLD.org_id THEN

  END IF;
```

## 7. Bucket layout

```
s3://<bucket>/
├── catalog/
│   └── templates/<name>/<version>/      Goal-curated starting points, immutable per version
│         template.yaml                  title, summary, description, connectors[], changed (date)
│         factory/…                      factory.yaml (metadata.id 00000000-0000-0000-0000-000000000000), agents/, skills/, contracts/, evals/
└── orgs/<org-id>/
    └── blobs/<sha256>                   one definition file, written once (PutIfAbsent), never overwritten
orgs/<org-id>/factories/<id>/…           A's interim layout (A §7, after A4's MigrateLegacy); read once by the import (§14), then ignored; removed by hand later (review)
```

- Blob keys are lowercase hex with no extension. A reader verifies the hash of every blob it fetches.
- Bucket versioning stays on (it protects deletes and `knowledge/`); blobs never create a second version because they are never rewritten.
- Templates: a template carries no `credential:` values ("Templates never include them"); `goal catalog templates push` refuses one that does and refuses an existing `<name>/<version>`. goald lists `catalog/templates/` every 5 minutes into an in-memory index (immutable per version; a cache, not state). `catalog/connectors/` is G's.
- Blank: the `blank` template when it exists; otherwise a skeleton with only `apiVersion`, `kind`, `metadata` and `spec.runtime` (`GOAL_DEFAULT_AGENT_IMAGE`), no station or agent names, because names in Go would break the config-driven rule. The Line section then starts empty with "Add station".

## 8. API (tag `definitions`)

All under `/v1/orgs/{org}`. `{factory}` = id or name. `{version}` = a number, `current`, `draft`, `base` (the draft's base) or `source` (the draft's starting tree). Errors are RFC 9457 with a `code` extension member (cross-spec: Problem gains optional `code` and `problems[]`). Concurrency tokens use `ETag`/`If-Match`; a failed precondition is **412** `draft-conflict` with the current value in the body.

Conflict handling (two editors): each save re-reads the draft, checks the precondition against *that part* (the section's etag, or the file's hash), applies the change on top of whatever else changed, and commits with `SaveDraft(ExpectedRevision)`; a revision race re-runs the cycle (at most 3 times). Every save emits a `definition` stream event so the other editor's untouched sections refresh.

## 11. Security and tenancy

- Every table has `org_id` and RLS; the adapter runs each call in one transaction with `SET LOCAL goal.org_id` from ctx (A). Factories, versions and blobs of another org answer 404.
- Roles (A's helper, checked in handlers before calling the service): viewer reads drafts, versions, compare and files; editor (or org admin/owner) writes drafts, publishes, restores, discards, pauses, deletes an unpublished factory; any member creates a factory and becomes its editor. "Who approves" edits A's `factory_roles`, never a draft.
- Blob reads are only ever through a factory/version route the caller can view; there is no org-wide blob endpoint.
- Paths: `^[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*$`, ≤ 255 chars, no `.`/`..` segments, no hidden segments, not under `knowledge/`. Limits: 1 MiB per file, 1,000 files, 16 MiB per tree or request, YAML ≤ 1 MiB with alias expansion capped (yaml.v3 limits plus a 100,000-node cap) and nesting ≤ 64.
- Secrets: definitions hold references (`credential:` names, `env:` refs), never values; `literal-secret` warns on literals; templates and clones carry no credential names. No file content is logged.
- Contracts keep compiling with no loader (no remote or file refs).
- Audit (A's `audit_log`, same transaction): `factory.created` (source), `factory.deleted`, `definition.published` (number, message, moved item count), `definition.restored` (from, to), `definition.draft_discarded`, `factory.paused`, `factory.resumed`. Draft saves are not audited (the version row has `updated_by/at`).

## 18. ADR 0005 amendment (text to add to `docs/adr/0005-factory-definitions-in-object-storage.md`)

> ## Amendment — 2.2: versions in PostgreSQL, content as blobs
>
> Status: accepted · amends decisions 1, 2, 4, 5 and 7.
>
> **Context.** A version was "whatever object versions a listing returned". A bucket has no transaction across objects, so a refresh that lists a prefix halfway through a push can load new prompts with the old `factory.yaml`; pushing `factory.yaml` last narrows that window but does not close it. The builder adds shared drafts, publishing by people in the UI, rollback, per-run version pinning and questions such as "which factories use this credential" — all of which need atomic writes, foreign keys and queries.
>
> **Decision.**
> 1. The bucket stays the home of definition **content**: every file is stored once per organization under its SHA-256, `orgs/<org-id>/blobs/<sha256>`, written with a conditional put and never overwritten. Readers verify the hash.
> 2. PostgreSQL is the **index of versions**: `definition_versions` holds each draft and published version as a manifest (path → sha256) with its number, author and publisher; `factories.current_version_id` names the version that runs. Publishing (and restoring) is one transaction that also writes the audit row; a trigger NOTIFYs `goal_definitions` and every goald reloads. Published versions are immutable; rollback moves the pointer.
> 3. Agent runs record the version they started on (`agent_runs.definition_version_id`) and finish on it; the next step of an item uses the current version.
> 4. `internal/config` still loads a definition from an `fs.FS`; the tree now comes from a manifest and its blobs.
> 5. Editing happens through goald's API: the builder (Visual and YAML) and the CLI both write a draft; `goal factory pull/push/validate/list/publish` call the API instead of the bucket. Validation runs on save and before publish and includes credential grants.
> 6. Jonah's remediations become drafts published like any other; their rollback pin is the previous version id.
> 7. Templates are definitions saved as data under `catalog/templates/<name>/<version>/`. The other two curated catalogs are definition content too: vendorable skills under `catalog/skills/` (phase E) and connector specs under `catalog/connectors/` (phase G). Nothing else goes in the bucket. (review)
>
> **Rejected.** Keeping versions implicit in object versions (no atomicity, no foreign keys). Moving file content into PostgreSQL (definitions are file trees agents and Bedrock read as files; the bucket keeps them cheap and readable). Per-factory prefixes of mutable files (the blob store deduplicates across versions and clones and makes every version reproducible).
>
> **Consequences.** A version is reproducible from its manifest alone. The legacy `factories/<id>/` prefix is imported once as v1 of each factory and then ignored. Unreferenced blobs accumulate until a garbage collector is added. The bucket's object versioning stays on as protection, no longer as the version mechanism.
