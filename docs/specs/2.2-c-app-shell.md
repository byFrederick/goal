# 2.2-C — App shell and organization screens

Status: draft for review · depends on A · tag `shell`

## 1. Summary

The web UI moves from a single-factory sidebar under `/f/:factory` to the canvas's organization shell. It has a 72px rail, a factory sidebar (Work / Build / Learn) and an organization sidebar. On a phone it becomes a top row, a bottom tab bar and an organization sheet. All routes live under `/o/:org/...`, and old links redirect. C ships the Factories home and Organization settings on phase A's API, plus three small read endpoints the chrome needs (attention badges, factory summaries, the org-wide "waiting on you" list). `web/src/api` moves onto the generated `@goal/api-client` with org-scoped query keys and one SSE stream per open organization. The shared component inventory in `web/src/ui` is what phases D and E (and later phase 3) build their screens from. (no-auth) There is one local user and nothing is shown or hidden by role; Members and roles moves to phase 4.

## 4. Domain and engine changes

The engine is untouched. `internal/domain` gains one read model:

```go
// Attention is what a factory needs from people right now.
type Attention struct {
	Factory       FactoryID
	WaitingHuman  int         // items in state waiting_human
	WaitingByType []TypeCount // WaitingHuman by work type, for the overview's "2 changes" (C2)
	Blocked       int         // items in state blocked
	Andon         *AndonPull  // the open pull, nil when the line runs
}

// AndonPull is an open stop of a factory's line. (review) E §4.4 extends this same type (ID,
// Kind, Station, ClearedBy, ClearedAt, Note, Data); there is one domain.AndonPull.
type AndonPull struct {
	Reason   string
	PulledBy string // A's Actor.Ref(): "system:engine" or "user:local" (no-auth)
	PulledAt time.Time
}
```

## 5. Ports and adapters

`ports.Store` gains two reads. The organization comes from the request's org transaction, using A's Tenancy convention. If A passes `OrgID` explicitly instead, these follow it.

```go
// Attention returns, for every factory of the organization, the items waiting for a person
// (with their split by work type), the blocked items and the open andon pull, ordered by factory
// id (C2: the in-memory store knows no factory names; the API orders by its factory list).
// Factories with nothing pending are included with zeros.
Attention(ctx context.Context) ([]domain.Attention, error)

// WaitingHuman returns up to limit items in state waiting_human in the given factories,
// most recently changed first (updated_at desc, id). (review) Interim: E11 replaces it with
// FlowStats.InboxItems (waiting_human, blocked and expedite items) and deletes it.
WaitingHuman(ctx context.Context, factories []domain.FactoryID, limit int) ([]domain.Item, error)
```

- Implemented by `internal/adapters/postgres` (sqlc) and the in-memory fake in `internal/ports/porttest`. Added to `storetest`.
- `internal/api.Items` gains the same two methods. The handlers live in the new file `internal/api/shell.go`.
- No new depguard rules: `internal/api` already may import `domain`, `ports`, `config`, `engine`.

## 6. Data model

No migration. Queries (`queries/attention.sql`):

```sql
-- name: FactoryAttention :many
SELECT f.id AS factory_id,
       count(w.id) FILTER (WHERE w.state = 'waiting_human')::int AS waiting_human,
       count(w.id) FILTER (WHERE w.state = 'blocked')::int       AS blocked,
       a.reason AS andon_reason, a.pulled_by AS andon_pulled_by, a.pulled_at AS andon_pulled_at
FROM factories f
LEFT JOIN work_items w ON w.factory_id = f.id AND w.state IN ('waiting_human', 'blocked')
LEFT JOIN andon_pulls a ON a.factory_id = f.id AND a.cleared_at IS NULL
GROUP BY f.id, a.id
ORDER BY f.id;

-- name: WaitingByType :many   (C2: the overview's waiting.items_by_type, same snapshot)
SELECT factory_id, type, count(*) AS waiting FROM work_items
WHERE state = 'waiting_human' GROUP BY factory_id, type ORDER BY factory_id, type;

-- name: WaitingHumanItems :many
SELECT * FROM work_items
WHERE state = 'waiting_human' AND factory_id = ANY (sqlc.arg(factories)::uuid[])
ORDER BY updated_at DESC, id
LIMIT sqlc.arg(lim);
```

- Row-level security (A) limits both queries to the organization; neither adds a `WHERE org_id`.
- `work_items_open_idx (factory_id, station) WHERE state NOT IN ('done','cancelled')` serves both queries. Add a partial index only if `EXPLAIN` at 10k open items shows a need (it would take `00050`).

**Conformance (`storetest`)**
- Attention counts only `waiting_human` and `blocked`, per factory.
- It reports only an uncleared andon pull and lists idle factories with zeros.
- WaitingHuman orders newest change first, ignores factories not passed, and honours `limit`.
- Postgres integration: with A's harness, rows of another organization are never counted.

## 8. API

Tag `shell`. Every path runs behind A's org middleware: an unknown or deleted org gets 404, and each transaction does `SET LOCAL goal.org_id`. (no-auth) No role checks: every path passes A's `Authorizer` seam, and "waiting on you" means waiting on a person, so it counts every decision. Errors are RFC 9457 `Problem`.

### `GET /v1/orgs/{org}/attention` — `getOrgAttention`
This feeds the chrome's badges and is cheap enough to refetch on every stream event.

```yaml
OrgAttention:
  type: object
  required: [waiting_on_you, factories]
  properties:
    waiting_on_you: { type: integer }            # sum of factories[].waiting_on_you (+ phase 3's approvals)
    # (restructure) phase 3.1 adds credentials_needing_attention (expired or failing); C ships without it
    factories: { type: array, items: { $ref: FactoryAttention } }
FactoryAttention:
  type: object
  required: [factory_id, waiting_on_you, blocked_items, andon, connections_blocked]
  properties:
    factory_id: { type: string, format: uuid }
    waiting_on_you: { type: integer }   # waiting_human items (every decision; no-auth); Phase 3 adds pending tool approvals
    blocked_items: { type: integer }
    andon: { $ref: AndonPull, nullable: true }
    connections_blocked: { type: integer }  # phase 3 fills; 0 until phase 3
AndonPull: { type: object, required: [reason, pulled_by, pulled_at],
  properties: { reason: {type: string}, pulled_by: {type: string}, pulled_at: {type: string, format: date-time} } }
```

### `GET /v1/orgs/{org}/overview?window=7d` — `getFactoryOverview` (review)
`window` uses the same pattern as metrics (`^[1-9][0-9]?d$`, default `7d`). The previous window has the same length and ends where this one starts.

```yaml
FactoryOverviewList:   # (review) renamed from FactorySummaryList; B's former FactorySummary is now fields of Factory
  required: [window, since, until, waiting_on_you, spend_usd, budget_usd, factories]
  properties:
    window: { type: string }
    since: { type: string, format: date }
    until: { type: string, format: date }
    waiting_on_you: { type: integer }
    spend_usd: { type: number }
    budget_usd: { type: number, nullable: true }   # sum of factories' budget_usd; null when none has a budget
    factories: { type: array, items: { $ref: FactoryOverview } }
FactoryOverview:
  required: [factory, health, andon, throughput, constraint, waiting, spend_usd, budget_usd]
  properties:
    factory: { $ref: Factory }                    # A's shared schema; B adds current/draft/paused there (no separate version object) (review)
    health: { enum: [running, stopped, draft] }   # stopped = open andon; draft = no published version (B/D)
    andon: { $ref: AndonPull, nullable: true }
    throughput:
      required: [per_day, previous_per_day, days]
      properties:
        per_day: { type: number }          # items done in window / days
        previous_per_day: { type: number }
        days: { type: array, items: { required: [day, done], properties: { day: {format: date}, done: {type: integer} } } }  # one entry per day, zeros included
    constraint:
      nullable: true
      required: [station]
      properties:
        station: { type: string }
        busy: { type: number, nullable: true }   # E: share of the window the station was busy; null until E
    waiting:
      required: [on_you, items_by_type, tool_approvals]
      properties:
        on_you: { type: integer }
        items_by_type: { type: array, items: { required: [type, count] } }
        tool_approvals: { type: array, items: { required: [connection, count] } }   # phase 3; [] until phase 3
    spend_usd: { type: number }
    budget_usd: { type: number, nullable: true }   # runtime.budget.weeklyUsd (B §4.6, enforced by D) × window days / 7; null without one (review)
```

**Handler**
- For each factory it reads `Attention`, `StationLoads` → `domain.Line.Constraint` (today's snapshot heuristic), `FlowMetrics` for the window and for the previous window, and the budget from the definition.
- That is 3N+1 queries. It is acceptable at the expected org size (≤ 25 factories). Above that, it logs a warning with the count and duration.

### `GET /v1/orgs/{org}/inbox?factory=&limit=20` — `getInbox` (review)
One inbox for the Factories home (C), the Floor's Needs you card and the Phone board (E). C2 ships it with entry kind `decision` only (every item waiting for a person; no-auth); E11 adds `andon`, `rework_warning`, `blocked`, `expedite` and the approval brief; Phase 3 adds `tool_approval`. The schema is E §8.4's `Inbox{entries, truncated}` / `InboxEntry` without E's `factories[]` (the counts are `/attention`'s); C2 ships `id, kind, factory, since, item, station, action` and E11 adds its fields. Entries are ordered by kind, then oldest first; when more than `limit` exist the most recent are kept and `truncated` is set. C sorts the home list newest first on the client; `limit` is 1–500, default 20 here. Sources implement `InboxSource.Inbox(ctx, InboxQuery{Factories, Limit})` (C2: the query carries the `?factory=` filter and the limit, so no source reads unboundedly) and register in `api.Deps.InboxSources` after the built-in `decisions`.

**SSE**
- C consumes A's `GET /v1/orgs/{org}/stream` (optional `?factory=`).
- It handles `event: item` (`StreamEvent` + `org_id`) and `event: resync`. It ignores unknown event names, so B, E and phase 3 can add `definition`, `factory`, `credential`, `approval`, `connection` without breaking older clients. C owns this event union (README registry). (review)

Query keys (`api/queries.ts`), all org-scoped by org id, factory by id:

```ts
export const keys = {
  orgs: ['orgs'] as const,
  org: (org: string) => ['org', org] as const,                  // prefix for everything below
  orgDetail: (org: string) => ['org', org, 'detail'] as const,
  attention: (org: string) => ['org', org, 'attention'] as const,
  factories: (org: string) => ['org', org, 'factories'] as const,
  overview: (org: string, window: string) => ['org', org, 'overview', window] as const,   // (review)
  inbox: (org: string, factory?: string) => ['org', org, 'inbox', factory ?? 'all'] as const, // (review) E's key
  settings: (org: string) => ['org', org, 'settings'] as const,
  factory: (org: string, f: string) => ['org', org, 'factory', f] as const,
  board: (org: string, f: string) => ['org', org, 'factory', f, 'board'] as const,
  metrics: (org: string, f: string, w: string) => ['org', org, 'factory', f, 'metrics', w] as const,
  items: (org: string, f: string, filter: ItemFilter) => ['org', org, 'factory', f, 'items', filter] as const,
  item: (org: string, item: string) => ['org', org, 'item', item] as const,
  events: (org: string, item: string) => ['org', org, 'item', item, 'events'] as const,
};
```

**staleTime**: orgs/factories 60s; attention 10s; overview 30s; settings 30s.

**Stream** (`shared/stream.tsx` `OrgStream`, one EventSource per open org, mounted in the `o.$org` layout)
- `packages/api-client` `subscribe` changes to `subscribe(baseUrl, { org, factory? }, handlers)`.
- Handlers: `onItem`, `onEvent(name, data)` for other event names, `onResync` (on `event: resync` and on every reconnect after the first open, not on the first open), `onStatus('connecting' | 'live' | 'reconnecting')`.
- `invalidationsFor(org, event): QueryKey[]` is a pure function, unit-tested. For `item` it returns E §10.3's rules (review):
  - `attention(org)`, `inbox(org, *)`, the factory's work keys named one by one (`board`, `metrics`, `items`, and E's `weekly`, `lead-time`, `constraint`, `andon`, `agent`; tool-call kinds only `board`), `item(org, e.ref)`, `item(org, e.item_id)` (batched 300ms, as today). Never the bare `factory(org, f)` prefix: B's draft, model and compare keys and phase 3's factory credentials live under it and must not refetch while agents work (D §16) (review);
  - `overview(org, *)` (batched separately, at most once per 5s).
- Other phases register handlers for their event names in `streamHandlers` (B `definition` → B's keys + overview; Phase 3 `credential` → credentials keys + attention; E `factory` → work keys + inbox + attention; Phase 3 `approval` → approvals + attention + inbox, `connection` → connections + attention) (review).
- `resync` invalidates `org(org)`.
