# Add a provider

A provider is data, never code in the engine. Runs reach a provider through the factory's environment files, and its credentials are the organization's secrets ([ADR 0037](../../../docs/adr/0037-secrets-and-environment-files.md)). The boundary rules are in [architecture.md](../../rules/architecture.md) (depguard in `.golangci.yml` enforces them; never silence it). Read [architecture.md](../../../docs/engineering/architecture.md) and [testing.md](../../../docs/engineering/testing.md) first.

1. **Decide what is needed.** If runs only need the provider's credentials as environment variables, files or an MCP server (an API, a CLI, an MCP server), nothing in Goal has to change: a factory names a secret in its environment file, and Custom in Add a tool writes those lines. Add a tool template (steps 2 and 3, then 9) only when the provider should appear in the catalog. If goald itself must call the provider (a code host, a knowledge source to sync, embeddings), you also need an adapter: do steps 4 to 10.
2. **Write the template** as `internal/catalog/<name>.yaml` in the shape of the templates beside it: `apiVersion: goal/v1`, `kind: Template`, `metadata` (name, title, description), and `spec` with its secret slots (`secrets`, each with a `slot`, a title, a description and a `suggest`ed secret name), what it adds (`env`, `files`, `mcp`, tools) with `{{slot}}` references, and an optional HTTP `test` that proves the values work. `catalog.Parse` checks it against `domain.ToolTemplate.Check`. Follow the change map's catalog row (`docs/engineering/change-map/162-catalog.md`): a template that needs a field no template has changes `domain.ToolTemplate`, `GET /v1/catalog` in `contracts/api/openapi.yaml` and `internal/api/catalog.go`.
3. **Test the template.** `internal/catalog/catalog_test.go` loads every template; add the new name to `TestTemplates_LoadAll` and `TestCatalog_List` in `internal/api`. Run `go test ./internal/catalog/... ./internal/core/domain/...` and `go test -run TestCatalog_ ./internal/api`.
4. **Find the port.** Pick the interface in `internal/core/ports/ports.go` that the adapter implements (`CodeHost`, `SourceReader`, `Embedder` and so on). A new port is a design change: write an ADR first with [goal-adr](../goal-adr/SKILL.md).
5. **Write the adapter** in its own package `internal/adapters/<port>/<name>`, under the group named after the port it implements (`codehost/gitlab`, `embedder/openai`); the package name is the leaf directory. Let it take its configuration through a constructor. It calls out through the public-only connection transport goald passes in (`connectionTransport` in `cmd/goald`), follows no redirects, and puts no secret in an error or a log line.
6. **Test the adapter.** Run the port's conformance suite from `internal/core/ports/porttest` when the port has one. Against a real dependency, write an integration test tagged `//go:build integration`, which `task test-integration` runs. Against an HTTP API you cannot run locally, write unit tests against a local test server that answers as the provider documents: listing, paging, refusals and errors.
7. **Wire it** in `cmd/goald/main.go`, by constructor, beside the adapters of the same port. A sync reader goes in the `readers` map of `openKnowledge` under the reader key a synced source names. Use no globals and no `init()`.
8. **Run the checks.** `task lint` (depguard included) and `task test`.
9. **Docs as built.** Update `docs/engineering/architecture.md` (the port's table and the adapter) and the spec that names the provider. A new environment variable follows the change map's row for it.
10. **Deliver** with [goal-deliver](../goal-deliver/SKILL.md). Name the integration tests you could not run and why.
